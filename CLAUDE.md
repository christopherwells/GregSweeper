## Modifier Load-Bearing Filter (generation)

Beyond solvability, every generation path (precompute, daily play-path local-gen, weekly play-path local-gen, challenge) requires that each non-mystery modifier on a board contributes at least one deduction the player needs to make. Implemented via `findDecorativeGimmicks` in `boardSolver.js`: strip one gimmick type's info at a time and re-run the solver — if the board is still solvable, that type is decorative on this layout and the candidate is rejected.

- **Mystery is exempt** — it removes info by definition, can't be load-bearing. Every mystery board would fail the test, so we don't apply it.
- **Worm is exempt** — same logic as mystery: worms only delay information (a covered number returns when the worm moves), so they can never contribute a deduction. Exemption is by omission from `TESTABLE_GIMMICK_TYPES` in boardSolver.js; `gradeGimmickContribution` grades worm `structural`.
- **Walls and locked are exempt** — they're structural (topology change, reveal-order change), not deduction contributors. Stripping them would invalidate the cell numbers.
- **Sonar / compass / wormhole / liar / mirror** are testable. The filter strips their constraints (and for mirror, the un-swap assumption) and asks "could the player still solve this board with only the other modifiers' info, AT THE SAME DIFFICULTY?"
- **Per-type, not per-cell.** A board with 3 sonar cells where only 1 contributes passes — sonar AS A TYPE contributed. We don't iterate per-cell; that's intentional.
- **A modifier "contributes" when stripping it does ANY of**: makes board unsolvable, raises technique level (Pass C tank/gauss instead of Pass A), or adds ≥2 clicks. The threshold catches both strict load-bearing AND meaningful shortcut — a sonar that lets the player skip a tank-solve counts even if Pass C could have eventually solved without it. See `_gimmickContributes` in `boardSolver.js`. The 2-click threshold avoids penalizing incidental savings (1 saved click is often just "the same cell deduced moments later via a neighbor").
- **Fallback when no candidate contributes**: precompute falls back to the highest-scoring solvable candidate (with a console note); play-path retry loops relax the requirement after RELAX_AFTER_BASES (challenge) / LOAD_BEARING_BUDGET=25 (daily/weekly) attempts. Better to ship a decorative-modifier board than spin forever.
- **Why this matters**: an audit (2026-05-10) found ~3-5 of the prior 13 dailies shipped decorative modifiers (sonar, compass, or liar that contributed nothing). With force-injected coverage missions pushing under-sampled gimmicks, the natural rate of "decorative" was rising. This filter makes the modifier MEAN SOMETHING on the board — either required, or at least a useful shortcut.

## The No-Guess Contract (status per 2026-06-10 adversarial audit)

**Where it holds, and how:** `generateBoard` is NOT self-certifying — its terminal fallback returns the best-effort (possibly unsolvable) board, so the contract lives in caller-side verification. Challenge/timed: certified from the player's ACTUAL first click; the relax tiers (technique floor, load-bearing) never relax solvability — worst case regenerates forever, never ships uncertified. Daily/weekly: certified from the board CENTER at precompute + every load; the rendered "Start here" cell is a separately-searched certified full-solve anchor. Hard gates added 2026-06-10: precompute/regenerate scripts THROW rather than write an uncertified canonical; the client strip-modifiers fallbacks verify (bounded retry) before shipping/writing; first-click mine relocation was REMOVED 2026-06-12 (frozen board: a first-click mine is a bomb hit, the canonical never mutates); the post-tutorial warm-up board uses the certified generator. Daily/weekly bomb strikes are information-monotone (mine preserved, numbers unchanged, strike = free flag) — they can never create a guess state. A revealed mine is modeled as a KNOWN MINE (sim=2) in `findDeducibleFrontier` — modeling it as revealed-safe poisoned every adjacent constraint after a strike (fixed 2026-06-10; regression-tested).

**The per-state honesty asterisk:** the certificate guarantees a no-guess PATH from the certified anchor, not that every reachable state is deduction-complete. A daily player who skips the marked start can legitimately reach proof-free states (measured: ~71% of off-path first clicks) — the board stays winnable via the start cell. Chaos is OUTSIDE the contract by design and is now labeled so in the UI (mode card "No guarantees", help-modal line); site metadata says "every standard board".

**Reveal gating (closed 2026-06-10, per-board):** sonar / compass / wormhole constraints are usable by the solver only once their number is on screen — the origin cell revealed; for wormhole, EITHER endpoint (both display the pair sum). Implemented as `gimmickConstraintVisible` in `boardSolver.js`, applied in `isBoardSolvable` (Pass A push + `buildGimmickRuntimeConstraints` for Pass B/C) and `findDeducibleFrontier`. The gate's default comes from the BOARD's own contract flag: `createEmptyBoard` stamps `board._gatedCert = true`, `serializeBoard`/`deserializeBoard` carry it as `gatedCert` in canonical payloads (rules-validated boolean), and `gamePersistence` saves/restores it — so newly generated boards certify gated on every solver surface (generation acceptance, load re-certification, features, start-cell search, receipts, bomb pricing) while historical canonicals (no flag) keep their ungated contract verbatim. `options.gateGimmickOrigins` overrides for tooling. Cross-contract asymmetry: gating only removes constraints, so a gated certificate ALMOST always implies an ungated one — not a theorem, because a wide ungated gimmick constraint can merge components past the 20-unknown tank limit into the (sound but incomplete) gauss path, occasionally proving LESS with more information (~3% of probe boards). Harmless: fetched canonicals are used VERBATIM — the client's load-time solve only feeds features / par / start-cell, it never rejects the board. Measured before shipping (`scripts/measure-reveal-gating.mjs`, 61 canonicals): 41 unaffected, 16 identical, 2 feature-drift (already played), 2 lose certification — weekly 2026-05-04 (past, left as history) and daily 2026-06-14 (precomputed ahead; regenerate before it goes live). Feature determinism: both precompute scripts now also write `dailyMeta/{date}` (and `dailyMeta/{weekStart}_weekly_first`) at generation time, so the generator's gated counts land before any client — possibly on older code, computing ungated counts — can upsert its own. Residual accepted risk: a client that cannot reach Firebase at all on a gimmick-board date locally generates with gated acceptance and can diverge from an old-contract canonical (same class as any code-version drift; the canonical-board architecture absorbs it for everyone online). Same commit also fixed a related certifier hole: liar stacks freely on base-value gimmicks, and `buildStaticGimmickConstraints` used to emit the liar-adjusted `displayedMines` as an EXACT constraint — a false premise that could certify a safe cell as a provable mine on challenge L81+ liar+sonar/compass/wormhole stacks. Such cells now contribute nothing, matching `isPureLiar`'s contract (zero canonical boards ever carried one; regression-tested in `test/revealGating.test.mjs`).

**Mystery is information-free, and the solver now enforces that locally (2026-07-10 audit).** `getPlayerVisibleCount` returns UNKNOWN(255) for a mystery cell and is the ONLY populator of `adjCount` on both constraint-build paths, and `buildConstraints` skips 255 — so `isBoardSolvable` is a **mystery-BLIND** solver and certification is CONSERVATIVE: a board only certifies if it fully clears WITHOUT ever reading a "?". Mystery therefore cannot force a guess (measured: over 4000 random-mystery boards, no certified board ever cited a mystery cell as a proving source, and every board the gate rejected became solvable once mystery numbers were readable — 100% capture of load-bearing mystery). This is also why mystery is exempt from the load-bearing filter: it only removes information. Flood parity holds because `recomputeDisplayedMines` leaves a mystery cell's `displayedMines` undefined, so the certifier's cascade and the live `floodFillReveal` both drive off the true `adjacentMines`. **The one guard that was missing:** `buildStaticGimmickConstraints` gated only on `isMine || displayedMines == null`, so a mystery cell stacked on a base-value gimmick (which WOULD carry a real `displayedMines`) would have emitted a constraint the certifier consumes while the player sees only "?" — a genuine no-guess hole, unreachable only because `applyGimmicks` places mystery first and base-value gimmicks skip `hasDisplayBlockingGimmick` cells. It now skips display-blocked cells (mystery + pressure plate) explicitly, so the solver is safe on its own terms rather than by an invariant enforced in `gimmicks.js`. Regression-tested in `test/mysteryConstraintGuard.test.mjs` (including a CONTROL case that a plain wormhole pair still emits, so the guard can't silently over-block).

**Known remaining gaps (documented, not yet fixed):**
- **magnetPull: RESOLVED 2026-06-11** — redesigned from relocation to EXTRACTION (mines in the 3×3 are removed from the board entirely, revealed as defused markers, `state.totalMines` decremented). Removal is information-monotone — numbers only drop, no mine ever lands on a proven-safe cell — so the certificate survives and the liar-clamp exploit class is gone. Pinned by `test/magnetExtract.test.mjs`.
- **Locked-cell certification oracle: RESOLVED 2026-06-12** — the certifier no longer auto-reveals freed locked cells via ground truth; an unlocked cell is an ordinary unknown the passes must PROVE safe (still-locked cells are excluded from deduce-reveal sites so counters can't spin), and zero-valued cells now act as Pass A constraint sources (a zero adjacent to a locked cell is a real proof the old flood-exclusion missed). `test/lockedOracle.test.mjs` pins the first constructed counterexample (a 50/50 behind a lock certified under the oracle, refuses now). All shipped locked canonicals (dailies 2026-06-14/16, weeklies 2026-06-08/15) re-certify under the honest solver — no regenerations were needed.
- **Pressure plates: MITIGATED 2026-06-12 (calibration, not proof)** — the countdown is now par-calibrated via `plateSeconds` in difficulty.js: Pass-A-resolvable disarm work keeps the classic 10s/step rate, and each target the Pass-A estimator could NOT resolve (needs subset/tank reasoning — previously nearly free, the systematic under-timing) is billed at PLATE_TIER_WEIGHT × the par model's dearer tier coefficient, with a never-below-classic per-target floor, PLATE_MIN_SECONDS, and a PLATE_MAX_SECONDS cap. The certificate still doesn't model wall-clock (an unusually slow player can lose to a deadline) — the deadline just no longer ignores reasoning difficulty, and it rescales automatically with every refit. Pinned by `test/plateSeconds.test.mjs`.
- **First-click mine relocation: RESOLVED 2026-06-12 — the board is FROZEN.** Daily/weekly first-click mines are no longer relocated; the click falls through to the standard bomb-hit path (info-value penalty, strike marker, no game over) like any other mine click. Zero divergence: every player's canonical board is byte-identical for the whole date, and submitted features always describe the played layout. The marked start cell remains the certified safe entry; ignoring it is the player's choice.

## Board Topology (the solver is geometry-blind)

A board's adjacency is a GRAPH, not a geometry, and `src/logic/adjacency.js` is the single place that answers "what touches what". Two boards can share the same `rows`/`cols` container and have completely different neighbor structure. There are two ways a board declares its topology, and `buildNeighborCache(board, rows, cols)` returns the same data shape for both, so no consumer can tell them apart: `Array<number[]>`, outer length `rows*cols`, outer index `r*cols+c`, inner entries flat neighbor indices, no self, no duplicates, symmetric.

- **Implicit** (every board shipped today): the rectangular 8-neighborhood minus wall-severed edges, derived on demand from `rows`, `cols`, and `board._wallEdges`.
- **Explicit** via `board._cellNeighbors`, stamped by `defineCellNeighbors(board, rows, cols, adj)`: when present it IS the topology, full stop. `rows`/`cols` degrade to pure container indexing (the cell list reshaped, so `(row, col)` says nothing about what a cell touches) and walls do not enter, because a severed link is simply absent from the list.

`defineCellNeighbors` VALIDATES before stamping — bounds, no self-loops, no duplicates, and above all SYMMETRY. An asymmetric edge list does not crash; it quietly certifies a board nobody can solve, because one cell's clue counts a mine the mine's own neighborhood does not count back. Validation runs at construction and on restore from a save, never in a hot loop; `isValidCellNeighbors` is the boolean form for deciding whether to TRUST a topology that arrived from outside the process.

**An explicit topology rides the game save as its own top-level `cellNeighbors` field**, exactly as `wallEdges` does and for the same reason: the snapshot is JSON, and `JSON.stringify` drops properties stamped on the board ARRAY. Without it a tiling game saved and resumed came back RECTANGULAR mid-play — the board silently changing shape under the player, with the adjacency it was certified under gone (found in the Phase 1 adversarial review, fixed the same day). `isSaveResumable` REJECTS a save whose topology fails validation rather than restoring a corrupt one, and `tryResumeGame` re-stamps through `defineCellNeighbors` before anything reads the board. Ordinary rectangular saves emit `null` and are unaffected. Pinned in `test/persistRoundTrip.test.mjs` and `test/resumeEligibility.test.mjs`.

**Walls are baked INTO the neighbor list rather than consulted alongside it.** `hasWallBetween`'s diagonal rule synthesizes the four orthogonal edges of the 2×2 block a diagonal crosses, which is irreducibly rectangular; on a non-rectangular topology there are no diagonals to disambiguate, so a severed link is just a missing edge. This is why re-keying `_wallEdges` from `"r,c-r,c"` to index pairs was considered for Coastline and REJECTED (Christopher, 2026-07-19): it would not have bought geometry-neutrality, and the string format is a stored contract — it lands in the signed bytes of every canonical `dailyBoard`/`weeklyBoard`, in every `cruxes/{date}` payload, and in every in-flight save. Changing it silently UN-WALLS every board already written (a lookup builds a key the stored Set does not contain and finds nothing, which reads as "no wall" rather than as an error). The nightly sweep would catch future dates loudly and never touch past ones, so Archive replays would get wrong par and a false Certified chip with no test firing.

**Coastline Phase 1 (2026-07-19) proved the no-guess contract transfers off the square grid.** `isBoardSolvable` needed NO changes: inside it, `cols` is only ever CONTAINER indexing — the `idx = (r,c) => r*cols+c` closure, a `preFlagCells` bounds check, and row-major setup loops — and never expresses adjacency, while `rows*cols` is always a pure cell count. The deduction core already ran on flat indices plus a neighbor list. Handing it an explicit topology is the whole port. The gate is `test/tilingCertification.test.mjs` against `test/fixtures/tiling488.mjs` — a 4.8.8 truncated-square tiling (octagons + interstitial squares, valences 3/4/5/8, and crucially diagonal octagons do NOT touch since a square sits between them). What Phase 1 left rectangular has since been converted:
- **Compass's ray — RESOLVED in Phase 2.** A compass is not a topological property: sonar asks "how far", which a graph answers, but a compass asks "which way", which needs geometry `_cellNeighbors` does not carry. So Phase 2 computes the ray from cell POSITIONS at generation (`computeCompassRay` in tilingGeometry.js — 8 directions incl. diagonals) and STORES it per cell; `compassRayCells` returns that stored list on an explicit topology (it THREW in Phase 1). Display (`recomputeDisplayedMines`) and certifier (`buildStaticGimmickConstraints`) read the identical stored ray, so they can never disagree about a geometry neither of them computes. Christopher chose diagonal rays after seeing a rendered sketch (it is a see-it decision). `buildStaticGimmickConstraints` emits nothing for a board carrying neither sonar, compass nor wormhole, which is why a plain tiling needs no solver edit at all.

**Tiling #2 is the 6.6.6 regular honeycomb (2026-07-22), and adding a tiling is now a DISPATCHER call rather than a fork.** Christopher chose hexagons over kagome / 3.12.12 / 4.6.12 after a rendered comparison of the candidates. The decisive constraint was LEGIBILITY, which is also the durable selection rule: a number plus a modifier watermark has to fit in EVERY cell, so the seven Archimedean tilings that contain triangles are all disfavored (a triangle is the hardest host there is, and 4.8.8's interstitial square already had to be tuned up via `OCT_CUT`). A honeycomb is one shape at one size with every cell large, and it is the other major lattice symmetry (6-fold against 4.8.8's 4-fold), so the two shipped tilings read as different worlds rather than variations. Its own adjacency surprise is that **a hexagon has no diagonals at all** — all six neighbors are edge neighbors, interior valence is a constant 6 (against 4.8.8's mixed 3/4/5/8), so the corner-touch ambiguity every rectangular assumption is built around simply does not exist.
- **One descriptor, two builders.** `buildTiling(type, M, N)` in tilingGeometry.js returns either `buildTiling488` or `buildHexTiling`, and both emit the SAME shape: `{adj, cellPos, cellVerts, verts, wUnits, hUnits, centerIndex, type}`. `generateTilingBoard` takes a `type` (default `'4.8.8'`) and opens on `centerIndex`; `applyWallsTiling` rebuilds the wireframe through the dispatcher from `board._tiling.type`. Those two were the only places hardcoding `buildTiling488`, and a third tiling now costs a builder plus a clip-path.
- **The renderer is extent-driven, not cell-count-driven.** `board._tiling` carries `wUnits`/`hUnits`, the tiling's extent in PITCH UNITS, because a honeycomb is WIDER than N (odd rows offset half a hex) and SHORTER than M (rows overlap vertically at 1.5R), so N×M pixels would be wrong in both axes. `_renderTilingBoard` picks a clip-path per `cellPos.shape` (octagon / diamond / hexagon), and the hex box is one pitch wide by `HEX_BOX_H` (2/√3) tall, centered on the cell center so the number lands dead center. Boxes of neighboring hexes OVERLAP while the clip-paths tile exactly, which is also what makes pointer hit-testing land on the right hexagon. `_renderTilingWalls` now anchors on `cellPos[0]`'s own center instead of assuming a P×P box centered at unit (0.5, 0.5) — a hex box is taller than it is wide, so the old anchor would have offset every hex wall vertically.
- **What actually needed hexagon-specific code, and what did not.** Sonar (depth-2 graph BFS), worm (walks the neighbor graph with positional momentum), mystery, liar, locked, mirror and walls needed ZERO change — they are topology- or position-generic already. Only the COMPASS did: a honeycomb has six straight lines of cell centers, not eight, so `COMPASS_DIRS_HEX` is the six hex axes and there is deliberately **no due-north/south ray** on a pointy-top lattice (no column of centers runs vertically). `computeCompassRay` gained a tolerance because hex row spacing is √3/2 and colinearity is therefore only exact to floating point; the nearest OFF-axis cell sits ~0.4 away in cross-product terms, orders of magnitude above float error, so it cannot misclassify — and display and certifier read the same STORED ray regardless, so any ray it returns is self-consistent.
- **The gate.** `test/tilingCertificationHex.test.mjs` runs the shipped, unmodified certifier over a frozen 7×7 honeycomb (49 cells, 9 mines) and it certifies at techniqueLevel 2 — Pass A, generic subset AND tank/gauss all running on hexagonal adjacency — while the RECTANGULAR control over the same mine layout is UNSOLVABLE, stalling on the first click. Holding the control to "unsolvable" rather than merely "different" is what keeps the gate non-vacuous; pick fixtures that way for future tilings.
- **The tiling layout re-runs on every pitch change (2026-07-22).** A tiling cell carries INLINE pixel left/top/width/height derived from its unit-pitch geometry, so unlike a rectangular cell (which reads `var(--cell-size)` through the CSS grid and reflows for free) it is frozen until something re-lays it. `layoutTilingCells()` is that pass, split out of `_renderTilingBoard` and called by `resizeCells`; re-laying rather than rebuilding is deliberate, since a rebuild would drop keyboard focus, restart the cascade animation, and detach the wall/worm overlays' reference cell. Before this, a resize or phone rotation recomputed the pitch and threw it away — the board stayed frozen at its old size and, once the viewport was narrow enough, was WIDER than its own container. Pinned by `tests/e2e/tilingResize.spec.mjs` (both tilings, rotation + shrink + grow-back), which was break-tested against the un-fixed renderer.
- **Keyboard focus on a tiling cell is an INSET wash, not an outline.** CSS applies `filter` first and `clip-path` second, so a `drop-shadow` ring around the silhouette is clipped away entirely, and an `outline` (or any box-edge shadow) survives only where the polygon meets its bounding box — two slivers that read as cell seams. The indicator therefore has to live INSIDE the clip: a huge-spread `inset` box-shadow washes the cell's whole painted area, so it takes the hexagon / octagon / diamond shape exactly, and because an inset shadow paints above the background but BELOW text, the number or flag the player is navigating by stays legible. The cell is also scaled up slightly, because the cells tile edge-to-edge with no gaps and identical colours — there is nothing for a mere ring to contrast against. Rectangular boards keep their original 2px outline untouched.
- **`computeLiarZone` follows the topology (2026-07-22).** The liar-zone tint walked `(row±1, col±1)` of the CONTAINER, which on a tiling is pure storage — so it tinted cells that were not the liar's neighbours and missed ones that were (visual only; the certifier reads `liarOffset`, never the zone). It now reads `buildNeighborCache` on an explicit topology. The rectangular walk is kept VERBATIM and is deliberately wall-BLIND — the zone is a spatial cue, not an adjacency claim, and the tint has always crossed walls — so routing it through the wall-aware cache would silently restyle every walled square board. Both halves pinned in `test/liarZoneTopology.test.mjs`.
- **Reachability is unchanged: still test-gated.** `?coastline=` gained an optional shape prefix — `?coastline=hex`, `?coastline=hex:sonar,walls` — with no prefix still meaning 4.8.8, so every existing test link works verbatim. The whole surface remains `isTestEnvironment()`-gated and UNREACHABLE in production.

**Sonar and compass region geometry is single-sourced in `adjacency.js`** (`sonarScanCells` / `compassRayCells`), consumed by BOTH `recomputeDisplayedMines` (what the player is shown) and `buildStaticGimmickConstraints` (what the certifier proves from). Those were two hand-copied loops until Coastline; drift between them is a silent no-guess hole, since the certifier would deduce from a premise the board never displayed and no test would notice. `test/adjacency.test.mjs` pins that the region the player SEES equals the region the certifier PROVES from, on a walled board, and the guard was break-tested against a one-cell drift.

**Sonar transfers to a tiling; it reads "within two steps" as graph distance** (a depth-2 breadth-first walk) when an explicit topology is present. That is the honest generalization rather than a convenience: on an UNWALLED rectangle the depth-2 closure of the 8-neighborhood is EXACTLY the 5×5 block, so the graph reading and the geometric one already agree wherever both are defined (pinned as its own test — if it ever fails, the generalization is the wrong one). Rectangular boards keep the literal 5×5 scan verbatim, walls severing only the inner ring. That inner-ring-only rule is NOT the same as graph distance once walls exist (the outer ring reaches through a wall the inner ring is blocked by) and looks more like an accident than a principle, but it is the rule players have been solving against and the help text promises "a 5×5 area", so changing it is a design call rather than a refactor's side effect. **No board has ever combined sonar with walls** (measured across all 144 canonicals, 2026-07-19), so the quirk has never actually manifested in production. Byte-identical square-board behavior was verified by recomputing the number layers of every one of those 144 canonicals and diffing against a `main` control: zero `displayedMines` differences on both sides.
**Pressure plates follow the topology (2026-07-19), and the plate's demand region is single-sourced.** `plateDisarmCells` in `adjacency.js` answers "which cells must be revealed before this plate disarms", and is read by BOTH the live `checkPlateDisarmed` (gameActions.js) and the target set of `estimatePlateMovesToDisarm` (boardSolver.js). Those were two copies of one rule; drift between them prices the countdown for a different job than the player is actually being asked to finish — a mis-timed board rather than a broken one, and silently so. The estimator's other two loops (Pass-A deduction, cascade) now read `buildNeighborCache`. **The wall asymmetry is DELIBERATE and pinned:** the demand region ignores walls, while deduction and cascade respect them. That is coherent rather than a bug — the plate states what must end up revealed, walls constrain the reasoning and the flood that get you there, and a severed cell is still reachable from its own side — but it is exactly the kind of thing a well-meaning refactor "fixes", which is why a test asserts the walled neighbor is still demanded. On an explicit topology the distinction dissolves, since a severed link is simply absent from the edge list. Plates are NOT in `DAILY_SAFE_GIMMICKS` (challenge/chaos only), so no canonical board carries one and there is no stored-board blast radius. Verified by a PLATE-PRICING differential (3840 estimates: 8 gimmick combinations × 20 seeds × 3 shapes × 4 partial reveal fractions, fingerprinting `{moves, steps, unsolved}` plus the derived `plateSeconds`) hashing identically to a `main` worktree. Reveal fractions matter — the Pass-A loop and cascade only fire on already-revealed cells, so a fully-fogged fingerprint would exercise almost nothing. Control-tested by making the target set wall-aware, which moves the hash and so also proves the asymmetry is a real distinction rather than a cosmetic one.

**Locked and mirror follow the topology (2026-07-19).** `isLockedCell`, `applyLocked`'s accessible-safe-neighbor check, and `applyMirrorPairs`' partner search each walked the 8-neighborhood by coordinate; all three now read `buildNeighborCache`. This was a TRUE no-op on rectangles rather than a judgment call like sonar's, because each already paired its coordinate walk with a `hasWallBetween` check — which is exactly what the cache computes — and the cache iterates `dr`/`dc` in the same order the hand-rolled loops did, so candidate and partner ORDER is preserved and the seeded shuffle consumes the RNG identically. `isLockedCell` gained an optional `neighborCache` param (pass one from a loop; both current callers are single-cell click checks). It must agree with the certifier's own unlock model (`canUnlock` in boardSolver.js, which has always read the cache): if the two disagree the solver certifies an unlock order the live game refuses. **`applyLocked`'s interior-only candidate rule (`r`/`c` never on the container edge) is skipped on an explicit topology** — the container's border is an arbitrary set of cells with respect to the graph, so it made ordinary tiling cells unplaceable, and on a degenerate N×1 container it would exclude every cell and silently place nothing. The accessible-safe-neighbor test is the constraint that actually matters and applies either way; rectangular boards keep the rule verbatim. Verified byte-identical on square boards by a GENERATION differential (`applyGimmicks` over 15 gimmick combinations × 24 seeds × 4 board shapes = 1440 boards, fingerprinting placement + walls + both number layers + the `applied` payload) hashing identically to a `main` worktree — and the differential was itself control-tested by perturbing candidate order, which moves the hash. A recompute-only check could not have caught this class, since placement runs at generation time.

**The par FEATURE VECTOR follows the topology too (2026-07-23).** `computeDailyFeatures` had the last two rectangular assumptions outside generation, and both produced a plausible number rather than an error. `wallEdgeCount` read `board._wallEdges`, but `applyWallsTiling` severs links out of `_cellNeighbors` and stores the removed pairs in a render-only `board._tilingWalls` — so **every walled tiling board reported ZERO walls** (measured: 9 and 10 severed edges reported as 0). It now floods `buildNeighborCache`. **The rectangular half was a real pre-existing bug too:** the old walk never consulted `_wallEdges`, so it merged zero-clusters that walls genuinely separate and disagreed with the cascade the player sees. Fixing both halves rather than branching was Christopher's call, taken against the measured blast radius — a differential over every canonical (148 daily + 13 weekly) moves par on **7 boards, all by +0.1s, largest +0.235%**, and all 7 carry walls. The two wall units are NOT identical and the model does not pretend otherwise: a rectangular wall edge blocks one orthogonal step plus up to two diagonals, a tiling wall edge blocks exactly one graph edge, and sharing `secPerWallEdge` across topologies is a modelling assumption the per-shape offset absorbs the average of. Pinned in `test/tilingFeatures.test.mjs`, break-tested against the un-fixed feature on both halves.

Also still rectangular but pre-existing and unrelated to topology: `redistributeMines`' mine-density ranking loop and the power-up effect radii. Measured max valence today: 4.8.8 = 8, hex = 6.

**What a tiling board still CANNOT do is produce a fit row, and the gap is the canonical serializer.** `serializeBoard`/`deserializeBoard` in `dailyBoardSync.js` carry `wallEdges` only — no `cellNeighbors`, no `_tiling` — so a tiling board round-tripped through `dailyBoard/{date}` comes back RECTANGULAR, the same class of bug Phase 1 found on the game save. The rest of the instrument is in place: features and par are computed on every `?coastline=` board (`state.coastlineFeatures` / `state.coastlinePar` — nothing submits them, a coastline run is `isLevelPractice`), the feature vector carries its own shape, and the `features` object in both the `dailyMeta` and `timed` rules blocks validates only `hasChildren(['rows','cols','totalMines'])` with **no nested `$other: false`**, so new feature keys need no rules deploy.

## Board Solver Architecture

Two-layer solver guarantees no 50/50 guesses:

1. **Board solver** (`boardSolver.js`): Simulates full game playthrough from first click. Wall-aware neighbor lists. Gimmick handling via `getPlayerVisibleCount`:
   - **Mystery / sonar / compass / wormhole:** return UNKNOWN (no direct per-cell constraint; sonar/compass/wormhole contribute separate gimmick-range constraints in Pass A/B/C — reveal-gated on `board._gatedCert` boards, see the No-Guess Contract section). Liar-stacked gimmick cells contribute NO range constraint (their displayed value includes the lie).
   - **Liar:** return UNKNOWN. Liar's displayed value is true count ±1 — a disjunctive constraint, not a single value. `buildLiarConstraints` emits `{allowedMines: [X-1, X+1]}` for Pass C tank solver.
   - **Mirror:** return `cell.adjacentMines` (the true count). The displayed value shows the partner's count for visual deception; a smart player who recognizes the pair can mentally un-swap. Using `displayedMines` would create false constraints that made post-gimmick boards spuriously unsolvable.
   - Returns `{ solvable, remainingUnknowns, totalClicks, techniqueLevel }` where `techniqueLevel` is 0 (Pass A), 1 (Pass B subset), 2 (Pass C tank/gauss), or 3 (required disjunctive liar reasoning).

2. **Constraint solver** (`constraintSolver.js`): Union-find partitions independent constraint groups. Constraints use `allowedMines: number[]` — single-element for exact, multi-element for disjunctive (liar) — plus an optional `origin` (the source cell index) for provenance. Tank solver (bitmask brute-force with disjunctive check) for <=20 unknowns; Gaussian elimination for larger groups (exact constraints only — disjunctive filtered out before gauss). Gauss is sound-or-skip (reworked 2026-06-10): float row-reduction with partial pivoting, then a row yields deductions ONLY if every coefficient and the RHS snap to integers within 1e-6, extracted via the binary-variable bound rule (rhs == min/max achievable). The old extraction `Math.round`ed coefficients before pattern-matching — 0/1 systems legitimately produce 0.5 entries under elimination, and on unsatisfiable systems (wrong player flag) it fabricated "provable mine" verdicts (`test/gaussSoundness.test.mjs` pins both the fabrication case and a witness-consistency sweep). Gauss remains INCOMPLETE by design — a missed deduction is honest, a false one never is. `solveConstraints` returns, besides the flat `mines`/`safe` sets: `groups` (per-component `{unknowns, hasDisjunctive, origins}`), `cellGroup` (cell → group index for every solved cell), and `contradiction` (a tank component with zero satisfying assignments — on live player state this means a provably wrong flag).

**Deduction substrate (2026-06-10)** — the engine-as-witness layer the receipt surfaces consume:
- **Trace**: `isBoardSolvable(..., { trace: true })` returns `result.trace = [{cell, tier, sources}]` — one entry per deduced reveal, where `sources` are the origin cells of the constraints that PROVED it (Pass A: the one constraint; Pass B: the subset pair; Pass C: the whole union-find component — the honest minimal explanation for enumeration). Collection-only: counters, ordering, and behavior are unchanged; generation hot loops don't pass the flag. Invariant: `trace.length + 1 === totalClicks`.
- **Per-group disjunctive attribution**: a Pass C deduction counts as `disjunctiveMoves` (and promotes techniqueLevel to 3) only if ITS union-find component carries a liar constraint. The old version batch-flagged every Pass C deduction of a round whenever any liar constraint existed anywhere, inflating `disjunctiveMoves` in dailyMeta on liar boards and over-promoting techniqueLevel. Consequence: on liar boards, `advancedLogicMoves` (the model's searchMoves) can be higher and `disjunctiveMoves` lower than under the old counting — the honest direction; historical dailyMeta rows written by old clients carry the old counting.
- **`findDeducibleFrontier(board, {respectFlags})`**: everything provable from the live state — full safe + mine frontier, each with `{tier, sources}`, plus `contradiction`. `respectFlags: false` runs flags-blind: player flags are CLAIMS, not facts, and one wrong flag can poison the constraint system into certifying a mine "provably safe" — every player-facing verdict must use the flags-blind run. `findNextSafeMove` is now a thin first-safe-cell wrapper over it.
- **`detectWrongFlags(board)`**: dual-solve diff — a player flag is provably wrong when the flags-blind run proves that cell safe; the flags-respecting run's `contradiction` additionally says "some flag is wrong" without localizing it.
- **Click timeline**: `state.clickTimeline = [{t, r, c, a}]` (a = r/f/u/c) records every player action via `recordPlayerAction` in gameState.js — reset per game, persisted with the auto-save, capped at 2000. The ground truth for player-grounded receipt claims (never narrate the solver's order as the player's).

- **Technique-floor verification** — each level demands a minimum `techniqueLevel` via `getRequiredTechnique(level)`: L1-30→0, L31-60→1, L61+→2. Boards below the floor are rejected. After 15 base-board attempts without success, the floor relaxes to 0 so we don't spin forever.
- Up to 25 gimmick re-rolls per base board before regenerating the (expensive) base board. Daily strips gimmicks if unsolvable. Chaos is exempt from solvability.

## Game Modes
- **Challenge (normal):** 120 levels, sawtooth difficulty, checkpoints every 5 levels, modifiers from L11+
- **Timed:** Race the clock, 4 difficulty tabs (Beginner/Intermediate/Expert/Extreme). Every timed board gets a par at generation (same PAR_MODEL as daily; gimmick terms zero on gimmick-free boards) shown as a par-relative delta on the win modal; wins submit {name, time, level, uid, par, features} to timed/{pushId} (features embedded per row - every timed board is unique, no meta bucket to join). Quick play has its OWN equation, PAR_MODEL_TIMED (between TIMED_PAR_MODEL markers in difficulty.js, refit-owned): timed rows exist only on WINS (losses never report), so the sample is win-censored and is never pooled with daily completions. The refit fits it as par-for-a-winning-run on the LOG scale (like the daily model, `scale:'log'`), on ratio-adjusted times (`log(time / k)`, dividing out the player's multiplicative handicap) with priors centered on the daily log posterior and a two-tailed outlier screen ([0.3x, 3x] predicted - the slow tail catches AFK rows); below TIMED_FIT_THRESHOLD=20 usable rows it ships as a verbatim copy of PAR_MODEL. predictPar selects the model on features.modeTimed (stamped by the timed path).
- **Daily:** One seeded puzzle per day, no levels. Modifiers are force-injected on improvement days when the target maps to a gimmick (sonar, wormhole, walls, mystery, liar, locked, mirror, compass, worm) — see Adaptive Experimental Design. Falls back to the natural ~35% lottery only when the target is a non-gimmick feature (move-type counts, structural features). Past dailies are replayable via the **Daily Archive** (a "Past dailies" link on the Daily card opens a month calendar) — see that section.
- **Weekly:** ONE single canonical puzzle for the whole ET week (Monday → Sunday), one attempt per day for 7 days. Best time across the 7 attempts wins. Same bomb-hit mechanic as daily (info-value penalty: `+infoValue + BOMB_PENALTY_BASE × (1 + BOMB_PENALTY_RAMP × (strikeNumber − 1))` — the base RAMPS gently per hit (`strikeNumber = priorHits + 1`, `BOMB_PENALTY_RAMP = 0.5` in `handleDailyBombHit`, so 1st +3s, 2nd +4.5s, 3rd +6s, 4th +7.5s …; first hit unchanged, each later one adds half a base — discourages casual mine-popping without clobbering a legit multi-hit day, since the >30% anti-cheat handles brute-force; softened 2026-06-16 from a steeper × n ramp), where info-value is the par-seconds of deduction the struck mine was anchoring, computed by `computeBombInfoValue` via a double solver run — see `src/logic/bombInfoValue.js`. NO re-fog: every other revealed cell stays revealed; the mine is preserved so adjacent numbers don't drop. The hit cell stays revealed with `cell.isStrike = true` so the strike sprite marks where the bomb was; strike cells count as flags for chording and persist across subsequent hits. A chord that exposes SEVERAL mines (two wrong flags around a satisfied number) charges EVERY one as its own strike in one batch — per-mine marginal info-value + ramped base, one shared popup (`handleDailyBombHit(row, col, extraMines)`; pinned in `test/chordPerMine.test.mjs`); challenge/timed keep the re-fog (`unrevealChordMines`) since one lifeline/loss handles the first mine there. Penalties live in the `bombHitEvents` log, not in wall-clock `elapsedTime`. Popup labels Minor/Key/Critical mines at info-value ≥ 2 / 6.5 / 13, quantile-anchored by `scripts/reanchor-bomb-tiers.mjs`. No game-over. **Anti-cheat:** a run that detonates more than `BOMB_HIT_CHEAT_FRACTION` (30%) of the board's mines is probing the layout, not playing — `isBombHitCheat` (difficulty.js) flags it and the submit gates in `submitOnlineScore` / `submitWeeklyScore` / `submitArchiveScore` reject it (returns `'cheat'` / `false`, never queued for retry), so it never reaches the leaderboard, the `dailyHistory` chart, OR the par fit. The player still finishes — streak / completion are unaffected.) Board size 8–14 × 8–14, 2–4 modifiers stacked, daily-density. Architecture mirrors daily's canonical-board: `weeklyBoard/{weekStart}` is write-once on Firebase, pre-generated by `precompute-weekly-board.yml` Monday 00:00 UTC (`scripts/precompute-weekly-board.mjs`). Cloud-synced one-attempt-per-day cap at `users/{uid}/weeklyAttempts/{weekStart}/dayAttempts/{N}` so clearing localStorage can't grant a second try. Leaderboard is one row per player per week at `weekly/{weekStart}/{uid}` (set, not push) carrying `bestTime` and a `dayTimes` map. Submission helpers: `submitWeeklyScore`/`fetchWeeklyLeaderboard` (firebaseLeaderboard.js), `markWeeklyDayAttempted`/`loadWeeklyAttempts` (firebaseProgress.js). Seed selection in `selectWeeklyRngSeed.js` scores 10 candidates by `activeGimmicks.length + advancedLogicMoves * 0.01`. Gimmick pool: `getWeeklyGimmicks` picks 2–4 distinct from the daily-safe subset, no `singleOnly`. **First-attempt-of-the-week qualifies for par-model fit data**: when `Object.keys(state.weeklyDayTimes).length === 0` at win time, winLossHandler additionally calls `submitOnlineScore('{weekStart}_weekly_first', ...)` so the score lands in `daily/{weekStart}_weekly_first` and features in `dailyMeta/{weekStart}_weekly_first`. Days 2–7 attempts are speedruns of a known board and stay out of the fit. Weekly does NOT touch streak / handicap / `dailyHistory`. The Stats modal has a Weekly tab with a 7-day line chart.
- **Chaos:** Rapid rounds with random modifiers, exempt from solvability guarantee

## Privacy / sensor-permission posture

By design, GregSweeper requests ZERO sensor permissions and reads NO clipboard / camera / microphone / location data. Audited 2026-05-10:

- No `navigator.geolocation` calls anywhere.
- No `getUserMedia` (camera / microphone) calls.
- `navigator.clipboard.writeText` is used in `main.js` (Settings copy-link) and `diagnosticsModal.js` (copy diagnostic state). Write-only — modern browsers grant this without a permission prompt for user-initiated actions. No `clipboard.read*`.
- No `navigator.permissions.query()` calls.
- Notifications and persistent-storage are the only Web APIs that prompt the user, and both are gated by explicit opt-in actions (Settings toggle, install heuristic).

When adding a new feature, treat this list as a constraint: if it requires a sensor permission, surface that decision explicitly rather than silently expanding the permission surface.

## Molt Day (daily-streak insurance)
Every 5 consecutive daily completions banks one **molt day** (player-facing name; glyph 🦀), capped at 2. A banked molt day is spent automatically and lazily at the next completion to cover a missed ET day, so the streak survives a day off. When the gap exceeds the bank the streak resets to 1 and the bank is RETAINED (all-or-nothing: a molt day is spent only when it actually saves the streak). Covered days add nothing to the count and never help earn. Weekly never touches streak; archive plays (`state.isArchivePlay`) and practice dailies (`?seed=`, `state.isDailyPractice` — the `isPractice` guard in `saveGameResult`) never earn, spend, or touch it. Archive `dailyHistory` rows carry `archive: true` and are filtered out of the streak derivation by `streakBearingDates` (archiveEligibility.js) before `reconcileStreakFromHistory` runs, so a replayed gap day can't retroactively splice the streak. The metaphor is Greg the crab sheltering while it molts.
- **One pure module** `src/logic/moltDay.js` is the single source of truth (no imports): `applyStreakContinuation` (the commit math), `projectContinuation` (read-only "what would completing today do"), `isStreakAlive` (read-side lapse check — a covered gap is still alive), `coversTonight` (the push gate). Constants `MOLT_EARN_EVERY = 5`, `MOLT_CAP = 2`. Consumed by THREE surfaces so they can never disagree: the completion path (`statsStorage.saveGameResult`), the title-card notice (`getMoltProvisionalNotice` → `main.js`), and the push script (`send-push.mjs` imports `coversTonight`).
- **Storage** (`statsStorage.js`): `modeStats.daily.moltBanked` + `moltLastUse = { date, covered, streakKept }` (defaults 0/null, backfilled like other added fields). `getDailyStreak()` now returns `{ streak, best, banked }` and is bank-aware (a covered gap reports the live streak, not 0). `saveGameResult` records a transient `_lastMoltEvent` drained once by `consumeMoltEvent()` (NOT persisted, so a stale "earned" can't resurface). `applyCloudProgress` rides the molt fields in the SAME date-anchored snapshot as `(dailyStreak, lastDailyDate)` so the bank never pairs with the other side's streak (pinned by `test/moltDayCloudMerge.test.mjs`). **Legacy-preserve rule (fixed 2026-06-16):** a missing cloud `moltDay` node, OR the bare default `{banked:0, no lastUse}`, is the pre-molt shape every existing account carries — absence of information, NOT an authoritative 0. `adoptMolt` only overwrites the local bank when the cloud carries REAL molt state (`banked > 0` or a recorded `lastUse`); otherwise it preserves local. Without this, the overwrite listener (`applyCloudProgress(cloud, {overwrite:true})` on every snapshot) zeroed the freshly-granted backfill on every boot, so an existing-streak player never kept their molt days (Christopher, 92-day streak, saw 0 crabs). A genuine cross-device spend (`{banked:0}` WITH a `lastUse`) is still adopted, so a spend can't resurrect.
- **Cloud**: `saveProgress` writes `users/{uid}/moltDay = { banked, lastUse }`. The rule block IS whitelisted in `firebase-rules.json` — the `users/{uid}` node ends with `$other: false`, so an un-whitelisted child would make the WHOLE progress `update()` fail validation and drop silently (the 866683d class of bug); pinned by `test/moltDayRules.test.mjs`.
- **One-time launch backfill** (`backfillMoltDays` in statsStorage, `backfillGrant` pure in moltDay.js): an existing streak earns the molt days it would have banked (>4 → 1, >9 → 2). Self-guarding (skips once any bank or `moltLastUse` exists), so it runs safely every boot, never re-grants, and never undoes a spend cross-device; local-only (the next completion syncs it, and a 2nd device converges from the shared streak). Called at boot after `_reconcileDailyStreak`.
- **Daily-card indicators** (`updateTitleProgress`): the card frames Greg's note with four corners — 🦀 tokens top-left, the Past chip top-right, streak ("N days") bottom-left, par ("Par Ns") bottom-right. The streak + par are PLAIN corner text in the note's muted color (NOT pills, NOT italic), so the Past chip stays the one pill that pops; they hug the corners absolutely like Past (a reserved `padding-bottom` on the daily card keeps them clear of the note across breakpoints). Greg's note keeps the THEME-matched Greg sprite (`themeSpriteImgHTML` resolves the active world's Greg via `getThemeEmoji('smiley')`, not the forced-canonical `spriteImgHTML`). A provisional "Molt day holds your N day streak" replaces the note before play when a cover is holding the streak; completed shows "Played today" + the dimmed `.daily-completed` card. No in-game LCD change.
- **Earned celebration**: earning a molt day flags `flagMoltCelebrate` (statsStorage); `showTitleScreen` drains it once (`consumeMoltCelebrate`) to show the `#molt-earned-modal` popup, and on dismiss the crab drops into the card's top-left corner (`moltPlace` keyframe, `_animateMoltPlacement`). The covered/used event still shows its quiet inline `.molt-note` in the win modal.
- **Tests**: `test/moltDay.test.mjs` (bank-math table + `backfillGrant`), `test/moltDayCloudMerge.test.mjs` (snapshot atomicity + the legacy-preserve rule + an end-to-end legacy-streak backfill-then-listener boot), `test/moltDayRules.test.mjs` (rule block), `test/sendPushMolt.test.mjs` (the three push branches).

## Greg-par Model (Daily)
Daily par is a **log-linear (multiplicative) regression** over board features (`PAR_MODEL` carries `scale: 'log'`): `par = exp(intercept + Σ coef·feature)`, the lognormal MEDIAN — so par is always positive (no more negative-intercept-on-tiny-boards bug) and each coefficient is a **log-multiplier**, NOT seconds. Fit in R offline against real completion data. Coefficients live in `PAR_MODEL` in `src/logic/difficulty.js`; `predictPar` branches on `model.scale` (absent ⇒ the legacy additive-seconds form). The whole model lives in `src/logic/dailyFeatures.js` (`computeDailyFeatures`, `predictPar`, `breakdownPar`, `applyParModel`). (Migrated from additive seconds → log 2026-07-02, v1.6.127; the player handicap became a multiplicative ratio in the same change — see Handicaps.)
- **Move type, not move count, is the primary signal.** The solver in `boardSolver.js` classifies every deduction into one of five buckets at the three `totalClicks++` sites: `passAMoves` (trivial propagation), `canonicalSubsetMoves` (Pass B subset with larger-constraint size ≤3 — 1-1 / 1-2 / 1-1-1 shapes), `genericSubsetMoves` (Pass B, size ≥4), `advancedLogicMoves` (Pass C tank/gauss), `disjunctiveMoves` (Pass C with liar). Invariant: `passA + canonical + generic + advanced + disjunctive + 1 === totalClicks` for solvable boards. The solver still classifies all five, but the **model pools them for identifiability** (2026-06-08 rework): a VIF/sparsity audit showed the four raw move-types are too sparse / small-count to fit separately, so `predictPar` uses two earned tiers — **pattern** (`canonicalSubsetMoves + genericSubsetMoves`, subset deductions) and **search** (`advancedLogicMoves`, tank/gauss enumeration). `passAMoves` is dropped as a model predictor (it's a board-size proxy, VIF 7.4, absorbed into `cellCount`); `disjunctiveMoves` stays unmodeled (dropped 2026-05-04, confounded with `liarCellCount`). The solver keeps counting all five for diagnostics.
- **Stored feature vector (`dailyMeta`):** raw move-type counts + board shape (rows, cols, cellCount, totalMines, wallEdgeCount, etc.) + gimmick cell counts — UNCHANGED by the rework, so every historical board stays usable with no migration. The **model predictors are DERIVED from these** at predict/fit time: `cellCount` (lone size axis), `totalMines` (raw — VIF 3.6, fine once the redundant size features are dropped; density was tried 2026-06-08 but made the coefficient unreadable), `patternMoves`, `searchMoves`, `wallEdgeCount`, `zeroClusterCount`, and the modifier cell counts (kept split — sparse, prior-anchored until coverage missions build data). `nonZeroSafeCellCount` is dropped (near-redundant, VIF 23.7). One source of truth: `COEF_TERMS` in `dailyFeatures.js`, where each term is a function of the raw features (so the R refit derives the same from stored `dailyMeta`).
- **End-of-game modal** renders a per-term breakdown below par: `+18s search moves · +12s pattern moves · …`. Under the log model `breakdownPar` allocates the above-baseline seconds by each term's share of the log-difficulty (`coef·x / Σ coef·x`), so the chips still read in seconds and sum to par. Baseline terms (`exp(intercept + size)`) merge into a single chip to keep the line readable.
- **R refit workflow:** export Firebase JSON from the console → run `scripts/fit-par-model.qmd` → paste the emitted `PAR_MODEL = { ... }` block into `difficulty.js` → commit + deploy. The .qmd also runs diagnostics (residual plots, QQ for log-linear check, VIF for collinearity, bootstrap CIs).
- **Pre-ship scale anchor:** `scripts/calibrate-today.mjs` regenerates today's daily board locally and verifies `predictPar` lands inside the observed completion-time range before shipping new coefficients. One-board check, not a fit.
- **Board shape is an OFFSET on the shipped model, not a parallel equation (Project Coastline, 2026-07-23).** A tiling board is priced by `PAR_MODEL` plus one 0/1 term per non-rectangular tiling — `secPerShape488` / `secPerShapeHex`, with rectangles the omitted reference. Christopher's ruling; the alternative considered and rejected was a `PAR_MODEL_TILING` marker block on the `PAR_MODEL_TIMED` pattern. **Why an offset.** The reasoning tiers already transfer in MEANING (a search move is a search move on any lattice), so where a shape does less reasoning the feature vector says so on its own and the term contributes `coef × 0`. Measured over 1200 unfiltered first-shot layouts: a **honeycomb certifies at techniqueLevel 0 on 95-99% of boards and produced ZERO tier-2 boards at any density**, while **4.8.8 spans the full range much as a rectangle does** (33/40/27 across tiers 0/1/2 at density 0.20). So a separate hex model would be fitting two CONSTANT-ZERO columns and would ship its priors back looking like a fit; and because the two tilings differ from each other about as much as either differs from a square, "one tiling model" was never one population. The structural substrate: Pass B needs one clue's unknown set inside another's, and adjacent-pair neighbor overlap caps at **2 on both tilings against 4 on a rectangle** (mean shared 2.86 rect / 1.91 4.8.8 / 1.88 hex); what separates the two tilings is constraint-size heterogeneity (mean adjacent valence gap **2.34** on 4.8.8 vs 0.80 rect / 0.54 hex). What the offset buys is the one thing no feature expresses — the parse cost of an unfamiliar lattice, which in a log model is exactly an intercept shift — and it doubles as the honest TEST of the null that the par model is geometry-blind the way `isBoardSolvable` turned out to be. A third tiling is ONE more `COEF_TERMS` line plus one R column, which is the other half of why this beat marker blocks. **Gated per shape, never pooled:** R adds `shape488`/`shapeHex` to the fixed effects only once THAT shape has rows (`add_shape488_term` / `add_shapeHex_term`, the same zero-variance guard as `archivePlay` / `wormLoad`), and the shipped coefficient additionally sits behind the `NEW_FEATURE_DATA_THRESHOLD` zero-guard — so both ship at `0.00000` today and par is byte-identical on every rectangular board. **Assumption to revisit:** `build_priors` bounds every fixed effect at `lb = 0`, so this asserts a NON-NEGATIVE offset ("a tiling never takes LESS time than a rectangle with the same measured work") — the a-priori direction for an unfamiliarity tax, but if a shape's coefficient piles up at zero once real boards land, the bound is the thing to change. Same caveat `archivePlay` carries.
- **`tilingType` is DERIVED from the board and ABSENT on rectangles.** `computeDailyFeatures` reads `board._tiling.type`; it is not stamped by the caller the way `features.modeTimed` is, because a daily board's features are recomputed independently by every client, by `daily-board-pipeline.mjs`, and by the nightly `verify-canonical-boards.mjs` — a caller-stamped shape could differ between them and a derived one cannot. It must stay ABSENT (never `'rect'`, never `0`) on a rectangular board: the verify sweep's vintage escape hatch is `stored === undefined && recomputed === 0`, so a new key recomputing to a truthy value would hard-fail every historical date. `COEF_TERMS` derives the 0/1 indicators from it, so they never reach `dailyMeta` at all. Pinned in `test/tilingFeatures.test.mjs` + `test/tilingParModelContract.test.mjs` (which also counts the R `sprintf` slots against its args — a coefficient added to `difficulty.js` but not to the R template survives only until the next 14:00 UTC refit, and a dropped arg silently SHIFTS every later coefficient).

## Leaderboard Modal (scope x view)

The leaderboard modal (600px, `leaderboard-modal-content`) is a Daily/Weekly SCOPE pill-toggle crossed with three VIEW tabs (`data-lb-view`): **Scores** (the classic table, top-3 rank coloring, an "N played" count in the date line), **Adjusted** (the DEFAULT view, both scopes — `time / k` where `k` is the player's multiplicative handicap ratio from the SHIPPED handicaps.json, via `rankAdjusted` in `src/logic/leaderboardViews.js`; ranks by fractional performance vs one's own par. ## Daily History Chart
- `src/ui/dailyHistoryChart.js` — pure-SVG timeline of the signed-in user's past 30 days of deltas from par (lives on the Stats modal's Daily tab; a play-day column can hold several dots — a live daily plus archive replays). The stats tab's percentile-trend chart is toggleable Adjusted/Raw (Adjusted default: each player's best time / their shipped `k` via `rankAdjusted`). No external library. Dots coloured green (under par) / grey (even) / red (over).
- Data source: `users/{uid}/dailyHistory/{date} = { time, submittedAt, archive? }` in Firebase — ONLY the raw time is stored. Timeline placement is by the day the run was PLAYED (`attributePlayedDate` in archiveEligibility.js, surfaced as `playedDate` by `fetchUserDailyHistory`): live rows belong to their board date (even when the write flushed late), archive replays to their submittedAt ET day — so a replay never back-dates a dot or pollutes the career/rolling averages, while par/features still join on the BOARD date (`boardDate` in statsRenderer). When a live play and a replay share a day, the live play owns the chart dot. Par and delta are computed at render time against the current `PAR_MODEL` (via `predictPar` on `dailyMeta/{date}` features) combined with the user's current ratio handicap. This keeps older entries automatically in sync with the latest model after each refit — no server-side rewrites needed.
- The delta plotted is against the user's PERSONAL par (`global par × k + bombSeconds`), so a dot below zero means "better than your typical" regardless of how fast you are in absolute terms.

## Handicaps (user-specific par offsets)
- Each user has a handicap as a **MULTIPLICATIVE RATIO `k`** — their typical `time / par` vs Greg's CLEAN par across recent dailies. `k > 1` = typically slower than Greg, `k < 1` = faster/better. `personalPar = par × k + bombSeconds`: clean skill scales with the board (the ratio), the player's typical bomb cost is a SEPARATE additive-seconds term. The RATING shown to players is `(1−k)×refPar` seconds and `(1−k)×100`% — **positive = faster/better than Greg** (opposite sign from the Lab File "your pace" line, which is a par composition `gregPar×(k−1)` that must sum to personal par).
- Stored in `src/logic/handicaps.json`, a static JSON asset committed to the repo. Keyed by Firebase anonymous uid. Not in Firebase — shipping via static file avoids write-permission issues and lets handicaps update the same way everything else does (commit → GitHub Pages redeploy).
- Computed server-side (GitHub-Actions-side) by `scripts/refit-par-model.R` running daily: fits `brm(log(pure_time) ~ features + (1|uid))` where `pure_time` has ALL bomb cost removed BEFORE logging (so there is no bomb regressor). The ratio is `k = exp(recentered random intercept)` (geometric-mean recentering → play-weighted geometric mean of `k` is 1), clamped to a WIDE `[0.1, 10]` sanity bound — partial pooling is the real regularizer; the clamp only rejects garbage, never a well-sampled player. Each player's mean per-play bomb cost is a SEPARATE `bombSeconds`. Falls back to a residuals path (geometric-mean ratio + bombSeconds) when N or n_players is below the fit threshold.
- **`handicaps.json` is `format: "logratio-v1"`**: `handicaps {uid: k}`, `handicapDetails {uid: {k, bombSeconds}}`, top-level `refPar` (median day-of par, for the seconds display), `secPerBombHit`. Static JSON committed to the repo (ships via GitHub Pages redeploy).
- Client reads via `src/logic/handicaps.js`: `loadHandicaps()` fetches once; `getHandicapRatio(uid)` returns `k` (default 1 = neutral/unrated); `ratioDisplaySeconds`/`ratioDisplayPercent` + `getHandicapSeconds`/`getHandicapPercent` give the RATING display; `personalPar(par, uid) = par × k + bombSeconds`; `getHandicapsMeta()` returns `{updatedAt, modelFitN, nPlayers, method, format, refPar, secPerBombHit}`. A dual-reader treats a legacy additive file (no `format` tag) as unrated (`k=1`) so additive seconds are never misread as ratios. Used in the end-of-game modal ("Your par" vs "Greg's Time"), the Adjusted leaderboard, and diagnostics.

## Refit Workflow (.github/workflows/refit-par-model.yml)
- Runs daily at 10am America/New_York (14:00 UTC; 9am ET in winter since Actions cron doesn't observe DST).
- Pulls `daily/*` and `dailyMeta/*` from Firebase (both world-readable — no secrets required), fits the Bayesian mixed-effects model via `brms` + Stan, patches `src/logic/difficulty.js` between `PAR_MODEL:START` / `PAR_MODEL:END` markers, and rewrites `src/logic/handicaps.json`. Commits both files under "Christopher Wells" identity and pushes to main, then explicitly dispatches the Pages deploy — GITHUB_TOKEN pushes never fire push-triggered workflows (GitHub's recursion guard), so without the dispatch each refit sat on main undeployed until the next human push (found and fixed 2026-06-10). Also pulls `dailyBoard/*` (world-readable) for the clue-digit derivation below.
- Guards: `MIN_SCORES_TO_FIT = 30` (total scores required, priors do the regularisation so the old `MAX_COEF_DRIFT` clamp was retired), `MIN_PLAYS_FOR_FIT_INCLUSION = 5` (per-user TOTAL-play threshold — only users at/above this contribute to the global PAR_MODEL and receive a handicap entry in handicaps.json; below-threshold users get a provisional handicap computed client-side via `estimateHandicapFromHistory`. Set low because partial pooling shrinks a small-N user's random intercept toward zero and the heavy players anchor the fixed effects, so a light player can't drag the coefficients — the threshold only excludes true one-offs. Bomb-hit plays count toward the threshold now that they're included in the fit via the `bombHits` regressor), `ADAPT_DELTA = 0.99` with `MAX_DIVERGENT_FRAC = 0.25%` — a fit that comes back with Rhat > 1.05, ESS < 400, or more than 0.25% divergent transitions is rejected and the previous `PAR_MODEL` stays.
- Priors: the coefficients are now LOG-multipliers, so the prior CENTERS are OLS-seeded per refit from `lm(log(pure_time) ~ features)` (`compute_log_ols_seeds`) — each a `lognormal(log(seed), sigma)` with the wide `PRIOR_SIGMAS` (sigma = 1.0). Variance priors are on the LOG scale (`normal(0,1)` residual, `student_t(3,0,1)` between-user), NOT the old seconds-scale values (which would be absurd on a log response). The seconds-scale `PRIOR_MEANS` at the top of the script are retained as documentation only. (OLS-seeding is dynamic per run; freeze a hardcoded log-scale `PRIOR_MEANS` if a stable non-ratcheting anchor is wanted.)
- After the fit: random intercepts are play-weighted-recentered in LOG space (geometric-mean centering — brms can park the baseline in either the global intercept or the random intercepts; without recentering the handicaps come out shifted by a common constant), then `k = exp(recentered ranef)`, clamped to `[0.1, 10]`. Each player's mean per-play bomb cost rides SEPARATELY as `bombSeconds` (never folded into `k`). The log-intercept is MEDIAN bias-corrected over day-of rows so `mean(log pure-play time) = mean(predicted log-par)` — par = `exp(Xβ)` is the time Greg beats half his runs (bombs live in the handicap, never in par).
- First CI run after a `brms` package cache miss takes ~5 min (Stan + dependencies compile). Subsequent runs hit the cache and finish in ~2–3 min including Stan model compilation.
- **Bomb-hit plays are kept in the fit; ALL bomb cost is subtracted out of `pure_time` BEFORE logging** (new-mechanic base surcharge `bombBaseSum` + legacy at a fixed `LEGACY_BOMB_RATE`/hit ≈ 15s, shipped as `secPerBombHit`), so there is NO bomb regressor under the log model. Each player's per-play bomb cost then rides as the separate additive `bombSeconds` in their handicap. The per-player bomb cost that par excludes is then folded back into THAT player's handicap (see Handicaps) — so bombs are a personal handicap component, never board difficulty. Kept-not-filtered replaced an earlier filter-out that dropped ~60% of plays with asymmetric bias (Chris's bomb-hit rate is higher than Kate's). Clients submit per-hit `bombHitEvents: [{ t, row, col, penalty, infoValue }, ...]`. **Brute-force exception:** a run that detonated > `BOMB_HIT_CHEAT_FRACTION` (30%) of the board's mines IS dropped from the fit (the `df` filter mirrors the client `isBombHitCheat` gate) — a probe's time (tiny wall-clock + every mine's info-value) is a garbage data point no matter how it's priced. Historical >30% rows (e.g. the 100%-mine brute-force on 2026-06-15) are excluded the same way without being deleted from the leaderboard.
- New features added to the fit follow a threshold guard: until ≥20 plays have nonzero values for a given new feature, its coefficient is forced to 0 in the SHIPPED `PAR_MODEL` even if brms has fit a posterior. This avoids the lognormal-prior median (~prior_mean × 1.65) being shipped as a real coefficient, which would inflate `predictPar` with no data justification. The fit still treats it as a regressor so other coefficients aren't polluted by missing-data variance.
- **Clue-digit studies (2026-07-17, PR D — absorbed from Christopher's `cwells/par-digit-feature` experiment, commit 51d451f).** The arithmetic-load question: beyond board size and the reasoning tiers, does clue MAGNITUDE (more 2s vs 3s) cost time? `clue_histogram`/`digit_shares_from_boards` derive the per-board TRUE-adjacency histogram FROM THE CANONICAL BOARDS at fit time (full historical coverage from day one — every `dailyBoard` back to `DIGIT_ERA_START = 2026-04-27` carries the data, no client instrument needed; before that date the stored board was regenerated by the backfill and does NOT match its `dailyMeta`/played time, so it is the provenance floor). The four features are `clueShare2/3/4/5plus`. **They are measured in a SEPARATE canonical-era SECONDARY brms fit** (`digit_df`, reusing the same lognormal + lb=0 + OLS-seed `build_priors`/`compute_log_ols_seeds` machinery, so a digit study reads on the same positive log-multiplier scale as every other study), whose posteriors merge into `target_candidates` — so a digit share can become the experiment target (a journal study) and appear in the parameter table, WITHOUT ever entering `PAR_MODEL`. The secondary fit is fully failure-tolerant (any error / bad diagnostics drops the digit candidates for the night and leaves the primary pipeline untouched) and gated on ≥`MIN_SCORES_TO_FIT` canonical-era rows with variance. **Note (flagged for review): on the current log-scale data (211 canonical-era rows) the digit effect is NOT the null Christopher's June seconds-scale read found (LRT p = 0.52, 155 rows) — clueShare3 lands ~+30% per unit, tight (CV 0.18); digit VIFs 1.5-3.9.** Promote to a shipped par term only once the density confound is resolved on more players (the same instrument-first discipline as the per-technique predictors above).
- **Revalidation targeting (2026-07-17, PR D — approved 2026-07-12).** Every `REVALIDATION_INTERVAL = 14` days the primary target becomes the STALEST SETTLED feature (bottom half of the CV ordering, longest since last targeted) instead of the top-CV feature, so a closed finding gets deliberately re-checked. The cadence is anchored to `lastRevalidationDate` in `experimentTarget.json` (robust to missed refits, unlike a modulo on refit count); a MISSING anchor makes the first post-deploy run due, so the mechanism is visible immediately. "Settled" mirrors the journal's RESTING contract (bottom-half CV); the `recentTargets` (last 3) exclusion still holds; a revalidation only fires when a qualifying settled feature exists (else it falls through to the normal CV pick and leaves the clock for the next run). On a revalidation day the `reason` field is stamped EXACTLY `"revalidation"` (the journal fires its revisit story on `meta.reason === 'revalidation'`); normal days keep the descriptive CV sentence.
- `scripts/refit-par-model.R` is the full pipeline; `scripts/fit-par-model.qmd` is the exploratory Quarto notebook (diagnostic plots, VIF, bootstrap CIs) for interactive review.

## Canonical Daily Board (cross-client board agreement)
Every player on the same ET date plays the same board, period. Three divergence sources are eliminated:

1. **Code-version drift** between clients on different cached SW bundles. Same seed + different code = different board. Closed by storing the resolved board on Firebase, not the seed.
2. **Experiment-target drift** between clients with different cached `experimentTarget.json`. Same code + different target = different `selectDailyRngSeed` winner = different board. Same fix.
3. **Firebase cold-load race** where `loadDailyBoard` returns null because the Firebase SDK hasn't initialized yet, and the client silently falls through to local generation against a stale `experimentTarget.json` — different `:trialN` winner from whatever wrote the canonical, so same date but divergent board. Closed by `runStartupGate` in `main.js`, which renders nothing user-interactive until the SW is current, Firebase is ready, and today's canonical is in memory. Without this gate, a player who lost the cold-load race would silently play a divergent board (this happened to Kate on 2026-05-06 v1.5.30 — the trigger for the gate).

Mechanism:
- **`dailyBoard/{date}`** in Firebase Realtime DB stores the fully-resolved board (mine layout, gimmick assignments, displayed numbers, wall edges) — write-once at the rules layer.
- **`getLocalDateString()`** is anchored to America/New_York via `Intl.DateTimeFormat('en-CA', { timeZone: 'America/New_York' })`. A player in Tokyo loading at 9am JST sees the puzzle for the previous ET date if it's still before midnight ET.
- **`src/firebase/dailyBoardSync.js`** — `loadDailyBoard(date)` / `saveDailyBoard(date, payload)` / `serializeBoard({ board, rows, cols, ... })` / `deserializeBoard(raw)`. Both load and save now go through `waitForFirebaseReady` (50ms-poll up to 8s) so a cold-load race can't make them silently no-op. The serialiser drops `false`-valued booleans to keep the JSON tight (~30% smaller), and the deserialiser fills them back in from defaults so the consuming code sees a fully-shaped cell object.
- **Startup gate (`runStartupGate` in `main.js`)** — runs before `init`'s routing branch, behind the `#boot-overlay` div in `index.html`. Three steps: (1) `ensureLatestServiceWorker` — `registration.update()` and wait up to 3s for any new SW to activate (controllerchange handler in `<head>` reloads us if it does), (2) wait up to 8s for `firebase.apps.length > 0` and stash the result in `state.firebaseReady`, (3) pre-fetch `loadDailyBoard(today)` into `state.canonicalDailyBoard = { date, raw }`. Practice loads (`?seed=`) skip step 3. Boot overlay only hides at the END of `init` (after routing + first newGame await), so the player never sees a flash of a wrong board.
- **Daily entry path** (`gameActions.js` daily branch — `async`): read `state.canonicalDailyBoard` first; if it exists and matches `state.dailySeed`, deserialize verbatim (skip generation, gimmicks, solvability retry). Fall back to a fresh `loadDailyBoard` call only when the cached canonical is for a different date (tab open across midnight) or when the gate's fetch failed. If both miss, run the full local-generation flow and `saveDailyBoard` the result fire-and-forget so the next visitor sees what we generated. The solver still runs locally on the resolved board to compute features (move-type counts) and the best-start cell — that's deterministic, so different clients agree on features even if they came in via different paths.
- **Completion ↔ cloud reconciliation** in `runStartupGate` (one `daily/{today}` read, both directions; row matching via the pure `src/logic/scoreRowMatch.js`, node-tested): (a) local "completed" flag set + the account's cloud row POSITIVELY divergent (truthy `rngSeed` ≠ canonical) → clear `minesweeper_daily_completed_date` plus the cached par/moves keys, unblocking the canonical replay (a missing row trusts the local flag — clearing on missing-score used to let raced uid lookups unlock replays); (b) local flag unset + a cloud row matching the canonical's effective seed → ADOPT the completion (markDailyCompleted + drop any in-progress daily save), so finishing the daily on one device marks it completed on every device sharing that account. The `?mode=daily` deep link gates on `isDailyCompleted` like the Daily card (a notification tap can't relaunch a completed daily). Skipped on the test env and for `?seed=` practice.
- **Submission dedupe** in `_doSubmitOnlineScore`: before pushing, read the date's rows and skip the push (returning `'duplicate'` — a third outcome alongside `true`/`false`) when this uid already has a row for the SAME effective board seed. Matching is per BOARD, not per uid: rows omit `rngSeed` when it equals the dateString, so the effective seed is reconstructed (`effectiveRowSeed`), practice rows can never block the real daily, and a divergent historical row doesn't block a canonical replay. First completion wins: callers toast "Already on the board from another device" and skip the `dailyHistory` write on `'duplicate'`; the offline retry queue treats `'duplicate'` as resolved (covers the offline-race where another device submits before the queue flushes). Both submit paths (auto in winLossHandler, manual in main.js) anchor the score's date to `state.dailySeed` (the board's date), so a finish at 12:00:01 AM lands on the board's own leaderboard.
- **Resume eligibility** (`src/logic/resumeEligibility.js`, pure + node-tested; consumed by `tryResumeGame` in `src/game/gamePersistence.js`): a persisted save resumes only if (a) its `gameMode` matches the slot it was loaded from, (b) a daily save carries BOTH `dailySeed` and `dailyRngSeed` and the seed equals today's ET date (practice `?seed=` equals its custom seed instead), (c) the save's `dailyRngSeed` matches the canonical board's when one is cached for that date (divergent-canonical drop), (d) a weekly save carries full identity (`weeklySeed`/`weeklyDay`/`weeklyRngSeed`) matching the live ET clock, (e) cells have `row`/`col` (v1.5.19 corruption check), and (f) any explicit `cellNeighbors` topology on the save still validates (right length, in range, symmetric — a corrupt one would restore a board whose adjacency disagrees with the one it was certified under). Date anchors compare against the CLOCK (`getLocalDateString`/`getWeekStart`/`getWeekDayIndex`), never against live state fields — a session that survives midnight ET carries yesterday's seeds in state. Saves missing their seed identity are REJECTED, not waved through: the pre-fix Daily card handler nulled live seeds before `switchMode` persisted the outgoing game, and those fingerprint-less snapshots resumed yesterday's board as "today's" daily (found 2026-06-12).
- **Date-rollover discipline (2026-06-12):** daily/weekly identity is derived inside `newGame` from the ET clock (practice keeps its caller-set seed via `isDailyPractice`); the mode-card handlers no longer pre-set identity fields before `switchMode` (mutating identity before the outgoing game is persisted forges or strips the snapshot's fingerprint — the root cause above). A live session that sleeps through midnight (background tab, suspended PWA) is caught by `expireRolledOverGame` in `main.js` on `visibilitychange → visible`: `isLiveGameExpired` (same pure module) checks the live game's date anchor against the clock; on expiry the persisted save is cleared, `state.status = 'expired'` (persist only writes playing/idle, so the dead game can't re-save), and the player lands on the title screen with a toast. Actively-visible play across midnight is deliberately NOT interrupted — finishing keys under the board's own date.
- **codeVersion provenance**: SW posts `{ type: 'codeVersion', value: CACHE_NAME }` to clients on activate, plus replies to `getCodeVersion` requests. Page caches the result in `state.codeVersion` and stamps it onto canonical-board writes (replaces the stale `'v1.5.19'` literal that used to lie about which build wrote a board).
- **On-demand par calc** in `main.js` (leaderboard modal opening before play) calls `loadDailyBoard` directly — also benefits from `waitForFirebaseReady` now.
- **Practice daily** (`?seed=...`) bypasses canonical fetch/write — practice is per-user and shouldn't pollute the shared bucket.
- **Pre-generation** runs nightly at 00:00 UTC via `.github/workflows/precompute-daily-board.yml` (`scripts/precompute-daily-board.mjs`). Anchoring to UTC gives a 4-5h buffer before the daily flips at 00:00 ET. The seed-to-board pipeline lives in `scripts/daily-board-pipeline.mjs` (shared with the regeneration tool, ONE copy) and runs the SAME pipeline `selectDailyRngSeed` + `gameActions.js` would: load the experiment target, force-inject the gimmick if applicable, run candidate selection across 10 trial seeds, pick the winner, write board + dailyMeta to Firebase. Idempotent — write-once rules silently no-op repeated writes for the same date. **Script auth lives in `scripts/anon-auth-rest.mjs`** (shared by both precomputes + the backfill/bootstrap one-offs): its REST sign-in sends a `Referer: https://gregsweeper.com/` header — the web API key is HTTP-referrer-restricted (2026-07-06) and rejects referer-less requests outright — and `deleteSelf(idToken)` removes the run's anonymous Auth account in a `finally` once the writes land (best-effort, never fails the workflow), so script runs stopped accumulating orphan Auth users (~35/month before). The pre-gate/pre-cleanup backlog is cleared by the one-off `scripts/purge-anon-orphans.mjs` via `purge-anon-orphans.yml` (dispatch-only, dry-run default, five-way filter — see the script header). **`scripts/merge-player-uids.mjs`** consolidates one human's multiple anonymous uids (pre-account-linking device fragmentation): rewrites leaderboard-row uids in place, moves/merges uid-keyed weekly rows (per-day best on collision), merges the users/{uid} nodes (history/attempts union, checkpoint/best max, the (streak, lastDailyDate, moltDay) trio as one date-anchored snapshot, powerUps per-key max — pinned in `test/mergeUids.test.mjs`), and removes the emptied source node; the source AUTH record is deliberately left for the aged-orphan purge. Dry-run default; service-account auth; first used 2026-07-07 (anemone-guy ×3, MJP+Stickleback, Hieronymus Bosch ×2).
- **Board cache is network-first with cache fallback** (`loadDailyBoard`/`loadWeeklyBoard` + `src/firebase/boardCache.js`): while online, every load fetches the canonical and refreshes the local copy (~2KB); offline, the cached copy keeps daily/weekly playable. The cache is deliberately NOT authoritative — an admin regeneration can replace an unplayed future board, and a blindly cache-first client that had prefetched the old layout would play a divergent board on the day. Server-reachable-and-empty returns null (no resurrection of deleted canonicals); admin deletions must always be followed immediately by a rewrite.
- **Canonical-board signatures (the #114 trust-model close, 2026-07-05)**: every pipeline-written `dailyBoard`/`weeklyBoard` carries a `sig` — ECDSA P-256 over `canonicalStringify(payload)` (recursively key-sorted JSON, `sig`/`writtenAt` excluded), private key ONLY in the `CANONICAL_SIGNING_KEY` Actions secret (precompute daily/weekly + regenerate daily/weekly + bootstrap all sign; each THROWS without the key). Clients verify BEFORE playing via `gateCanonicalTrust` in dailyBoardSync (applied to network AND cached copies in `loadDailyBoard`/`loadWeeklyBoard`; an untrusted canonical is treated as MISSING → local-gen fallback + reportCaughtError, and is never cached). Trust policy in `src/logic/canonicalSignature.js` (`assessCanonicalTrust`, node-tested): key date < `SIGNATURE_EPOCH` (2026-07-06) → grandfathered unsigned; signed → must verify (an invalid sig is affirmative tamper evidence — rejected outright); unsigned post-epoch → trusted ONLY when `writtenAt` (rules-validated `=== now` on a write-once path, so unforgeable) falls inside the board's own play window (the daily's ET date; the weekly's Mon..Sun) — exactly the first-client-fallback shape, so convergence on precompute-failure days survives while a pre-poisoned future board (writtenAt before its window) is rejected. Verifier-machinery EXCEPTIONS fail open with a report (a browser quirk must not brick a legit daily; attackers can't trigger exceptions, only clean `false`s). Key rotation is additive: new pair, replace the secret, prepend the SPKI to `PUBLIC_KEYS` — the epoch never moves. The `sig` child is whitelisted in both rules blocks.
- **Nightly integrity sweep** (`.github/workflows/verify-canonical-boards.yml`, 00:30 UTC + dispatch; `scripts/verify-canonical-boards.mjs` — read-only over world-readable paths, no secrets): the DETECTION layer for the #114 poisoned-canonical vector (canonical paths are write-once but anon-writable, and clients play them verbatim). Re-verifies every FUTURE-dated dailyBoard (+ dailyMeta + crux) and every current/future weeklyBoard: clean deserialization, mine count === totalMines, byte-identical recompute of the adjacency + displayed-number layers (liar offsets are stored, so recompute is deterministic), and center certification under the board's own gatedCert contract — the generator's exact acceptance. dailyMeta STRUCTURAL feature keys must match a recompute (solver-derived move counts are warn-only: legit drift when a solver change lands mid-horizon); crux payloads must be SOUND (their own numbers admit a provably safe cell, and the claimed answer is among them — version-independent). Post-epoch FUTURE canonicals must additionally carry a VALID `sig` (`verifyFutureSignature` — the unsigned fallback shape is written same-day, never ahead, so an unsigned future board is poison or a pipeline that lost its signing key). Any failure exits non-zero, so the failed workflow run is the alarm, days before the board goes live; remediation (the regenerate workflows) is printed in the log. Tamper classes pinned in `test/verifyCanonicals.test.mjs` + `test/canonicalSignature.test.mjs`.
- **Force-regeneration of an UNPLAYED future date**: `scripts/regenerate-daily-board.mjs` via `.github/workflows/regenerate-daily-board.yml` (`-f date=YYYY-MM-DD -f dryRun=true|false`). Service-account auth bypasses write-once; replaces dailyBoard + dailyMeta with a fresh run of the shared pipeline; prints gated AND ungated certification verdicts. Rails: refuses non-future ET dates (`--force-past` to override) and any date with score rows. Built for the 2026-06-14 reveal-gating re-certification. Weekly equivalent: `regenerate-weekly-board.yml` (also wipes leaderboard + attempt markers).
- **One-off bootstraps** (e.g., a date played by a real user before the canonical-board ship): `scripts/bootstrap-daily-board.mjs` — hardcode date + seed + force-injection state, regenerate, write. Used to lock 2026-04-27 to Chris's actual played v1.5.18 board.
- **Audit script**: `scripts/audit-divergent-scores.mjs` reads `daily/*` and `dailyBoard/*` and reports any score whose `rngSeed` mismatches the canonical's for that date. Read-only by default; `--delete` flag does the cleanup. Used to confirm no historical divergent rows remain after the gate ships.

## Daily Archive (replay past dailies, feed the model)
Past dailies are replayable. A "Past dailies" link on the Daily card opens a month calendar (`#archive-modal`, outside `#app`); tapping a date plays that date's canonical board. Archive plays are a day-of daily in every visible way (same board, par, features, Certified chip) but are walled off from anything that would corrupt the day-of ritual or the par fit.

- **A finished board is NOT replayable** (Christopher, 2026-07-18: "I don't want them able to play archive boards they've already played"). A daily is a one-off: once a board is cleared there is nothing left to find on it, and a replay recorded nothing anyway (`archiveSubmitPlan` is first-completion-only), so it was playable but pointless. `archiveDayState(date, today, completed)` returns `'playable' | 'done' | 'today' | 'unavailable'` and is the single source for the decision; the calendar paints `'done'` as a NON-INTERACTIVE span carrying the ✓ and an "already played" label, so a completed month still reads as a completion map (his call) without inviting a tap. The click handler RE-DERIVES the state rather than trusting the rendered class, because the grid is painted once per month view while the completed-set refreshes on open. **`completed == null` means UNKNOWN, not empty, and fails OPEN**: a signed-out player or a failed `loadDailyHistory` read cannot be told what they have finished, and blocking the whole calendar on a flaky read is worse than letting a replay through — the data is protected regardless, since `archiveSubmitPlan` fails CLOSED on unknown history and records nothing. The calendar's completed-set and the Board Heatmap's spoiler gate both derive from the same `users/{uid}/dailyHistory` node (via `loadDailyHistory` and `fetchUserDailyHistory` respectively), so the two surfaces cannot disagree about what you have played.
- **Two pure gates** (`src/logic/archiveEligibility.js`, node-tested in `test/archiveEligibility.test.mjs`): `isArchivableDate(date, today)` offers `FIRST_ARCHIVE_DATE` (2026-03-06, the app launch) through yesterday (today is the live Daily's job; canonical storage only began 2026-04-27, so launch..04-26 were regenerated from each date's seed with the current pipeline and backfilled by `scripts/backfill-old-dailies.mjs` — fresh boards stamped with old dates, NOT the unrecoverable per-device originals, and all below `ARCHIVE_FIT_EPOCH` so they never feed the fit); `archiveSubmitPlan(date, hasHistory)` returns `{submitFit, writeHistory}` enforcing first-completion-only (a `dailyHistory` row present → record nothing) and the `ARCHIVE_FIT_EPOCH` (2026-05-07, the dailyHistory ship) below which a date stays playable but never submits a fit row (it could double-count a pre-history live play). `CRUX_VIEWED_KEY_PREFIX` is the shared localStorage key PR 4's `?crux=` route writes and the archive submit reads.
- **Launch** (`launchDailyArchive(date, raw)` in modeManager): the calendar PROBES the canonical first (`loadDailyBoard`; archive has NO local-gen fallback, a missing board isn't offered), then this bypasses `switchMode`'s resume-the-real-daily path and forces a fresh `newGame` with `state.isArchivePlay = true`, the caller-set past `dailySeed`, and the fetched board in `state._archiveRaw`. `newGame` keeps the past seed for archive, reads `_archiveRaw` verbatim, never re-stamps `canonicalDailyBoard` (today's stash), and ABORTS rather than local-gen if the board is somehow missing. `switchMode` clears `isArchivePlay` on every normal mode switch so a resumed real daily can't inherit it.
- **Never persists** (`persistGameState` early-returns on `isArchivePlay`): archive shares the daily save slot, so persisting would clobber an in-progress real daily, and a past-date save would fail resume anyway. The outgoing real game is persisted before archive starts, so returning to today's daily resumes intact. Archive is always re-launched from the calendar.
- **Win path** (`winLossHandler`): `isArchivePlay` is excluded from `isRealDaily`, so streak, `saveProgress`, `markDailyCompleted`, the residual cache (`appendDailyResidual`), and the "day streak" suffix are all skipped. Submission routes through `submitArchiveCompletion`: read `dailyHistory[date]`; on a fresh date submit `submitArchiveScore` to `dailyArchive/` (only when `date >= ARCHIVE_FIT_EPOCH`) and write `dailyHistory` (the dedup key + the chart feed); a replay records nothing. Archive uses ONLY the auto-submit path (the manual name form stays hidden, with a defensive guard in main.js so a stale form can't post archive into `daily/`).
- **R refit** (`scripts/refit-par-model.R`): archive rows fetch from `dailyArchive.json`, parse through the shared `parse_score_rows`, bind with an `archive` marker, drop `cruxViewed` rows, and are held OUT of the fit until `ARCHIVE_FIT_THRESHOLD` (20) rows exist (instrument-first, like timed mode and new features). Once pooled, an `archivePlay` offset term (positive-only lognormal prior, since `build_priors` bounds every fixed effect at `lb=0`; a non-negative replay-pace offset is the documented assumption) absorbs the cohort shift and is netted out of the intercept bias-correction. `archivePlay` is FIT-ONLY — never written into `PAR_MODEL` (predictPar stays day-of par), exactly like `legacy_bombs`. Archive rows that collide with a same-`(uid,date)` day-of row are dropped (defends the falls-open dedup).

## Crux Teaser (`?crux=` share route)
A standalone share page showing a PAST daily's crux — the first step plain counting could not reach — as a "find the safe square" mini-puzzle, then a CTA to today's board. The teaser itself writes nothing, but the route is NOT fully write-free: `initAnonymousAuth` and the module-level lastSeen-beacon wiring in main.js run before the `?crux=` early-return, so a prod crux visitor still gets an anonymous session and (after auth settles) a `users/{uid}/lastSeen` stamp — deliberate, since a share-page visitor is a prospective player. Built for public growth (the par model needs sample size). Never spoils the live board: the route refuses today and later, and the default (`?crux=` / `?crux=1`) is yesterday ET.

- **One source of truth** (`src/logic/cruxExtract.js`, node-tested in `test/cruxExtract.test.mjs`): `extractCrux(board, rows, cols, fr, fc)` finds the crux = the first `isBoardSolvable(..., {trace:true})` entry with `tier >= 1` (the SAME definition the win-receipt confession uses — `winLossHandler._renderWinReceipt` now calls `extractCrux`, so receipt and teaser can never disagree about the square). Default first click is board center, matching the receipt and the feature/par solve. All trace entries are SAFE reveals (mines are flagged, never traced), so the crux is always a safe deduction; the sentences come from `explainDeduction`.
- **Pre-crux snapshot** (`boardSolver.js`, opt-in `{captureCruxState:true}`): captures `sim.slice()` (0 hidden / 1 revealed / 2 flagged) the instant before the first `tier>=1` reveal — the exact state a player faces at the crux. Additive and off in generation hot loops (like `trace`); lets `materializeCrux` skip re-implementing flood/unlock.
- **Materialization** (`materializeCrux`): crops the snapshot to the sources + answer + a widening ring (1→3, capped at 9×9 so the teaser stays phone-sized), rebuilds a plain mini (other gimmicks stripped) with every revealed number RECOMPUTED to count the mines shown so the real layout satisfies it (`findDeducibleFrontier` on a satisfiable system can never prove a false square), then re-verifies the answer is provably safe at `tier >= 1` from the shown numbers alone, widening until it is. **Walls are carried, not stripped**: in-crop wall edges (both endpoints inside the crop) are remapped into the mini so the recompute + re-verify are wall-aware, and they ship in the payload so the teaser DRAWS them — numbers, adjacency, and what the player sees all agree; out-of-crop walls can't affect an in-crop count, so they're dropped. Returns the `cruxes/{date}` payload `{rows, cols, cells:[{r,c,n}], answer:{r,c}, sources:[{r,c}], walls?:[edgeKey], tier, sentence, sentenceSocratic}` (~600 B, max ~1.4 KB) or null. **Coverage ≈ 77% of past canonicals** (measured 37/48); the rest are genuine breather boards (no tier>=1 step) or cruxes whose proving region is too wide to crop. `scripts/measure-crux-yield.mjs` reports yield/tiers/sizes.
- **Teaser page** (`src/ui/cruxTeaser.js` + `#crux-teaser` sibling of `#app`): `main.js` init branches on `?crux=` BEFORE the startup gate (resolve date, refuse `>= today` and `< FIRST_ARCHIVE_DATE` → fall back to yesterday, then render and return — no game init, no canonical prefetch). `loadCrux(date)` (dailyBoardSync) fetches the world-readable node (works logged-out). The mini renders revealed clues + fog, plus wall lines via `_renderMiniWalls` (a bar in each walled edge's gap, positioned from the laid-out cells' offsets, `pointer-events:none`). **The frame is "look how much Greg can prove", not "find THE safe square"** (a real position has many provably-safe cells, not one — a single-answer model wrongly bounced the others). The teaser recomputes the FULL deducible frontier ON THE PAGE (`findDeducibleFrontier` over the payload's numbers + walls via `_boardFromPayload`) and leads with the counts ("Greg can prove N squares safe and M mines"); left-tap / Enter OPENS a provably-safe cell (✓, advances a counter), right-click / long-press FLAGS a forced mine (the drawn flag sprite via `spriteImgHTML`, not an emoji), and any gated wrong gesture bounces with a teaching nudge — open only safe, flag only mines, the same control scheme and gating as the Gym. Greg and the flag render as the canonical drawn sprites (`spriteImgHTML('smiley'|'flag')`), so the share page looks like the real game. A "Show me all" button (or finding every safe) lights up the whole frontier + the crux sentence + the play CTA. Because the frontier is recomputed client-side, this needed NO re-backfill; the payload's `answer`/`sources` fields are now vestigial (the `sentence` is still the featured crux explanation). Viewing sets `localStorage[CRUX_VIEWED_KEY_PREFIX + date] = '1'` (the flag the Daily Archive submit reads to drop a previewed date from the par fit). When there's no crux node, the page solves the canonical client-side (`loadDailyBoard` + `extractCrux`) to distinguish a genuine BREATHER (no tier>=1 step — shows "{date} was a breather…") from a crux that just couldn't be cropped (the rare liar case — keeps the plain "no teaser" line); no Firebase marker needed, and a liar board is never mislabeled a breather. Fog cells use class `crux-fog`, NOT `hidden` (the global `.hidden` is display:none).
- **Writes**: the nightly `precompute-daily-board.mjs` and the admin `regenerate-daily-board.mjs` write `cruxes/{date}` alongside the board + meta (regenerate refreshes/clears it so a stale layout is never described). `scripts/backfill-cruxes.mjs [--dry-run] [date]` populates past canonicals (anon auth, write-once, strictly-past only). Rules: `cruxes/{date}` is write-once + world-readable (cloned from `dailyMeta`), pinned by `test/cruxRules.test.mjs`.
- **Share card upgrade** (`generateShareCard` daily branch, HARD CEILING 5 lines + URL): title+date · `⏱ {t}s · beat Greg by {Δ}s 🦀` (Greg = par; over-par → "Greg won by") · pace bar · modifier icons + the board's hardest step in plain words (from the certified `state.boardCertificate.tier`, never more than proved) · strikes. ## Board Heatmap ("where the mines went off", Journal PR E)

The Journal's one POPULATION exhibit, and the only Firebase phase of the Journal arc: a past daily board drawn as a grid, each square shaded by how many players detonated a mine on it. `bombHitEvents[].{row,col}` on the score rows is the ONLY per-cell signal a client ever submits (`clickTimeline` never leaves the device; `hintEvents` carry no coordinates), so it is the one thing this can be built from.

- **Pure layer** `src/logic/boardHeatmap.js` (node-tested in `test/heatmapAggregate.test.mjs`) owns every decision that could fabricate a claim: `aggregateBombHits(scoreRows, board)` (the rollup's whole decision layer), `selectHeatmapDate(entries, completedDates)` (the gate), `heatmapCopy(plan, dateLabel)`, `heatLevel`/`maxCellCount`/`cellKey`/`parseCellKey`. The script and the client both consume it, so the map and the map's caption can never disagree.
- **Aggregation rules.** ONE ROW PER PLAYER per date (day-of wins over an archive replay, then earliest timestamp) so one person's two sittings can't read as two people struggling. `n_players` counts SOLVERS, not hitters, so it is the honest denominator for the rate scale. Brute-force probe rows (`isBombHitCheat`, >30% of the board's mines) are dropped ENTIRELY, from both the cell counts and the denominator — that player is messing around, not playing (his ruling, 2026-07-18). Coordinates are bound-checked against the canonical board's `rows`/`cols`.
- **Shading is a RATE, not a rank (Christopher's ruling, 2026-07-18).** A square's level comes from the SHARE of that board's solvers who detonated it, on the fixed `HEAT_BANDS` scale (≤5% / ≤10% / ≤20% / above), so the same shade means the same thing on every board and the legend can state real percentages. The first implementation scaled against the board's own busiest square, which ranks rather than measures: a board where three people had a bad moment and nobody else did lit up as though it were brutal, because those three WERE the maximum. On a rate scale one hit among thirty reads as the 3% it is, which is why a single hit is safe to draw and why there is no per-square minimum. A square's count IS a distinct-player count (one row per player, and a struck mine stays revealed, so a player can hit a given square at most once), so the share is a genuine proportion of people.
- **The THREE gates (this is the feature's ethic, do not relax).** (1) AUDIENCE: nothing renders until `MIN_PLAYERS_FOR_HEATMAP` (30) distinct players have SOLVED a board. Below that the exhibit does not exist — no map, no waiting copy, no card (his ruling: hide it until we regularly have 10+ players and probably closer to 30). (2) SPOILER: a board is only drawn for a player who has already completed it — the map lights only cells that held mines, and past dailies are replayable through the Daily Archive, so an unplayed board would ship as a partial mine map. Unknown history (signed out / failed fetch) resolves to 'none', never to a guess. (3) ALIGNMENT: the canonical board is REQUIRED, not preferred — if it cannot be fetched, or its shape disagrees with the rolled-up grid, the caption renders and the grid does not. In gates 1 and 2 the pure layer WITHHOLDS the payload rather than merely hiding it, so a rendering bug cannot leak a map.
- **Rollup** `scripts/rollup-board-heatmap.mjs` + `.github/workflows/rollup-board-heatmap.yml` (15:30 UTC daily, after the 14:00 refit window, plus `workflow_dispatch` with `dryRun`/`refresh`/`date` inputs, all passed as ENV VARS rather than interpolated into the shell). Only dates strictly before today in ET are rolled up, so a map is built on settled scores. **`boardHeatmap/{date}` is writable by NOBODY at the rules layer** (`".write": false`) — the sibling `cruxes`/`dailyBoard` blocks grant `auth != null && !data.exists()` because they have a legitimate first-client fallback writer, but this node has none, and copying that grant would let any anonymous visitor pre-claim a date and permanently publish a fabricated per-cell mine map with a forged `n_players` that sails past the honesty gate (the #114 poisoned-canonical class, with no signature layer and no coverage in the nightly sweep). The service-account script bypasses rules and is the only writer. **Every run RECOMPUTES the trailing `REFRESH_WINDOW_DAYS` (45, matching the client's fetch window)**: a date becomes eligible the moment it is past in ET and the cron runs at 11:30 ET, so a freeze-on-first-write would pin `n_players` at its day-after value and gate 1 could never open on its own. Dates older than the window are skipped unless `--refresh`. A date with no canonical `dailyBoard` is skipped rather than published unanchored.
- **Client** `src/ui/journalHeatmap.js` (lazy-imported by `journalView.js` into a slot after the queue line, so a Firebase outage never holds up the notes) reads the bounded `loadRecentBoardHeatmaps()` in `dailyBoardSync.js`, the player's own `dailyHistory`, and the canonical board for the authoritative grid. In-app only: the logged-out `?report=` page has no play history to check the spoiler gate against.

## Adaptive Experimental Design
- EVERY daily generates 10 candidate seeds (`${dateString}:trial0`..`trial9`), solves each, scores each by its assigned mission, and picks the highest-scoring candidate. ~500–800 ms of CPU on first daily load.
- **Multi-objective per-slot missions.** Slot 0 = the PRIMARY mission, force-injecting the high-CV target's gimmick (chosen by the R refit) and allowed to roll a second gimmick at the natural ~10% rate. Slots 1–9 = COVERAGE missions, each force-injecting a different undersampled gimmick from the ranked `coverage_targets` list (also produced by the refit) and constrained to single-gimmick only via `getDailyGimmick(seed, rng, forcedGimmick, singleOnly=true)`. Slots map ONE-TO-ONE onto the coverage list and do NOT cycle: slot N takes `coverage[N-1]`, and a slot past the end of the list has no mission and is SKIPPED, so the effective candidate count is `1 + coverage.length` (with today's 8-entry list, 9 of the 10 slots are evaluated) unless a decorrelation mission claims the tail (next bullet). Wrapping would hand the top-deficit features double slots and silently halve the sampling rate of everything below them. **Four things are single-sourced in `experimentDesign.js` and must never be re-implemented anywhere**: the slot arithmetic (`resolveMissionForSlot`), the score formula and its cap (`missionCandidateScore` / `COUNT_CAP`), the candidate count (`resolveCandidateCount`), and the payload mission stamp (`missionStamp`). Both the client (`getMissionForSlot` → `selectDailyRngSeed`/`parResolve`) and the Node precompute (`daily-board-pipeline.missionForSlot` / `candidateCountFor`) call them. The slot mapping used to exist as two copies and DRIFTED (the pipeline wrapped, the client did not), so precompute could pick a `:trial8/9` seed the client would never choose and `parResolve` could quote a par for a different board than the date's canonical (fixed 2026-07-18; pinned by `test/missionSlots.test.mjs`); the other three followed it into one place before they could do the same. `TARGET_TO_GIMMICK` likewise now exists once — the pipeline's inline duplicate is gone.
- **Decorrelation missions (PR F1, 2026-07-18).** A third mission type, occupying the slots PAST the coverage list on nights the refit emits one. Primary missions chase a coefficient's uncertainty and coverage missions chase a gimmick's sample gap; neither breaks COLLINEARITY, which is what actually blocks a confounded coefficient — more boards of the same correlated shape cannot separate a feature from its confounder. A decorrelation mission aims at the RESIDUAL instead. The refit emits an optional `decorrelation_mission: { feature, confounder, slope, intercept, residualSd, weight }` (the fitted line between the worst-confounded PAIR it can act on), and the client scores a candidate by the MAGNITUDE of its residual, `|features[feature] − slope × features[confounder] − intercept| / residualSd`, capped at `COUNT_CAP` like every other mission. **Both tails count** (Christopher's ruling, 2026-07-18: "both tails should be sampled"): what reduces the correlation is residual VARIANCE, so a board two SDs BELOW the line is worth exactly as much as one two SDs above. An earlier cut scored a signed residual toward whichever tail the fit judged thinner; that discarded half the reachable boards for no gain in precision, and a one-sided design is also what would hide the inverted-U the clue-ambiguity hypothesis predicts. A board sitting ON the line scores 0 and loses the day to coverage, which is correct. All the statistics stay R-side; the client does one subtraction and one divide, so every player resolves the same board. Deliberately PAIRWISE rather than a multi-term VIF, because the client's scorer takes exactly two features and a mission it cannot act on is worse than none. `getTargetGimmickName` returns null for the target (there is no gimmick to force), so a decorrelation board rolls the NATURAL lottery and SELECTS rather than constructs — which makes candidate count its only reach knob: `resolveCandidateCount` adds `DECORRELATION_SLOTS` (10) past the coverage list on those nights, linear cost, paid only then. **With no mission emitted, selection is byte-identical to the pre-F1 behaviour** (`resolveMissionForSlot` with a null/malformed mission returns exactly what it returned before), and `normalizeDecorrelationMission` rejects anything malformed so a corrupt file degrades to an ordinary day rather than a NaN score. **Frequency is a CADENCE, not a weight** (`DECORRELATION_INTERVAL` = 7 days, anchored to `lastDecorrelationDate` like the revalidation clock, advancing only on a night that shipped a mission). A confound bad enough to deserve a mission is bad every night, so a weight tuned to actually win takes the whole calendar: measured at 11 of 12 days, which starves the coverage slate. The weight itself is DERIVED R-side, solving for the residual depth at which a decorrelation board ties the strongest coverage mission, so it recalibrates when the deficits move; a flat guessed weight made the mission lose 12 of 12 days and ship as dead code. Measured reach (`scripts/measure-decorrelation-reach.mjs`, 400 generated boards, seeded and reproducible): the generator's natural confound is r = 0.76 / R² = 0.58 between `clueShare3` and `density`, and its residuals are symmetric (15.3% beyond 1 SD on each side); best-of-19 (a live decorrelation day with an 8-entry coverage list) reaches ≥1 residual SD 100% of the time and ≥2 SD 63%, landing above the line 59% of the time (so both corners really are sampled), and adds spread around the line without dragging either marginal far (3-share +0.46 SD, density +0.17 SD). The high-clue tail is NOT reachable by selection at all (60% of boards carry no 5+ clue, median 0), which is the surviving case for F2's constructive placer. Pinned in `test/decorrelationMission.test.mjs`.
- **The clue-digit shares are MEASURED but never MAXIMIZED.** `clueShare2/3/4/5plus` are computed client-side by `clueShares` in `dailyFeatures.js` (a straight port of `clue_histogram` / `digit_shares_from_boards` in the R refit — same exclusions: mines carry no clue, mystery hides its number, a plate shows a timer) so the digit axis is scorable at SELECTION time. The R refit keeps deriving them from the canonical boards for the fit, which is authoritative and covers every date back to `DIGIT_ERA_START`. They are listed in `OBSERVATIONAL_TARGETS` and the COUNT scorer returns 0 for them: every board feeds every digit study, so a "threes study" needs no threes-heavy board, and chasing a high 3-share would actively deepen the confound (3-share runs r ≈ 0.80 with density, so the boards that maximize it are the dense ones we already have too many of). Before the port this held by accident, because `features.clueShare3` was undefined; it is now explicit and regression-tested. The refit's `digit_df` join drops any meta-carried copies of the shares BEFORE joining the board-derived ones (`select(-any_of(DIGIT_FEATURES))`) — without that, dplyr suffixes both sides to `.x`/`.y`, `digit_df$clueShare2` becomes NULL, `sd(NULL)` is NA, and the eligibility `if` (which sits OUTSIDE its tryCatch) kills the WHOLE nightly refit, not just the digit block.
- **Scoring.** Each candidate's score is `target_count_in_features × deficit_weight`, computed by the shared `missionCandidateScore` in `experimentDesign.js` (which both selection paths call — see the mirror-pair note below), where the target and weight come from `getMissionForSlot(i)`. Slot 0's weight is fixed low (`PRIMARY_WEIGHT = 0.1`) so it only wins when its target's cell count is high enough to overcome the gap with the heaviest coverage weight (typically ~0.5 for the most undersampled gimmick). In practice this yields roughly 1-in-10 primary outcomes when the coverage list is well-populated — matching the design intent that 9 of every 10 dailies probe sample-size deficits, not posterior-uncertainty.
- **Force-injection rationale.** Without forcing, the natural per-seed gimmick-inclusion rate of ~6.6% means ~50% of seeds have zero of the targeted feature, making maximisation meaningless. Force-injection drops miss rate to 0% so the 10-way contest competes on cell COUNT and DEFICIT WEIGHT instead of mere presence. All four call sites of `getDailyGimmick` (`selectDailyRngSeed`, `gameActions.js`'s play path, the on-demand par calc in `main.js`, and the precompute script) pass the same `(forcedGimmick, singleOnly)` resolved from `getMissionForSeed(seed)` so the chosen seed and the regenerated board agree.
- **Primary-target selection.** After each fit, the coefficient with the highest posterior coefficient of variation (SD / |mean|) from a whitelist of push-able features wins — EXCLUDING any feature targeted in the last 3 days (`recentTargets` in `experimentTarget.json`). Stops three liar-heavy dailies in a row while still pushing data toward the most uncertain coefficient. Client fetches via `loadExperimentTarget()` in `src/logic/experimentDesign.js`. **Two additions ride this candidate pool (PR D, 2026-07-17):** (1) the four `clueShare*` digit shares (from the secondary fit — see Refit Workflow) are merged into `target_candidates`, so a digit share can WIN the primary slot and become a journal study; a digit target is OBSERVATIONAL (not a gimmick, so no force-injection — `getTargetGimmickName` returns null and it falls through to the natural lottery; `selectDailyRngSeed` scores it 0 via `OBSERVATIONAL_TARGETS` and a coverage slot wins the actual board, which is correct: every board feeds every digit study, so a "threes study day" needs no threes-maximized board. **That zero used to be accidental** — the shares were simply not computed client-side. PR F1 ported the histogram so the decorrelation residual is scorable, so the refusal is now an explicit list; see the Adaptive Experimental Design section). (2) Every `REVALIDATION_INTERVAL = 14` days the primary target is instead the STALEST SETTLED feature (see Refit Workflow's revalidation bullet), stamped `reason: "revalidation"`.
- **Coverage-target selection.** The R refit counts unique-date occurrences of each gimmick feature, drops any gimmick at >= 20 boards (COVERAGE_SATURATION_BOARDS coverage throttle - saturated features still appear via the primary target or the natural lottery) in `df_fit`, computes `deficit_weight = 1 / (count + 1)` per gimmick, excludes the chosen primary target, and emits the result sorted descending by deficit. So `liarCellCount` with 1 board (deficit 0.5) ranks above `compassCellCount` with 5 boards (deficit 0.17). Lives in `experimentTarget.json` as `coverage_targets: [{feature, n_boards, deficit_weight}, ...]`.
- **Double-gimmick rate.** Default `DOUBLE_GIMMICK_PROB = 0.10` (was 0.20). The coverage missions absorb most of the "make boards more varied" goal so we don't need the natural double rate doing as much work, and lower noise = cleaner per-feature deltas. Coverage slots additionally suppress the roll entirely via `singleOnly`.
- **State plumbing.** `state.dailyRngSeed` holds the effective RNG seed (the trial variant on improvement days, plain dateString otherwise). All daily-mode RNG creation in `gameActions.js` routes through this field; `state.dailySeed` remains the plain date for Firebase keys / leaderboard joins / local-storage lookups. The play path uses `getMissionForSeed(state.dailyRngSeed)` to recover which mission won, then force-injects the matching gimmick — without this, a coverage-slot winner would get the primary gimmick force-injected on the play board and we'd ship the wrong layout.
- **Determinism.** Same date + same loaded primary + same coverage_targets list → same per-slot missions → same candidates → same winner across all clients. Cache-version drift on `experimentTarget.json` between clients can desync the chosen seed; Check-for-Updates handles most cases, and the diagnostics modal surfaces the loaded primary target + coverage list so mismatches are inspectable.

## Challenge Difficulty Curve (Sawtooth)
Computed by `getDifficultyForLevel()` in `difficulty.js` — no static table.
- **L1-10:** Tutorial ramp, 5x5→9x9, 8%→16% density, no gimmicks
- **L11-110:** Each 10-level block introduces one gimmick (walls L11 … compass L91, worm L101). Board drops to 11x11 at intro, ramps to 14x14 by block end. Density drops 10% (relative) at intro, ramps to next peak. The worm block L101-120 is the 20-level capstone (intro dip at 101, ramp to the 34% cap at 120); `getGimmicksForLevel` branches on "is any intro block active" (`primaryGimmick`), not hardcoded level bounds.
- **L111-120:** Post-intro free-for-all — all gimmicks equal, `progress = (level - 110) / 10`, second gimmick 80%→100%, third 40%→100% (guaranteed 3 at L120).
- **Gimmick selection:** Primary gimmick is 100% present during its intro block. Old gimmicks appear as secondary (60%) and tertiary (10%).
- **Hard cap:** 34% mine density maximum for fast board generation. `GIMMICK_INTROS` and `PEAK_DENSITIES` in difficulty.js are lockstep arrays (10 entries each); the final block runs to `MAX_LEVEL`.

## Modifier (Gimmick) System
11 types defined in `src/logic/gimmicks.js`:

- **Worm Tiles (L101, 2026-07-16):** revealing an egg hatches a worm (2–5 segments) that crawls one orthogonal step onto REVEALED cells every 0.5–3s (shifted down from 1–4s after playtest — worms squatted on needed numbers too long) scaled by its PACE trait — a per-egg roll in [0.8, 1.3] (`WORM_PACE_MIN/MAX`), so a board has noticeably quick and slow worms (~1.4s vs ~2.3s mean move) that every player sees identically (self-overlap allowed, spawns coiled on the egg, stays put when boxed in but still spends the move) and burrows after its OWN move budget — `wormLifetimeFor(seedIdentity, r, c)`, a per-EGG roll in [30, 80] (`WORM_LIFETIME_MIN/MAX_MOVES`) seeded like the length, so one daily worm can squat near-forever while another is a short cameo, yet every player sees the identical budgets (Christopher's ruling: per-worm variety, zero cross-player variability). Worms hatch at different times and each counts down alone — they never bury in sync. The step is NOT uniform, two layers: (1) MOMENTUM — with `WORM_PERSIST_PROB` (0.5) the worm first tries to continue its last heading when the cell ahead is walkable (`lastDir`, persisted; a pure random orthogonal walk backtracks so much its net travel grows like √moves — worms paced in place, Christopher's report); (2) otherwise candidates are roulette-weighted by `WORM_NUMBER_AVERSION^adjacentMines` (0.7 — his "lightly weighted away from large numbers, toward lower ones"; a 0 beats a 4 about four-to-one, nothing is forbidden, and the worm reads TRUE counts, not liar-displayed values — a side effect is that big-number clue cells are covered less often), with the REVERSE of the heading additionally suppressed to `WORM_BACKTRACK_WEIGHT` (0.05) of its weight — ~5% reversal in a corridor, under 2% in open field, and a dead end still resolves by turning around since the tiny weight is then the whole roulette (his "5% or if it's stuck"). ### Theme Expression Tokens (the "wildly different per theme" layer)
The `:root` block in `global.css` exposes a large token contract so a theme can diverge in **motion, type, texture, cell treatment, and feedback colors**, not just palette. Every token defaults byte-for-byte to the value that used to be hardcoded, so a theme that overrides nothing renders exactly as before. Groups:
- **Motion:** `--anim-reveal-dur/-ease`, `--anim-flag-dur/-ease`, `--anim-mine-dur/-ease`, `--ease-bounce`, `--ease-standard`. Only the `animation` shorthand (duration/easing) is tokenized — `@keyframes` interiors can't read vars, so a theme changes *choreography* by shipping its own keyframes in its theme file. History note: the flag/mine tokens were declared but DEAD (`.cell.flag-pop` / `.cell.mine-chain` hardcoded their literals) until 2026-06-10; the root defaults were corrected to the effective literals (flag 0.35s, mine 0.4s) when wired, so tokenless themes render byte-identically while the ~17 themes that had set flag tokens finally animate as designed. Flag choreography overrides use `[data-theme=X] .cell.flag-pop { animation-name: ... }`.
- **Type scale:** `--fs-title`, `--fs-lcd`, `--fs-cell-number`, `--fs-mine`, `--fs-flag`.
- **Cell + sizing:** `--cell-shape-radius`; `--cell-min-size` / `--cell-max-size` / `--cell-fit-max-size` are read by JS in `boardRenderer.js` (`resizeCells`/`adjustCellSize`) because JS owns `--cell-size` at runtime — a CSS `--cell-size` override would be clobbered, so these bound tokens are the only way a theme can widen/tighten cells. `--grid-gap` also participates in board width (candy 3px, matrix 1px vs the 2px default), so BOTH fitters read the live computed gap and `applyThemeLive` re-runs `resizeCells` after the new theme's lazy stylesheet loads (`loadThemeCSS` returns a promise resolving on link.onload) — without that refit a wider gap pushed the fit-content board past its container (cells spilling off the side, fixed 2026-07-12; pinned by `tests/e2e/themeCellFit.spec.mjs`). `--cell-gap-seal` = the grout color painted between cleared cells when an effect is on (see Effect layering). It defaults to `--color-cell-revealed`, but **that default is the banned "slab" look (grout == tile) and must NEVER ship on an effect-bearing theme** — see the grout-contrast HARD rule below. Every theme that registers a `THEME_EFFECTS` entry sets its own contrasting grout (forest sage, candy pink, circuit-board copper trace, nest twig weave, inferno lava crack, stained-glass dark lead, etc.).
- **Backgrounds:** `--bg-page-image` (a fixed `body::before` layer, default `none`), `--bg-page-blend`, `--bg-board` (`#board-container`). Vector only (gradients / CSS patterns / SVG data-URIs) — no raster assets, so no `sw.js` ASSETS/CACHE_NAME coupling. Animated / board ambiance routes through `src/ui/themeEffects.js`, not CSS. **Effect layering:** the `.theme-fx` container is `z-index: 1` — between unrevealed cells (z-index auto/0) and revealed cells (`.cell.revealed` is `z-index: 2`) — so ambient animations (rain, leaves, sparks, stars) play over the fog + background gaps but never wash over revealed numbers/markers. Walls stay on top at `z-index: 3`. Each theme's effect should keep particle counts modest but the particles large/visible (the original Forest spores were 2-4 sub-5px fading dots = invisible; falling leaves at 13-22px read clearly). **Gap-seal occlusion:** lifting revealed cells above the effect handles the cell *bodies*, but the 1-2px inter-cell *gaps* would still show the effect as slivers. `applyThemeEffects` adds `.fx-on` to `#board` only when a particle effect is registered (effect-less themes are byte-identical — no seal, no z-index lift). **Software-rendering gate (2026-06-17):** `applyThemeEffects` early-returns (treating every effect theme as effect-less, no `.fx-on`) under `prefers-reduced-motion` OR software compositing — `isSoftwareRendering()` in `src/logic/deviceCapability.js` probes the WebGL `UNMASKED_RENDERER` and matches SwiftShader / Microsoft Basic Render Driver / llvmpipe / software (or no GL context at all). Per-frame DOM particles are cheap on a GPU but stutter the whole game on the CPU, so a software-compositing browser (integrated/VM/remote, or a GPU-driver fallback that can hit even a strong card) keeps the theme's colors/sprites/static backdrop but loses the live particles. The pure string matcher `isSoftwareRenderer(str)` is node-tested in `test/softwareRender.test.mjs`; an unknown/blocked renderer string is conservatively treated as NOT software (real GPU with the debug ext hidden for privacy must keep its effects). As of wave 2 (2026-06-10), 24 of 26 themes register an effect; only classic and dark stay deliberately bare (restraint is their identity, like classic's default synth voice). Wave 2 effects (editorial ink flecks + headline rules, sumi-e ink motes + brush wisps, blueprint drafting ticks + measure lines, cartography route dashes + sounding rings, origami gliding paper triangles, nest gulls gliding across the sky) are VECTOR-DRAWN — styled divs with gradients / clip-paths / dash patterns, never emoji glyph particles — per the "worlds apart, less emoji" direction; prefer that style for any future effect work. Under `.fx-on`, each revealed cell gets a two-layer seal: a `::before` SQUARE solid fill of `--cell-gap-seal` over cell+gap (z-index -2; square so four neighbors tile every 4-cell junction shut — a rounded ring or box-shadow leaves a diamond there, the inherent weak spot of rounded corners), and a `::after` rounded `--color-cell-revealed` body on top (z-index -1) so each tile shows its own surface and the grout reads only in the gaps. The seal EXCLUDES the face-cue markers — sonar/compass/wormhole (translucent bg tints), locked/pressure-plate/defused (`::after` glyphs), and MIRROR (dashed border): the fx-on z-lift makes each revealed cell a stacking context, and negative-z pseudos paint ABOVE the element's own background and borders, so a sealed mirror cell's dashes were buried (found 2026-06-11, the mirror daily on chalkboard — invisible pairs in prod). The tint markers get an opaque revealed base composited under their tint on `.fx-on` so the effect can't bleed through them; a mirror PAIR is adjacent, so the seam between the two excluded cells can show a 1px effect sliver (accepted). Liar (outline — outlines paint last) and mystery (text) survive the body layer and keep the full seal. Colorblind mode (whose `::after` is a shape glyph) forces `--cell-gap-seal` back to the revealed color so the tile reads as one cleared surface. Verified by dyeing the effect a unique color and pixel-sampling every gap + junction: 0 leak. **Holistic fog art (2026-06-11):** `#board` consumes `--bg-fog-art` (default `none`) as a background-image sized 100% x 100% under the cells; a theme sets it to ONE large vector drawing (data-URI SVG or gradient) and switches its `.cell.unrevealed` gradient + `--color-cell-hidden-hover` to TRANSLUCENT rgba tints, so the drawing reads through the fog as one continuous image spanning the board (revealed cells stay opaque -- revealing tears the sheet). Compositing base is `#board`'s background-color (`--color-border`); the gallery mini-boards mirror that. Seven worlds use it: origami (crane crease pattern), cartography (worn chart), nest (open sky — clouds + a corner sun), blueprint (cyanotype sheet + white number set), chalkboard (half-erased workings + chalk-dust number text-shadow), noir (venetian-blind bands), ocean (sounding chart). Fog must STILL read as interactive tiles: keep borders/hover and tint alphas around 0.3-0.55, and drawings need bolder strokes than instinct suggests (the fog tint sits on top).
- **Special-cell markers:** `--marker-liar-outline(-width)`, `--marker-sonar-tint`, `--marker-compass-tint`, `--marker-wormhole-0/1/2`, `--marker-mirror-0/1/2(-width)`, `--marker-plate-timer/-border/-glow`. See legibility contract below.
- **Overlays / power-ups / timer / victory:** `--overlay-*` (wrong/correct flag, suggest move/start, mine-hit glow), `--pu-*` (shield, xray, lifeline, magnet), `--timer-warning/-critical/-critical-glow`, `--victory-color/-duration`.

**Special-cell legibility contract (HARD FLOOR — do not relax):** marker tokens may be re-hued slightly by a theme only to avoid clashing with its own background. Every marker must stay (a) unmistakable as its modifier, (b) mutually distinct, (c) high-contrast vs the cell bg (line markers ≥ 3:1, like `--color-wall`), (d) above the alpha floors (tints ≥ 0.12, borders ≥ 0.6). Identity is anchored in a non-color channel (📡/arrow glyph, italic+underline, dashed border vs outline vs fill) so meaning never rests on hue alone. The markers keep their `!important` so an aggressive cell-bg can't bury them.

**Grout-contrast contract (HARD RULE — absolute, do not relax):** for any theme that registers a `THEME_EFFECTS` entry (so `.fx-on` is set and the gap-seal is painted), `--cell-gap-seal` MUST be a color that visibly CONTRASTS `--color-cell-revealed` — never equal to it. Grout == tile produces a solid "slab" where cleared cells merge into one undifferentiated block; this was explicitly rejected ("I see that we might be making grout fill that's the same as the tiles. Absolutely don't do that."). Cleared cells must always read as separate tiles set in a contrasting grout (chalk line on slate, copper trace on PCB, twig weave between nest tiles, dark lead between stained-glass panes, glowing lava crack between charred inferno tiles). Practical floor: luminance delta ≥ ~50 between grout and tile, and the grout should be thematically motivated (it's the "what's between the tiles" of the world), not an arbitrary outline. The default (`var(--color-cell-revealed)`) is intentionally the slab so an *effect-less* theme stays byte-identical — but it is a bug on any effect theme. Verify by revealing a region and confirming the gap lines are clearly a different color from the tile bodies. Colorblind mode is the one exception: it forces gap-seal back to the revealed color (the `::after` shape glyph carries identity instead).

Architected so hand-drawn SVGs swap in later via the same classes with zero JS rewiring. That swap is now live as **`THEME_SPRITES` in `src/ui/spriteLoader.js`** (theme -> {mine, flag, strikeCell} -> `assets/sprites/themes/<theme>-<object>.svg`): `getSpriteUrl` consults it before the Tier 1 canonical-emoji match, and a theme sprite renders ONLY when the resolved emoji equals that theme's own object emoji (always true now; kept as the identity contract between getThemeEmoji and THEME_UNLOCKS) -- undrawn themes keep their emoji verbatim. **Regression invariant + how to verify:** because every default equals the old literal, all themes are byte-identical until one deliberately overrides a token. - Database paths:
  - `daily/{dateString}/{pushId}` — leaderboard score objects (`name, time, bombHits, uid, par, timestamp, rngSeed, bombHitEvents, wormEvents`). `hintEvents` ([{t, kind}]) is a RETIRED field: the Lens that produced it was removed 2026-07-18 and no build emits it, but the rules still whitelist it (see The Lens, removed) and the R refit still filters `n_hints == 0` so historical hinted rows stay out of the fit. `rngSeed` is OMITTED when it equals the dateString (plain-date seeds) — reconstruct via `effectiveRowSeed` in `src/logic/scoreRowMatch.js` before comparing seeds. One row per (uid, effective board seed) is enforced client-side at submission — see Submission dedupe in the Canonical Daily Board section.
  - `dailyArchive/{date}/{pushId}` — replay rows for PAST dailies (the Daily Archive, see that section). Same shape as a `daily/` row plus a required `archivePlay === true` and an optional `cruxViewed` boolean. SEPARATE path from `daily/` by design so the live day-of leaderboard never shows replay rows. World-read, append-only, uid-owned (rules cloned from the `daily` block). Feeds the par fit as nuisance-corrected data; the live leaderboard ignores it.
  - `dailyMeta/{dateString}` — per-date board features (write-once, public-read) — `{ features: {...}, writtenAt }`. Read by the R refit. Written at GENERATION time by the precompute scripts (daily dates and `{weekStart}_weekly_first`) so the generator's solver counts are canonical; the first-score-submission upsert and `backfill-features.html` remain as fallbacks for dates the precompute missed.
  - `cruxes/{dateString}` — crux teaser payload for the `?crux=` share route (write-once, public-read) — `{ rows, cols, cells:[{r,c,n}], answer:{r,c}, sources:[{r,c}], walls?:[edgeKey], tier, sentence, sentenceSocratic, writtenAt }`. A self-contained "find the safe square" mini-puzzle of a PAST daily's hardest step (see Crux Teaser). Written at generation by the precompute/regenerate scripts and backfilled by `scripts/backfill-cruxes.mjs`. ~0.6 KB.
  - `boardHeatmap/{dateString}` — per-cell bomb-hit rollup for a SETTLED past daily (write-once, public-read) — `{ rows, cols, cells: { "{r}_{c}": hitCount }, totals, n_players, writtenAt }`. `cells` is SPARSE (only detonated cells) and therefore OPTIONAL in the rules: a board nobody detonated aggregates to `{}`, which Firebase stores as absent, so requiring it would reject exactly the cleanest boards. `".write": false` — no client may write here; the service-account rollup (`scripts/rollup-board-heatmap.mjs`) is the only writer (see Board Heatmap). ~0.2 KB.
  - `dailyBoard/{dateString}` — canonical board layout for the date (write-once, public-read) — `{ rows, cols, totalMines, rngSeed, codeVersion, activeGimmicks, gatedCert?, cells: [{isMine, adjacentMines, displayedMines, isLocked, isMystery, ...}, ...], wallEdges?, writtenAt }`. `gatedCert: true` marks boards certified under the reveal-gated solver contract (see No-Guess Contract); its absence means the historical ungated contract. The source of truth for "what board does today look like" — `gameActions.js`'s daily branch fetches this BEFORE local generation so every player on the same ET date plays the exact same layout regardless of cached code or experimentTarget. Written by either the GitHub Actions pre-gen workflow at 00:00 UTC or, as fallback, by the first client that loads on a fresh date. Each cell ships with both `adjacentMines` AND `displayedMines` so future changes to wall-aware adjacency or gimmick-display logic can't retroactively shift historical numbers. ~1-3 KB per day.
  - `users/{uid}/` — cloud progress sync (maxCheckpoint, dailyStreak, bestDailyStreak, lastDailyDate, `moltDay = { banked, lastUse }` — see Molt Day)
  - `users/{uid}/dailyHistory/{dateString}` — per-user completion record (`time, submittedAt`, plus `archive: true` on archive-replay rows). Written on every daily completion (and on first archive completion of a past date), read on every leaderboard-modal open for the SVG history chart and at boot for the streak reconciler (which skips archive-marked rows).
  - `users/{uid}/friends/{friendUid}` — mutual friend list entry (`name, addedAt`). Owner-only READ (lists are private). The write rule carries a deliberate exception: a stranger may write/delete ONLY the entry keyed by their own uid (`auth.uid === $friendUid`) — that is what makes one code redemption link BOTH sides. Self-friendship rejected in validate. Accepted tradeoff: anyone who learns a uid could self-insert into that list (visible in the Friends tab, removable, fine at this community's scale).
  - `friendCodes/{CODE}` — ephemeral friend codes (`uid, name, createdAt`), CODE = 6 chars of `A-Z2-9` (no 0/O/1/I/L). 15-minute life enforced SERVER-SIDE by the rules read gate (`createdAt > now - 900000`); multi-use within the window BY DESIGN (one code on a classroom projector serves the whole class); create-only-if-absent (no hijacking); anyone authed may delete (cleanup). The 3-hourly scrub workflow deletes codes older than 1h. test/friendCodes.test.mjs pins the TTL + regex against src/logic/friendCodes.js; test/friendsRules.test.mjs pins the rule structure.
- Anonymous auth (`firebaseProgress.js`): silent sign-in on load, no UI. **Test environments never MINT Auth users** (2026-07-06): `initAnonymousAuth` passes a no-op `signInAnon` into `bootstrapAnonymousAuth` when `isTestEnvironment()`, and `signOut()`'s re-anonymize in `firebaseAuth.js` carries the same gate — account creation is a production write like any other. The auth listener stays attached either way, so a persisted session is still adopted (auth persistence is origin-scoped IndexedDB, which is why `gregsweeper.com/test/` sees the prod session); a fresh test/e2e context simply plays signed out, which every uid consumer null-guards. Pinned by the smoke spec's `accounts:signUp` network assertion. `saveProgress` calls before auth completes are coalesced into a pending-save and flushed once `_ready` flips, so fast daily completions on slow connections don't drop their cloud sync. **The uid is reactive — see Account Linking below.** Modules that depend on per-user data (push subscription, daily-residuals cache, settings UI render) subscribe via `subscribeToUidChanges` so they reload when the user signs in on a second device.
- Cloud sync: saves on checkpoint advance + daily completion, loads on init. Checkpoint takes the max. Daily streak is date-anchored: cloud date > local date adopts cloud's streak AND date verbatim (even if streak went down — the most recent play has the latest info), same date takes the higher streak, cloud stale keeps local. `bestDailyStreak` is always the high-water mark. The molt-day bank + lastUse ride this same snapshot (see Molt Day) so a cross-device merge can't pair a bank with the wrong streak.
- Falls back to localStorage leaderboards if Firebase unavailable
- Security rules live in `firebase-rules.json` and are AUTO-DEPLOYED on every push to main via `.github/workflows/deploy-firebase-rules.yml`. (`firebase deploy --only database`, config in `.firebaserc` + `firebase.json`, is the manual equivalent.) The file IS the live ruleset; edits to it ship.
- **Timestamp fields validated `=== now` (e.g. `daily/*/timestamp`, `users/*/dailyHistory/*/submittedAt`) MUST be written with `firebase.database.ServerValue.TIMESTAMP`, never a client `Date.now()`.** The server sentinel is the only value that equals server `now`; a client number is silently rejected and the whole write dropped. This froze every stats page from 2026-05-25 to 2026-06-08, when commit 866683d swapped the sentinel for `Date.now()` on the dailyHistory write (to make the offline queue serializable) and the rule rejected every completion after.

## Account Linking (cross-device sign-in)
The default anonymous uid per device makes phone and PC look like two unrelated players. `src/firebase/firebaseAuth.js` adds Google and email-link sign-in so the user can upgrade the anonymous account on one device and sign in to the same identity on another — both devices then share the same uid and `users/{uid}/*` syncs automatically (streak, dailyHistory, weeklyAttempts, checkpoints, handicap).

- **Provider 1 (Google):** `linkWithGoogle()` calls `auth.currentUser.linkWithPopup(GoogleAuthProvider)`. On the first device this upgrades the anonymous account (uid unchanged). On a second device the credential is already attached to the first device's uid, so Firebase throws `auth/credential-already-in-use`; the module catches it, shows a confirmation modal (delegated to the `onCredentialConflict` callback supplied by `main.js`), then calls `signInWithCredential` to SWITCH the second device's session to the existing uid. The abandoned anonymous Auth record is `.delete()`d as part of the switch so it doesn't linger in Firebase Auth.
- **Provider 2 (Email link / passwordless):** `sendEmailLink(email)` → Firebase emails a one-time link → `tryCompleteEmailLink()` (called at boot in `init()` once auth has settled) finishes the sign-in or switch. The originating device stashes the email in `localStorage['minesweeper_pending_email_link']`; on a different device the boot flow calls the `promptForEmail` callback so the user re-enters their email (Firebase security requires the email to be confirmed on the completing device).
- **Apple sign-in is intentionally deferred.** It requires an Apple Developer Program enrollment ($99/yr), a Service ID in Apple Developer, and a private key uploaded to Firebase. Can be added later without disturbing the existing flow.
- **The uid is reactive at runtime.** `firebaseProgress.js`'s anonymous-auth init now subscribes to `onAuthStateChanged` rather than capturing the uid once. `subscribeToUidChanges(callback)` fires whenever the uid flips. Callbacks distinguish `isInitial: true` (first auth settle of the session, no in-memory state to clear) from `isInitial: false` (mid-session switch — old uid's queued writes are discarded, push token is re-minted under the new uid via `initPushAuthListener` → `refreshTokenIfStale`, and the daily-residuals cache is rebuilt from the new uid's Firebase history).
- **V1 scope is intentionally simple:** signing in on the second device ABANDONS that device's anonymous data — both leaderboard rows under the old uid and the `users/{old_uid}/*` subtree stay in Firebase but are no longer reachable from the player. The confirmation modal warns the user before the switch. No merge logic (no taking max across two uids' streaks/checkpoints, no rewriting old leaderboard rows). If we ever want merge, it's additive — add a pre-switch snapshot step in `firebaseAuth.js`'s conflict handler and write merged values into `users/{new_uid}/*` after the credential switch.
- **Push subscription handoff.** When the user signs in (uid switches), `firebaseAuth.js` first writes `users/{old_uid}/pushSubscription = null` while still authed as the old uid, so the hourly send-push cron stops firing to the abandoned device. `firebasePush.js`'s `subscribeToUidChanges` listener then calls `refreshTokenIfStale` on the new uid — if that uid has `notificationPrefs.enabled === true`, a fresh FCM token is minted and written under the new uid (overwriting any existing token), so pushes follow the player to the device that just signed in. If the new uid hasn't enabled notifications, the device stays unsubscribed until the user toggles it on.
- **Manual Firebase Console prerequisites (one-time, before this feature works):**
  - Authentication → Sign-in method → enable **Google** (no extra cost).
  - Authentication → Sign-in method → enable **Email link (passwordless sign-in)**. The action-URL is computed dynamically (`?emailLink=1` on the current origin) so test and prod both work without further config.
  - Authentication → **Settings tab** → Authorized domains → add `gregsweeper.com` (the production custom domain) and `christopherwells.github.io` (the GitHub Pages host). Anonymous auth doesn't need this (server-side credential issuance) but Google sign-in's popup-return DOES, otherwise the popup throws `auth/unauthorized-domain`. Firebase auto-adds `localhost` and `<project>.firebaseapp.com`; the serving domain has to be added manually.
  - No security-rule changes needed for V1 (the existing `users/$uid/*` and `daily/$date/$entry` rules continue to work — sign-in just changes which uid the device authenticates as).
- **Verifying via diagnostics:** the Diagnostics modal (`?debug=1` then Settings → Show Diagnostics) shows a "Signed in" row reporting provider + email. If two devices report the same uid and email, the link worked.

## Leaderboard Name Filtering (hate speech)
Two-layer filter so slurs don't reach the daily/weekly leaderboards. Scope is **hate speech only** (racial, ethnic, homophobic, transphobic, misogynistic slurs) — NOT general profanity, to keep false positives near zero.

- **Client reject** (`src/logic/nameFilter.js` + `hateSpeechTerms.js`): `setPlayerName` (statsStorage.js) calls `containsHateSpeech`, which normalizes (lowercase, leetspeak map `4→a 3→e 1→i 0→o @→a $→s …`, strip non-letters, collapse 3+ repeats to 2) then substring-matches the **client-safe** term subset (`HATE_SPEECH_TERMS_CLIENT_SAFE` — only terms that don't collide with innocent words, so a dumb `includes()` won't reject "Nigeria"/"Pakistani"/"RaccoonKing"/"SanDiego"/"Fagan"). `setPlayerName` returns `{ ok, reason }`; the Settings name input toasts "Please choose a different name" on the `change` event (not per-keystroke) and reverts to the last good name. Rejected names are never saved.
- **Server sweep** (`scripts/scrub-leaderboard-names.mjs` + `.github/workflows/scrub-leaderboard-names.yml`, cron `0 */3 * * *` + `workflow_dispatch` with a `--dry-run` input): the authoritative backstop for names written before the filter shipped, clever evasions, or direct-to-Firebase writes. Uses the **union** of two detectors — `obscenity` (boundary- + whitelist-aware matching of the **fuller** `HATE_SPEECH_TERMS` list, so colliding terms like coon/spic/paki are caught WITHOUT flagging raccoon/Nigeria/Pakistan; whitelist enumerated in the script) and the client normalizer (aggressive leetspeak obscenity's transformer misses, e.g. `tr4nny→tranny`). Scrubs offending names in every world-readable leaderboard path — `daily/{date}/{pushId}`, `weekly/{weekStart}/{uid}`, `timed/{pushId}`, and `dailyArchive/{date}/{pushId}` — to **"Anonymous"** (`test/scrubCoverage.test.mjs` derives that path set from the rules file, so a new name-bearing path can't ship unswept) (replace, not delete — the score/streak isn't the problem, the name is). The user can set a clean name anytime.
- **Term lists live in `src/logic/hateSpeechTerms.js`** — a deliberately separate, content-warned blocklist module. Two exports: `HATE_SPEECH_TERMS_CLIENT_SAFE` (low-collision, for naive client substring) and `HATE_SPEECH_TERMS` (fuller, server-only, safe because obscenity is boundary-aware). NEVER feed the fuller list to a naive substring matcher.
