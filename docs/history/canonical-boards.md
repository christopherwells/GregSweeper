## Canonical Daily Board (cross-client board agreement)
Every player on the same ET date plays the same board, period. Three divergence sources are eliminated:

1. **Code-version drift** between clients on different cached SW bundles. Same seed + different code = different board. Closed by storing the resolved board on Firebase, not the seed.
2. **Experiment-target drift** between clients with different cached `experimentTarget.json`. Same code + different target = different `selectDailyRngSeed` winner = different board. Same fix.
3. **Firebase cold-load race** where `loadDailyBoard` returns null because the Firebase SDK hasn't initialized yet, and the client silently falls through to local generation against a stale `experimentTarget.json`, different `:trialN` winner from whatever wrote the canonical, so same date but divergent board. Closed by `runStartupGate` in `main.js`, which renders nothing user-interactive until the SW is current, Firebase is ready, and today's canonical is in memory. Without this gate, a player who lost the cold-load race would silently play a divergent board (this happened to Kate on 2026-05-06 v1.5.30, the trigger for the gate).

Mechanism:
- **`dailyBoard/{date}`** in Firebase Realtime DB stores the fully-resolved board (mine layout, gimmick assignments, displayed numbers, wall edges), write-once at the rules layer.
- **`getLocalDateString()`** is anchored to America/New_York via `Intl.DateTimeFormat('en-CA', { timeZone: 'America/New_York' })`. A player in Tokyo loading at 9am JST sees the puzzle for the previous ET date if it's still before midnight ET.
- **`src/firebase/dailyBoardSync.js`**, `loadDailyBoard(date)` / `saveDailyBoard(date, payload)` / `serializeBoard({ board, rows, cols, ... })` / `deserializeBoard(raw)`. Both load and save now go through `waitForFirebaseReady` (50ms-poll up to 8s) so a cold-load race can't make them silently no-op. The serialiser drops `false`-valued booleans to keep the JSON tight (~30% smaller), and the deserialiser fills them back in from defaults so the consuming code sees a fully-shaped cell object.
- **Startup gate (`runStartupGate` in `main.js`)**, runs before `init`'s routing branch, behind the `#boot-overlay` div in `index.html`. Three steps: (1) `ensureLatestServiceWorker`, `registration.update()` and wait up to 3s for any new SW to activate (controllerchange handler in `<head>` reloads us if it does), (2) wait up to 8s for `firebase.apps.length > 0` and stash the result in `state.firebaseReady`, (3) pre-fetch `loadDailyBoard(today)` into `state.canonicalDailyBoard = { date, raw }`. Practice loads (`?seed=`) skip step 3. Boot overlay only hides at the END of `init` (after routing + first newGame await), so the player never sees a flash of a wrong board.
  - **Everything the boot path awaits must be BOUNDED, and `init().catch` does not help** (2026-08-07, his "it won't load on loading screen" report). The overlay comes down only at the end of `init`, and the `.catch` safety net at the bottom of main.js catches a THROW, a hang is not one, so a promise that never settles strands the app on the loading screen with nothing logged. Two shapes have shipped, both pinned by SOURCE SCAN in `test/bootHang.test.mjs` because neither is reproducible at a cheaper layer (one needs a socket that accepts a read and never answers, the other a browser that refuses storage writes): (1) **Realtime DB's `once('value')` has no timeout of its own**, on a half-open socket (a phone waking from sleep, a captive portal, a dropped wifi handover) it never settles. Every board/progress read was already `Promise.race`d; the gate's completion-reconcile read was the one that was not. (2) **A throw inside a `setTimeout` callback does not reject the promise the callback was meant to resolve**, it escapes as an uncaught error and `resolve` is never called. The live hazard is `sessionStorage`, which throws on WRITE in a storage-restricted context (Safari private browsing, a locked-down PWA container), inside the iOS `reg.waiting` forced-reload block that exists precisely for that platform.
- **Daily entry path** (`gameActions.js` daily branch, `async`): read `state.canonicalDailyBoard` first; if it exists and matches `state.dailySeed`, deserialize verbatim (skip generation, gimmicks, solvability retry). Fall back to a fresh `loadDailyBoard` call only when the cached canonical is for a different date (tab open across midnight) or when the gate's fetch failed. If both miss, the live daily ABORTS rather than local-generating (the divergence block below), which leaves the old fire-and-forget `saveDailyBoard` fallback write unreachable on the live lane; only `?seed=` practice still runs the local-generation flow, and practice never writes the shared bucket. The solver still runs locally on the resolved board to compute features (move-type counts) and the best-start cell, that's deterministic, so different clients agree on features even if they came in via different paths.
- **Completion ↔ cloud reconciliation** in `runStartupGate` (one TIMEOUT-RACED `daily/{today}` read, both directions; row matching via the pure `src/logic/scoreRowMatch.js`, node-tested). **The lock's question is "has this ACCOUNT finished TODAY'S BOARD", which is NOT the streak's "did it play a daily today"**, those came apart on 2026-08-07 when a divergent board could count for the streak while its score was refused, and every symptom below is that conflation. (a) Local "completed" flag set + this account has NOT finished the canonical → unlock the replay. Three signals, cheapest first: the **board seed this device recorded** with the completion; then the account's cloud row being POSITIVELY divergent (truthy `rngSeed` ≠ canonical); then the one-time **vintage unlock**. A missing row alone still never clears (a player with no name set, or one whose submit is queued offline, legitimately has none, clearing on missing-score used to let raced uid lookups unlock replays). (b) Local flag unset + a cloud row matching the canonical's effective seed → ADOPT the completion (`markDailyCompleted(today, canonicalSeed)` + drop any in-progress daily save), so finishing the daily on one device marks it completed on every device sharing that account. The `?mode=daily` deep link gates on `isDailyCompleted` like the Daily card (a notification tap can't relaunch a completed daily). Skipped on the test env and for `?seed=` practice.
  - **The completion RECORDS ITS BOARD** (`minesweeper_daily_completed_seed`, written by `markDailyCompleted(date, seed)` from the same `state.dailyRngSeed || dateStr` expression the score row uses). Before this the only record of which board was finished lived in the cloud score row, and the submit guard (#252) stopped writing that row for **exactly the divergent case the unlock reads**, so the guard silently removed its own remedy: a player who played a divergent board was marked completed, refused at submit, and locked out of the real board for the rest of the day with no signal anywhere that could free them. An ABSENT seed means a completion predating this (UNKNOWN), never "played the canonical".
  - **The unlock has to be STICKY** (`unlockDailyReplay` → `minesweeper_daily_replay_unlocked`), because `applyCloudProgress` re-derives the lock from the cloud's `lastDailyDate` and the progress listener re-applies the cloud on EVERY write under `users/{uid}`, a `lastSeen` beacon is enough. A plain clear survives milliseconds, which means **the documented divergent-replay unlock had been dead well before the submit guard landed**. `applyCloudProgress` now defers to the marker; `markDailyCompleted` and the account-switch reset both retire it. `unlockDailyReplay` also drops the date's cached par/moves/features (they describe the wrong board), so the boot gate and the at-submit unlock cannot disagree about what a replay resets. Pinned in `test/dailyReplayUnlock.test.mjs`.
  - **The VINTAGE unlock is one boot, ever** (`minesweeper_daily_vintage_unlock_done`), for completions recorded before the seed was stored: local record for today with no seed AND no row for this account on today's board → unlock. "No row" is deliberately a weak signal, which is why it is spent once and never becomes a standing rule; anyone who really did play the canonical is re-locked immediately by `adoptCompletion`, whose row match is the precise test. Verified against live production data before shipping.
- **The at-submit unlock** (winLossHandler's `'divergent'` branch): the moment the client LEARNS the board was wrong is the moment to give the real one back, rather than waiting for the next boot. Writes `dailyHistory` (the day counts, his constraint, "I don't want people losing their streak, but I also don't want bad data") and calls `unlockDailyReplay`.
- **Submission dedupe** in `_doSubmitOnlineScore`: before pushing, read the date's rows and skip the push (returning `'duplicate'`, a third outcome alongside `true`/`false`) when this uid already has a row for the SAME effective board seed. Matching is per BOARD, not per uid: rows omit `rngSeed` when it equals the dateString, so the effective seed is reconstructed (`effectiveRowSeed`), practice rows can never block the real daily, and a divergent historical row doesn't block a canonical replay. First completion wins: callers toast "Already on the board from another device" and skip the `dailyHistory` write on `'duplicate'`; the offline retry queue treats `'duplicate'` as resolved (covers the offline-race where another device submits before the queue flushes). Both submit paths (auto in winLossHandler, manual in main.js) anchor the score's date to `state.dailySeed` (the board's date), so a finish at 12:00:01 AM lands on the board's own leaderboard.
- **Resume eligibility** (`src/logic/resumeEligibility.js`, pure + node-tested; consumed by `tryResumeGame` in `src/game/gamePersistence.js`): a persisted save resumes only if (a) its `gameMode` matches the slot it was loaded from, (b) a daily save carries BOTH `dailySeed` and `dailyRngSeed` and the seed equals today's ET date (practice `?seed=` equals its custom seed instead), (c) the save's `dailyRngSeed` matches the canonical board's when one is cached for that date (divergent-canonical drop), (d) a weekly save carries full identity (`weeklySeed`/`weeklyDay`/`weeklyRngSeed`) matching the live ET clock, and its `weeklyRngSeed` matches the cached weekly canonical's when one is stashed (the daily's divergent-canonical drop, extended to the weekly 2026-08-07), (e) cells have `row`/`col` (v1.5.19 corruption check), and (f) any explicit `cellNeighbors` topology on the save still validates (right length, in range, symmetric, a corrupt one would restore a board whose adjacency disagrees with the one it was certified under). Date anchors compare against the CLOCK (`getLocalDateString`/`getWeekStart`/`getWeekDayIndex`), never against live state fields, a session that survives midnight ET carries yesterday's seeds in state. Saves missing their seed identity are REJECTED, not waved through: the pre-fix Daily card handler nulled the live seeds before `switchMode` persisted the outgoing game, and those fingerprint-less snapshots resumed yesterday's board as "today's" daily (found 2026-06-12).
- **Date-rollover discipline (2026-06-12):** daily/weekly identity is derived inside `newGame` from the ET clock (practice keeps its caller-set seed via `isDailyPractice`); the mode-card handlers no longer pre-set identity fields before `switchMode` (mutating identity before the outgoing game is persisted forges or strips the snapshot's fingerprint, the root cause above). A live session that sleeps through midnight (background tab, suspended PWA) is caught by `expireRolledOverGame` in `main.js` on `visibilitychange → visible`: `isLiveGameExpired` (same pure module) checks the live game's date anchor against the clock; on expiry the persisted save is cleared, `state.status = 'expired'` (persist only writes playing/idle, so the dead game can't re-save), and the player lands on the title screen with a toast. Actively-visible play across midnight is deliberately NOT interrupted, finishing keys under the board's own date.

- **Board cache is network-first with cache fallback** (`loadDailyBoard`/`loadWeeklyBoard` + `src/firebase/boardCache.js`): while online, every load fetches the canonical and refreshes the local copy (~2KB); offline, the cached copy keeps daily/weekly playable. The cache is deliberately NOT authoritative, an admin regeneration can replace an unplayed future board, and a blindly cache-first client that had prefetched the old layout would play a divergent board on the day. Server-reachable-and-empty returns null (no resurrection of deleted canonicals); admin deletions must always be followed immediately by a rewrite.
- **`canonicalStringify` normalizes the Firebase round-trip, because signing a value the database discards breaks every signature whose payload includes one (issue #143, closed 2026-07-27).** Realtime DB has no empty node: writing `[]`, `{}` or `null` to a child path DELETES that child. `serializeBoard` sent `activeGimmicks: []` for a gimmick-free daily, so the payload that came back was not the payload that was signed, verification returned false, and `gateCanonicalTrust` rejected a legitimate canonical as tampered, which makes every client fall back to LOCAL generation on that date, reintroducing exactly the cross-client divergence the canonical architecture exists to eliminate, and simultaneously wedges the nightly sweep on a false positive with no working remediation. It went live on `dailyBoard/2026-08-03`, a DECORRELATION-mission board: that mission rolls the natural gimmick lottery rather than force-injecting, and an unforced roll is gimmick-free about half the time, so decorrelation nights raise the rate of gimmick-free dailies sharply. The fix is at the substrate, `canonicalStringify` drops the same values Firebase drops, bottom-up so a container emptied by its own children goes with them, so the signed string is invariant under storage for every field, present and future, instead of each new field having to remember to be omitted-when-empty. `serializeBoard` also omits an empty `activeGimmicks` now (like `wallEdges`/`gatedCert`), keeping the written payload honest about what lands. Two rails: non-finite numbers count as dropped (`JSON.stringify` renders NaN/±Infinity as `null`), and `signCanonicalPayload` THROWS via `unstorableShapeReason` on a shape storage cannot return unchanged, an empty at an ARRAY-ELEMENT position, which RTDB turns into a sparse object rather than a shorter array. The verifier stays TOTAL and never throws, because `gateCanonicalTrust` fails OPEN on an exception and a throw there would TRUST a malformed board. Verified a no-op on production: the signed string is byte-identical on all 166 stored canonicals, so no existing verdict moves.
- **Canonical-board signatures (the #114 trust-model close, 2026-07-05)**: every pipeline-written `dailyBoard`/`weeklyBoard` carries a `sig`, ECDSA P-256 over `canonicalStringify(payload)` (recursively key-sorted JSON, `sig`/`writtenAt` excluded, empty/non-finite values normalized away, see the #143 bullet above), private key ONLY in the `CANONICAL_SIGNING_KEY` Actions secret (precompute daily/weekly + regenerate daily/weekly + bootstrap all sign; each THROWS without the key). Clients verify BEFORE playing via `gateCanonicalTrust` in dailyBoardSync (applied to network AND cached copies in `loadDailyBoard`/`loadWeeklyBoard`; an untrusted canonical is treated as MISSING → local-gen fallback + reportCaughtError, and is never cached). Trust policy in `src/logic/canonicalSignature.js` (`assessCanonicalTrust`, node-tested): key date < `SIGNATURE_EPOCH` (2026-07-06) → grandfathered unsigned; signed → must verify (an invalid sig is affirmative tamper evidence, rejected outright); unsigned post-epoch → trusted ONLY when `writtenAt` (rules-validated `=== now` on a write-once path, so unforgeable) falls inside the board's own play window (the daily's ET date; the weekly's Mon..Sun), exactly the first-client-fallback shape, so convergence on precompute-failure days survives while a pre-poisoned future board (writtenAt before its window) is rejected. Verifier-machinery EXCEPTIONS fail open with a report (a browser quirk must not brick a legit daily; attackers can't trigger exceptions, only clean `false`s). Key rotation is additive: new pair, replace the secret, prepend the SPKI to `PUBLIC_KEYS`, the epoch never moves. The `sig` child is whitelisted in both rules blocks.
- **Nightly integrity sweep** (`.github/workflows/verify-canonical-boards.yml`, 00:30 UTC + dispatch; `scripts/verify-canonical-boards.mjs`, read-only over world-readable paths, no secrets): the DETECTION layer for the #114 poisoned-canonical vector (canonical paths are write-once but anon-writable, and clients play them verbatim). Re-verifies every FUTURE-dated dailyBoard (+ dailyMeta + crux) and every current/future weeklyBoard: clean deserialization, mine count === totalMines, byte-identical recompute of the adjacency + displayed-number layers (liar offsets are stored, so recompute is deterministic), and center certification under the board's own gatedCert contract, the generator's exact acceptance. dailyMeta feature keys must match a recompute EXACTLY unless `computeDailyFeatures` declares them solver-derived, in which case they warn (legit drift when a solver change lands mid-horizon); crux payloads must be SOUND (a provably safe cell follows from their own numbers, and the claimed answer is among them, version-independent). Post-epoch FUTURE canonicals must additionally carry a VALID `sig` (`verifyFutureSignature`, the unsigned fallback shape is written same-day, never ahead, so an unsigned future board is poison or a pipeline that lost its signing key). Any failure exits non-zero, so the failed workflow run is the alarm, days before the board reaches players; remediation (the regenerate workflows) is printed in the log. Tamper classes pinned in `test/verifyCanonicals.test.mjs` + `test/canonicalSignature.test.mjs`.
  - **Structural is the DEFAULT, and an ALLOWLIST is what made two guards silently inert (issue #180, closed 2026-07-27).** The sweep used to hard-fail only the feature names on a hand-written `STRUCTURAL_FEATURE_KEYS` list, which failed twice over in one stroke: two entries named `wormholeCellCount` / `mirrorCellCount` while `computeDailyFeatures` emits the PAIR counts (a player reasons about a pair), and because the comparison loop iterates the RECOMPUTED keys those dead names matched nothing while both real modifier counts fell through to WARN-only on a green workflow. Every structural feature the list just never mentioned was unguarded the same way, `density`, `gimmickTypeCount`, `nonZeroSafeCellCount`, `zeroClusterCount` (a SHIPPED par predictor) and the four `clueShare*`. The list is GONE. `dailyFeatures.js` exports `SOLVER_DERIVED_FEATURE_KEYS`, the producer declaring which of its own outputs depend on the `solverResult` argument, and the sweep imports it and hard-fails everything else, so a structural feature added tomorrow is guarded the moment it exists and the cost of mis-tagging is a loud false alarm rather than a silent hole. The membership is pinned by DIFFERENTIAL, not by eye (`test/dailyFeaturesClassification.test.mjs`): the vector is computed twice over one board with two different solverResults and exactly the tagged keys must move, so a dead name cannot survive and a newly solver-fed key cannot hide.
  - **Inverting that default collides with the precompute HORIZON, which is why `FEATURES_EPOCH` exists.** `dailyMeta/{date}` is write-once and the pipeline writes seven days ahead, so for a week after any new feature key ships, every future board in flight carries a meta that legitimately lacks it. The old value-based hatch (`stored === undefined && recomputed === 0`) covers a PLACEMENT feature like `wormLoad`, which recomputes 0 on a board that does not carry it, but NOT a DERIVED one: the clue shares recompute nonzero on essentially every board, and measured against the live database an absence-hard-fails rule reddens `dailyMeta/2026-07-19..22` on `clueShare2: stored undefined`, printing a remediation that would regenerate four perfectly good boards. So an absent key is vintage when the recompute is 0 **or** when the meta's own rules-validated `writtenAt` predates `FEATURES_EPOCH` in `verify-canonical-boards.mjs`; anything else is lying BY OMISSION and still hard-fails, which is what stops a poisoner zeroing a feature by leaving it out. **Bump `FEATURES_EPOCH` in the same commit as any new feature key**, forgetting reddens the nightly for up to a week on legitimate boards, which is loud and self-announcing, the safe direction to fail. A change to an existing feature's DEFINITION (not its existence) is deliberately NOT excused: the pre-written horizon then carries numbers the current code disagrees with, clients compute par from the STORED features, and the alarm saying so is correct, regenerate, or wait out the horizon.
  - **The sweep is future-dates-only, so running it over HISTORY reported 64 alarms that were all benign**, and that is exactly how a real failure gets lost. Both classes are now named rather than tolerated: (1) `verifyMetaAgainstBoard` takes the date and reports anything before `CANONICAL_ERA_START` (2026-04-27, exported from `archiveEligibility.js` and cross-checked against the refit's `DIGIT_ERA_START`) as PROVENANCE, before canonical storage existed the board was regenerated by `backfill-old-dailies.mjs` while the meta still describes the per-device board actually played, so the two describe different boards by construction. The META is the record that matters there: score rows join to it, so the par fit reads a consistent meta+score pair and only the canonical is the imposter. Omitting the date keeps the old strict comparison, so this is opt-in, not a global relaxation. (2) The 15 `dailyBoard` failures were all ONE defect, see the repair below.
- **Stale mine adjacency (`scripts/repair-mine-adjacency.mjs` + `repair-mine-adjacency.yml`, dispatch-only, dry-run default).** The invariant is "a mine carries no number, so its `adjacentMines` is ALWAYS 0". - **DIVERGENT SCORES ARE NOW PREVENTED, DETECTED AND REMEDIABLE (2026-08-07).** Two real divergences had sat unnoticed, one for two months, because divergence was only ever checked at BOOT. `startupReconcilePlan` spots a divergent row and unlocks a replay, which is right, but by then the row is written and joined against the wrong feature vector in the par fit. Three layers now:
  - **Prevention at submit.** `_doSubmitOnlineScore` reads `dailyBoard/{date}/rngSeed` beside its existing dedupe read and returns a new `'divergent'` outcome on a mismatch, so the row never reaches the leaderboard. It fails OPEN on a read error, exactly like the dedupe, a flaky read must never eat a real score. **The win path still writes `dailyHistory` on that branch**, which is the whole design: streaks read `users/{uid}/dailyHistory` and leaderboards read `daily/`, so the DAY counts and only the comparison is refused (his constraint: "I don't want people losing their streak, but I also don't want bad data").
  - **A harder startup gate.** One empty read is not proof the canonical is unavailable, and falling through to local generation is not graceful degradation for a daily, it is near-certain divergence, because the canonical is precomputed up to SEVEN DAYS ahead against the experiment target of that moment while the nightly refit rewrites that file underneath it, so a client re-deriving the day's board draws from a differently-sized candidate pool. (That is how a 2026-08-06 player landed on `:trial6` against a `:trial13` canonical: the pool is 16 slots on a decorrelation night and 6 otherwise.) The gate now retries twice with linear backoff INSIDE the `firebaseReady` branch, and only when `navigator.onLine` is not false (trusted negatively only), so an offline boot never pays a retry budget that cannot land; a recently-synced cache still serves the board offline, and with no cache the daily aborts (next bullet). **WHICH failures it retries is the part that had to be got right (issue #255, fixed 2026-08-10).** A canonical read returns null for four reasons and only ONE can improve on a second look, so the loop was spending its budget on the two that provably cannot: a date the server says is EMPTY answers the same way next time, and an UNTRUSTED payload returns the same bytes. `loadDailyBoardResult` / `loadWeeklyBoardResult` are reason-carrying siblings of the plain loaders (which keep their signature, nine callers want a board or nothing), classifying through the shared `canonicalReadReason`, and the pure `src/logic/canonicalRetry.js` owns the decision. **The budget is now WALL-CLOCK and checked BEFORE each attempt**, never raced against one in flight, since truncating a read that was about to land would defeat the retry's whole purpose: that bounds the loop at the budget plus at most one fetch timeout (~5.5s), where the attempt-count version allowed `retries × FETCH_TIMEOUT_MS` = 11.5s while its own comment promised "about a second and a half". A cheap failure still gets both attempts, the bound is on time, not tries. `weeklyCanonical.js` names this same ambiguity from the other side and works around it via the WRITE; that workaround is still correct and untouched.
  - **The live daily no longer falls back to local generation at all** (his ruling 2026-08-07, after his own client generated locally and lost the score). `newGame`'s daily branch aborts when no canonical resolves, same rule the archive path has always had, and the right precedent: a board that cannot be verified is not offered. This does NOT require a network (`loadDailyBoard` is network-first with a cache fallback and the boot prefetch pulls a week of boards, so a recently-opened offline client still gets the REAL board); what is gone is INVENTING one. The abort sets `state.status = 'aborted'` and clears the daily slot, because `newGame` has already installed an empty placeholder board stamped with today's identity and status `'idle'`, which `persistGameState` DOES write, and `pagehide`/`beforeunload` call it unconditionally, so without it the failed attempt could be saved and later resumed as a mine-free "today's daily". `revealCell` refuses `'aborted'` for the same reason (the placeholder is on screen for a frame or two before the title screen swaps in, and cascading a mine-free grid would satisfy the win check against a stale `totalMines`). **The residual, stated:** the first-client fallback for `dailyBoard` is now gone for the daily, so a precompute outage lasting longer than the 7-day horizon would leave the daily unplayable rather than divergent. That is the loud failure over the silent one, and the horizon makes a single failed night a non-event.
  - **The WEEKLY was the unguarded twin, closed the same arc (2026-08-07, v1.10.14/15).** Its submit path now runs the daily's check: `_doSubmitWeeklyScore` reads `weeklyBoard/{weekStart}/rngSeed` directly and refuses a mismatch (a week's whole leaderboard is ONE board, so a divergent row is not a slower time on the same puzzle, it is an incomparable time on a different one), and the `{weekStart}_weekly_first` FIT row is checked against the WEEKLY canonical via `canonicalSeedPath`, whose predecessor read `dailyBoard/{weekStart}_weekly_first/rngSeed`, a node that does not exist, so the fit-row guard had silently no-oped on every weekly fit row ever submitted. Both submit paths decide through the pure `src/logic/submitGate.js` (`planScoreSubmission`, behaviorally tested in `test/submitGate.test.mjs`; the decision was extracted because a verdict buried in an async Firebase call is a verdict nobody can test): both reads FAIL OPEN (null is "unavailable", never "mismatch", so an outage cannot silently drop real scores), and `'divergent'` is RESOLVED, never queued, since the board will still be wrong on the next flush. The played seed rides the weekly row on BOTH write shapes, the `update()` map and the first-write `set()` payload; on only one it would be absent for half of all players, and an absent seed reads as "nothing to check". `test/rules-contract.test.mjs` DERIVES the weekly whitelist from the writer, so a new row field cannot silently drop the whole write (the 866683d class). A weekly save whose `weeklyRngSeed` mismatches the cached canonical's is dropped at resume (resumeEligibility), and the startup gate retries the weekly canonical CONCURRENTLY with the daily on the same reason-carrying terms, because the weekly's blast radius is wider: the fallback below can establish the week for every player, and a weekly attempt is one of only seven. **The local-gen fallback SURVIVES BY RULING and is the deliberate asymmetry with the daily** ("a week with no canonical at all is worse than a week whose canonical came from the first player through the door"): the writer stays as the precompute-failure recovery, but the write's ANSWER is now read. A write-once REFUSAL is the server saying a canonical already exists, the one thing a read alone cannot establish (null means both "empty" and "unreachable"), so the client re-reads and PLAYS the settled canonical instead of its own board (`weeklyLocalGenPlan` in `src/logic/weeklyCanonical.js`, node-tested in `test/weeklyCanonical.test.mjs`; a settled payload that will not deserialize is not a reason to drop the playable board already in hand). The residual, stated: a genuinely offline client still plays its deterministic local board, and the submit guard settles the comparison whenever the score finally travels.
  - **Nightly detection.** `verify-canonical-boards.mjs` swept FUTURE dates only; it now also compares every score row since `CANONICAL_ERA_START` against its canonical and exits non-zero, across all THREE row families: `daily/` day-of rows, the `{weekStart}_weekly_first` fit rows (matched to the WEEKLY board via the same `canonicalSeedPath` the submit guard uses), and `weekly/` leaderboard rows, with weekly rows that predate the seed's recording counted and REPORTED as unverifiable rather than assumed clean. The era floor is what makes it an alarm rather than noise: every board before that date was regenerated by `backfill-old-dailies.mjs`, so 91 of the ~94 divergent rows disagree BY CONSTRUCTION. It REPORTS and never deletes, deleting player data on a schedule is fine until a canonical is itself wrong, and a scan that throws is reported as UNKNOWN rather than clean, which was a real trap: the first cut printed the same "no divergent rows" line whether it had scanned or crashed. Pinned in `test/divergenceGuards.test.mjs`; the detector was break-tested (274 rows found when every canonical seed was forced to mismatch, exit 1).
