## Board Topology (the solver is geometry-blind)

A board's adjacency is a GRAPH, not a geometry, and `src/logic/adjacency.js` is the single place that answers "what touches what". Two boards can share the same `rows`/`cols` container and have completely different neighbor structure. There are two ways a board declares its topology, and `buildNeighborCache(board, rows, cols)` returns the same data shape for both, so no consumer can tell them apart: `Array<number[]>`, outer length `rows*cols`, outer index `r*cols+c`, inner entries flat neighbor indices, no self, no duplicates, symmetric.

- **Implicit** (every board shipped today): the rectangular 8-neighborhood minus wall-severed edges, derived on demand from `rows`, `cols`, and `board._wallEdges`.
- **Explicit** via `board._cellNeighbors`, stamped by `defineCellNeighbors(board, rows, cols, adj)`: when present it IS the topology, full stop. `rows`/`cols` degrade to pure container indexing (the cell list reshaped, so `(row, col)` says nothing about what a cell touches) and walls do not enter, because a severed link is just absent from the list.

`defineCellNeighbors` VALIDATES before stamping, bounds, no self-loops, no duplicates, and above all SYMMETRY. An asymmetric edge list does not crash; it quietly certifies a board that nobody can solve, because one cell's clue counts a mine the mine's own neighborhood does not count back. Validation runs at construction and on restore from a save, never in a hot loop; `isValidCellNeighbors` is the boolean form for deciding whether to TRUST a topology that arrived from outside the process.

**An explicit topology rides the game save as its own top-level `cellNeighbors` field**, exactly as `wallEdges` does and for the same reason: the snapshot is JSON, and `JSON.stringify` drops properties stamped on the board ARRAY. Without it a tiling game saved and resumed came back RECTANGULAR mid-play, the board's shape silently changing under the player, with the adjacency it was certified under gone (found in the Phase 1 adversarial review, fixed the same day). `isSaveResumable` REJECTS a save whose topology fails validation rather than restoring a corrupt one, and `tryResumeGame` re-stamps through `defineCellNeighbors` before anything reads the board. Ordinary rectangular saves emit `null` and are unaffected. Pinned in `test/persistRoundTrip.test.mjs` and `test/resumeEligibility.test.mjs`.

**Walls are baked INTO the neighbor list rather than consulted alongside it.** `hasWallBetween`'s diagonal rule synthesizes the four orthogonal edges of the 2×2 block a diagonal crosses, which is irreducibly rectangular; on a non-rectangular topology there are no diagonals to disambiguate, so a severed link is just a missing edge. This is why re-keying `_wallEdges` from `"r,c-r,c"` to index pairs was considered for Coastline and REJECTED (Christopher, 2026-07-19): it would not have bought geometry-neutrality, and the string format is a stored contract, it lands in the signed bytes of every canonical `dailyBoard`/`weeklyBoard`, in every `cruxes/{date}` payload, and in every in-flight save. Changing it silently UN-WALLS every board already written (a lookup builds a key the stored Set does not contain and finds nothing, which reads as "no wall" rather than as an error). The nightly sweep would catch future dates loudly and never touch past ones, so Archive replays would get wrong par and a false Certified chip with no test firing.

**Coastline Phase 1 (2026-07-19) proved the no-guess contract transfers off the square grid.** `isBoardSolvable` needed NO changes: inside it, `cols` is only ever CONTAINER indexing, the `idx = (r,c) => r*cols+c` closure, a `preFlagCells` bounds check, and row-major setup loops, and never expresses adjacency, while `rows*cols` is always a pure cell count. The deduction core already ran on flat indices plus a neighbor list. Handing it an explicit topology is the whole port. The gate is `test/tilingCertification.test.mjs` against `test/fixtures/tiling488.mjs`, a 4.8.8 truncated-square tiling (octagons + interstitial squares, valences 3/4/5/8, and crucially diagonal octagons do NOT touch since a square sits between them). The fixture certifies at techniqueLevel 2, so tank/gauss enumeration runs on non-rectangular adjacency, and a RECTANGULAR control over the same mine layout must NOT reproduce the result or the gate would be vacuous. Phase 2 (2026-07-21, PR #176) PROMOTED the tiling builder from `test/fixtures/tiling488.mjs` into `src/logic/tilingGeometry.js` (topology + per-cell geometry + polygon vertices + wireframe, a LEAF module) and `src/logic/tilingGenerator.js` (seeded certified no-guess boards); the fixture now imports it. Phase 2 is MERGED to main but GATED, the tiling surface (renderer + all modifiers) is reachable only via the `isTestEnvironment()`-gated `?coastline=<modifiers>` deep link, UNREACHABLE in production (no card, no mode, no rotation). What Phase 1 left rectangular has since been converted:
- **Compass's ray, RESOLVED in Phase 2.** A compass is not a topological property: sonar asks "how far", which a graph answers, but a compass asks "which way", which needs geometry `_cellNeighbors` does not carry. So Phase 2 computes the ray from cell POSITIONS at generation (`computeCompassRay` in tilingGeometry.js, 8 directions incl. diagonals) and STORES it per cell; `compassRayCells` returns that stored list on an explicit topology (it THREW in Phase 1). Display (`recomputeDisplayedMines`) and certifier (`buildStaticGimmickConstraints`) read the identical stored ray, so they can never disagree about a geometry neither of them computes. Christopher chose diagonal rays after seeing a rendered sketch (it is a see-it decision). `buildStaticGimmickConstraints` emits nothing for a board with neither sonar, compass nor wormhole, which is why a plain tiling needs no solver edit at all.

**Tiling #2 is the 6.6.6 regular honeycomb (2026-07-22), and adding a tiling is now a DISPATCHER call rather than a fork.** Christopher chose hexagons over kagome / 3.12.12 / 4.6.12 after a rendered comparison of the candidates. The decisive constraint was LEGIBILITY, which is also the durable selection rule: a number plus a modifier watermark has to fit in EVERY cell, so the seven Archimedean tilings that contain triangles are all disfavored (a triangle is the hardest host there is, and 4.8.8's interstitial square already had to be tuned up via `OCT_CUT`). A honeycomb is one shape at one size with every cell large, and it is the other major lattice symmetry (6-fold against 4.8.8's 4-fold), so the two shipped tilings read as different worlds rather than variations. Its own adjacency surprise is that **a hexagon has no diagonals at all**, all six neighbors are edge neighbors, interior valence is a constant 6 (against 4.8.8's mixed 3/4/5/8), so the corner-touch ambiguity every rectangular assumption is built around does not exist.
- **One descriptor, one dispatcher.** `buildTiling(type, M, N)` in tilingGeometry.js routes through the `TILING_BUILDERS` lookup, and every builder emits the SAME shape: `{adj, cellPos, cellVerts, verts, wUnits, hUnits, centerIndex, type}`. `generateTilingBoard` takes a `type` (default `'4.8.8'`) and opens on `centerIndex`; `applyWallsTiling` rebuilds the wireframe through the dispatcher from `board._tiling.type`. Those two were the only places hardcoding `buildTiling488`, and the prediction that another tiling would cost a builder plus a clip-path is what the four Laves tilings below tested (it held for the topology and the generator; the renderer needed one generalization, and the compass needed a per-lattice table). **An unrecognized type falls through to the 4.8.8 rather than throwing**, the generator's own default depends on that, so any caller taking a type from OUTSIDE the code must validate against the exported `TILING_TYPES` first. With six types that fallback is a real hazard rather than a theoretical one: a typo produces a plausible board with no error anywhere.
- **The renderer is extent-driven, not cell-count-driven.** `board._tiling` carries `wUnits`/`hUnits`, the tiling's extent in PITCH UNITS, because a honeycomb is WIDER than N (odd rows offset half a hex) and SHORTER than M (rows overlap vertically at 1.5R), so N×M pixels would be wrong in both axes. `_renderTilingBoard` picks a clip-path per `cellPos.shape` (octagon / diamond / hexagon), and the hex box is one pitch wide by `HEX_BOX_H` (2/√3) tall, centered on the cell center so the number lands dead center. Boxes of neighboring hexes OVERLAP while the clip-paths tile exactly, which is also what makes pointer hit-testing land on the right hexagon. `_renderTilingWalls` now anchors on `cellPos[0]`'s own center instead of assuming a P×P box centered at unit (0.5, 0.5), a hex box is taller than it is wide, so the old anchor would have offset every hex wall vertically.
- **What actually needed hexagon-specific code, and what did not.** Sonar (depth-2 graph BFS), worm (walks the neighbor graph with positional momentum), mystery, liar, locked, mirror and walls needed ZERO change, they are topology- or position-generic already. Only the COMPASS did: a honeycomb has six usable straight lines of cell centers, not eight, so `COMPASS_DIRS_60` (named `COMPASS_DIRS_HEX` until rhombille turned out to share it verbatim) is the six hex axes and there is deliberately **no due-north/south ray**. `computeCompassRay` gained a tolerance because hex row spacing is √3/2 and colinearity is therefore only exact to floating point; the nearest OFF-axis cell sits ~0.4 away in cross-product terms, orders of magnitude above float error, so it cannot misclassify, and display and certifier read the same STORED ray regardless, so any ray it returns is self-consistent.
  - **The vertical ray is excluded for a measured reason, and it is NOT the one this file and the code comment used to give.** Both claimed no column of centers runs vertically on a pointy-top lattice. That is just false, in odd-r offset, rows *i* and *i+2* share `cx`, so the column exists and a vertical ray reaches something from 77 of 121 origins. The real reason is that the column runs along the shared VERTICAL EDGES of the row in between: only **66.3%** of the drawn line lies inside cells the number counts, and **not one step of it lands on a cell touching the last**, so a player cannot follow the arrow. Same for 30/150. That is the measurement every direction set is now judged against, the metric is the share of the drawn line inside counted cells, the shipped 4.8.8 diagonals score 100%, its axes 90.4%, and 66.3% is the reject side of the bar.
- **The gate.** `test/tilingCertificationHex.test.mjs` runs the shipped, unmodified certifier over a frozen 7×7 honeycomb (49 cells, 9 mines) and it certifies at techniqueLevel 2, Pass A, generic subset AND tank/gauss all running on hexagonal adjacency, while the RECTANGULAR control over the same mine layout is UNSOLVABLE, stalling on the first click. Holding the control to "unsolvable" rather than merely "different" is what keeps the gate non-vacuous; pick fixtures that way for future tilings.
- **The tiling layout re-runs on every pitch change (2026-07-22).** A tiling cell carries INLINE pixel left/top/width/height derived from its unit-pitch geometry, so unlike a rectangular cell (which reads `var(--cell-size)` through the CSS grid and reflows for free) it is frozen until something re-lays it. `layoutTilingCells()` is that pass, split out of `_renderTilingBoard` and called by `resizeCells`; re-laying rather than rebuilding is deliberate, since a rebuild would drop keyboard focus, restart the cascade animation, and detach the wall/worm overlays' reference cell. Before this, a resize or phone rotation recomputed the pitch and threw it away, the board stayed frozen at its old size and, once the viewport was narrow enough, was WIDER than its own container. Pinned by `tests/e2e/tilingResize.spec.mjs` (ALL SIX tilings, rotation + shrink + grow-back), which was break-tested against the un-fixed renderer. Two of its assertions were rewritten when the Laves tilings landed, both because the originals only worked on a TALL board. It asserted the pitch SHRINKS on rotation to landscape; rhombille and deltoidal are wide and short, so landscape hands them more room and their pitch GROWS (measured 26→35 and 27→33). The invariant that holds for every shape is that the board's box stays PROPORTIONAL to the pitch, `boardW/pitch` is a constant of the tiling, and that is strictly stronger: with the re-lay disabled, all six fail where only the tall ones did before. The ratio is taken on the CELLS' painted extent rather than the board's box (2026-08-06): the box is that extent plus a fixed 4px of border, so `boardW/pitch` carries a `4/pitch` term that moves with the pitch, negligible on a 13-unit-wide board and not on a 9-unit-wide one, which is what it became when 3D Cubes was turned. Measuring the cells makes the ratio exact and let the tolerance TIGHTEN from 1 decimal place to 2. It also now pins the per-cell CLIP-PATHS (their count is the tiling's orientation count: 1 hex, 2 for 4.8.8, 3 rhombille, 4 cairo, 6 floret and deltoidal, and they must be byte-identical at every pitch since percentages are scale-free). The spec's header had claimed to guard those; it did not, because clip-path is PAINT and every measurement was `getBoundingClientRect`, which reports the unclipped box, collapsing every cell onto one orientation passed all six tests until this was added.
- **A BOARD MAY NOT BE WIDER THAN A PHONE CAN HOLD (2026-08-06, `src/logic/boardFit.js`).** Christopher's report: "the width of some of the tilings can get too wide for playing on mobile. It hasn't been a problem with hex, but it certainly is a problem with the floor tiles." Measured, that is a property EVERY tiling board shares and only some were far enough along to feel: all of them are WIDTH-bound on a phone and none is ever height-bound. At the 360x740 reference the board gets 314px of width against 510px of height, while five of the six lattices lay out square-or-wider (aspect <= 1.0; only the floret is taller than wide), so the width crushes the pitch while a third of the vertical budget sits unused. The widest shipped Paving Stones daily was 4 rows x 10 columns: a 345 x 141px letterbox strip, 25px cells, 440px of height going spare.
  - **The pitch IS the tap target, except on the 4.8.8.** `assembleTiling` normalizes the hexagon and all four Laves tilings so a cell's INSCRIBED DIAMETER is exactly one pitch, which makes the pitch directly comparable to `--cell-size` on a rectangle. The 4.8.8 keeps its own tuning, so at `OCT_CUT` 0.42 its octagon is 0.820 pitch and its interstitial diamond 0.594. Those ratios are DERIVED from the shipped geometry at runtime, never written down: `OCT_CUT` is tuned by eye and has already moved once (0.37 to 0.42), so a hardcoded ratio would have gone quietly wrong that day and would be wrong again for a seventh tiling nobody thought to add to a table. `clip-path` gates pointer events, so the polygon really is the target.
  - **The floors are his: 28px for a board's MAJORITY cell class, 24px for a minority one.** On the five isohedral tilings there is one cell class and both reduce to 28. The split exists for the 4.8.8, whose two sizes differ by 38% and whose diamonds are ~45% of the board; he took the middle after the alternatives were measured (majority-only lets the diamonds fall to 21px; 28px on the diamond removes Octagons from the ladder above L50 and from the endless pool entirely). **28 is calibrated to his own verdicts, not to a guideline**: scored by delivered tap size at 360px the pre-cap configs cluster with a CLEAN GAP, everything is <= 25.5px or >= 28.5px, nothing between, with Honeycomb's worst at 29.9 and Octagons' at 28.6 (both fine by him) against Paving Stones' 23.0 (his complaint). Any floor in [26, 28] sorts them identically, so the bar is not balanced on a knife edge.
  - **The reference phone is 360x740**, his call against the measured alternative: sizing for a 320px legacy iPhone SE costs real difficulty reach (3D Cubes would cap at 84 cells, ~160s, unable to reach the top of the daily band at all) to serve a device almost nobody plays on. A 320px phone still gets ~25px cells on the worst board, which is what the whole game shipped with before this.
  - **Constraining cost NOTHING in difficulty.** The largest legal board of every shape still prices far past the 240s band ceiling (cairo 187 cells ~1448s, deltoidal 126 ~1665s). The violating configs were not big, they were SIDEWAYS: of 41 violations across six surfaces, most were fixed by TURNING M and N at an identical cell count (Paving Stones 4x10 to 10x4 goes 23.0px to 37.3px with the same 66 cells), and the calibrator re-proved every turned daily entry 12/12 certified with par drift x1.00-x1.07. Caps at the reference, expressed in pitch units and derived per shape: max N is Octagons 7 / Honeycomb 10 / Paving Stones 8 / Petals 5 / 3D Cubes 5 / Kites 3.
  - **`boardFit.js` is the ONE definition, and only chaos consults it at runtime.** Authored tables (`TILING_BAND_CONFIGS`, `CHALLENGE_BLOCKS`, `ENDLESS_SPECS`, `COASTLINE_BOARDS`) keep hand-picked dimensions and are held to the cap by `test/boardFit.test.mjs`, which is what keeps `challenge250.js` the leaf it is documented to be. Chaos derives its dimensions from a target cell count, so `chaosTilingDims` routes through `fittingDims`. **The calibrator's candidate grid must be kept in step BY HAND**, a committed entry absent from the grid is measured but never PROVEN, which is how the first calibration run after the cap came back clean without having touched a single changed entry.
  - **The chooser maximizes the delivered PITCH, which subsumes the aspect penalty it replaced.** `chaosTilingDims` used to score `|M - N|`, measuring lopsidedness in lattice indices, the wrong space, since a step in M and a step in N cover different distances on screen for four of the six lattices (the floret's 8x2 is 4.0:1 in indices and renders 314 x 471px, better proportioned than cairo's 10x5 at 2.0:1 rendering 255 x 510px). A ribbon loses on its own terms under a pitch objective, because too-wide is capped by the width budget and too-tall by the height one. `test/chaosShape.test.mjs` therefore asserts on the RENDERED extent and carries a non-vacuous check that the 4.8.8 M=3,N=13 strip which motivated the original guard still fails. The chooser works to a COMFORT height (viewport minus the measured ~168px of header/nav chrome minus ~110px of browser UI), not the renderer's 70vh: the cap must mirror the renderer because the renderer really will shrink the pitch to fit 70vh, but 70vh is more height than a phone showing browser chrome can display, and that slack is not a thing to aim for.

- **Tiling tile SEAMS are DRAWN, the clip-paths tile exactly, so nothing else separates neighboring cells** (his petals report, 2026-08-02: a floret rosette's six petals read as ONE solid hexagon and a revealed region as an undivided sheet; a rectangle gets its boundaries free from `--grid-gap`, a tiling had no equivalent, and borders/outlines are clipped away with the box). `_renderTilingSeams` (boardRenderer) draws every shared polygon edge from the SAME `buildWireframe` walls sever from, as ONE SVG path in unit coordinates: viewBox = tiling extent + CSS `100%` sizing means every re-lay rescales it with no re-render hook, and `vector-effect: non-scaling-stroke` keeps the line width in screen pixels at any pitch. Theme tokens `--tiling-seam-color` (default: the theme's own `--color-border`, the same color rectangular gaps show) and `--tiling-seam-width` (default 1.25px); dark overrides the color a step lighter because its border color vanishes over its near-black revealed cells, which is exactly where numbers must attribute to tiles. z-index 2: above cell bodies (including the `.fx-on` lift) so seams read across revealed regions, below walls (3) so a wall still dominates its edge. Verified by pixels (before/after screenshots, classic + dark); e2e pins presence on tiling boards and absence on rectangles.
- **Keyboard focus on a tiling cell is an INSET wash, not an outline.** CSS applies `filter` first and `clip-path` second, so a `drop-shadow` ring around the silhouette is clipped away entirely, and an `outline` (or any box-edge shadow) survives only where the polygon meets its bounding box, two slivers that read as cell seams. The indicator therefore has to live INSIDE the clip: a huge-spread `inset` box-shadow washes the cell's whole painted area, so it takes the hexagon / octagon / diamond shape exactly, and because an inset shadow paints above the background but BELOW text, the number or flag the player is navigating by stays legible. The cell is also scaled up slightly, because the cells tile edge-to-edge with no gaps and identical colors, there is nothing for a mere ring to contrast against. Rectangular boards keep their original 2px outline untouched.
- **`computeLiarZone` follows the topology (2026-07-22).** The liar-zone tint walked `(row±1, col±1)` of the CONTAINER, which on a tiling is pure storage, so it tinted cells that were not the liar's neighbors and missed ones that were (visual only; the certifier reads `liarOffset`, never the zone). It now reads `buildNeighborCache` on an explicit topology. The rectangular walk is kept VERBATIM and is deliberately wall-BLIND, the zone is a spatial cue, not an adjacency claim, and the tint has always crossed walls, so routing it through the wall-aware cache would silently restyle every walled square board. Both halves pinned in `test/liarZoneTopology.test.mjs`.
- **Reachability is unchanged: still test-gated.** `?coastline=` gained an optional shape prefix, `?coastline=hex`, `?coastline=hex:sonar,walls`, with no prefix still meaning 4.8.8, so every existing test link works verbatim. The whole surface remains `isTestEnvironment()`-gated and UNREACHABLE in production.

**Tilings #3-#6 are the four LAVES tilings (2026-07-27): cairo pentagonal [3².4.3.4], floret pentagonal [3⁴.6], rhombille [3.6.3.6] and deltoidal trihexagonal [3.4.6.4].** Six tilings total. The Archimedean list had run out of candidates the legibility rule allows, seven of the eleven contain triangles, and a triangle is the hardest number-host there is, so the search moved to their DUALS, where every tiling is isohedral by construction: ONE cell shape at one size, so every interior cell reasons about an identical neighborhood and the "a number plus a modifier watermark must fit in EVERY cell" bar is a single question rather than a per-shape one. **What each proves that the others do not**, which is also why four rather than one: rhombille reasons over a strictly LARGER neighborhood than a square grid (interior valence 10 against 8) and has a MISSING RUNG in its deduction ladder, so it is the gate that shows tank/gauss carrying a whole board alone; deltoidal is the richest of the six to solve (**62.3%** of constructively generated certified boards reach techniqueLevel 2, against rhombille's 6.2%) and is the second lattice above the classic ceiling at valence 9; cairo is the only one of the four whose compass runs on a SQUARE direction set, and, with deltoidal, the case that forced the compass's ray anchor apart from the point the number is drawn at; floret is the chirality and rotational-phase case, six orientations of one pinwheeled pentagon on a lattice that is itself rotated. All four are reachable only through the same `isTestEnvironment()`-gated `?coastline=` link, no card, no mode, no rotation, nothing in production.
- **CORNER-INCLUSIVE ADJACENCY is now the contract, and it is a strict NO-OP on the two Archimedean tilings that shipped before it.** Cells touching at a single VERTEX are neighbors, exactly as diagonal cells are on a square grid (Christopher's rule, 2026-07-27: "corners are adjacent in mine counts"). The backward-compatibility argument is structural rather than lucky: **4.8.8 and the honeycomb are TRIVALENT**, every interior vertex has degree 3, and at a degree-3 vertex all three incident faces are already pairwise edge-sharing, so there is nothing for the rule to add. Measured zero vertex-only pairs on both, across 77 patch sizes each and every value of `OCT_CUT` short of the degenerate 0.5 (where the interstitial diamond collapses to a point and diagonal octagons do meet). The four Laves tilings carry degree-4 and degree-6 vertices, which is exactly where the rule bites: interior valence goes 5 → 7 (cairo), 5 → 8 (floret), 4 → 10 (rhombille) and 4 → 9 (deltoidal), and on rhombille's 90-cell gate patch the corner links (207) OUTNUMBER the edge links (159). The closed form is **Σ over the cell's vertices of (deg(v) − 1), minus its side count**, which reproduces all six lattices plus a rectangular control exactly and is what a new tiling's valence should be checked against before it is measured. Adjacency is built in `assembleTiling` from an unordered pair map, so symmetry is structural and `defineCellNeighbors` cannot be handed an asymmetric list; the lists are sorted ascending because neighbor ORDER is load-bearing (`applyMirrorPairs` takes the first eligible neighbor in list order, and reversing the order moves 2 mirror cells on each of the two earlier tilings, the solver is order-blind, so certification and par are not exposed, but mirror placement is). **WALLS SEVER BY SIGHT LINE, not by shared edge (his rule, 2026-08-07, correcting what this paragraph used to claim was deliberate).** `buildWireframe` emits an edge only for a pair sharing exactly TWO vertices, so for a while a corner-only link had no wall segment and no wall could sever it. That was recorded here as right, and it was not: playing 3D Cubes at L87 he found a cell reading 5 that should have read less, with a wall drawn between it and the mines it was counting. His rule replaces it and is stated geometrically: **if a line drawn from the center of one cell to another is bisected by a wall, those two cells are not connected.** Whether two cells see past a corner depends on the ANGLE between them, so two facing each other across an open corner still count each other while two that would have to curve around the wall do not. ONE test covers both kinds of neighbor, since an edge neighbor sight line crosses its own shared boundary, and the previous edge-severing behavior falls out rather than being special-cased. Measured before the fix over 12 walled boards for each shape: EVERY board on all four Laves tilings was affected, **464 see-through corner links, 165 of them feeding a wrong clue** (rhombille worst at 77). The reason it is nastier than a wrong number is that the certifier reads the same adjacency, so those boards certified as no-guess and were internally consistent while being unsolvable for a person reasoning from the wall in front of them, and nothing in the engine could notice; the regression test therefore asserts against the GEOMETRY a player sees, not against the graph. **4.8.8 and the honeycomb are untouched, structurally**: both are trivalent, so they have no vertex-only pairs at all, and their fingerprints are byte-identical under the rule itself. A failing wall chain is now TRIMMED rather than abandoned (severing sight lines strands a cell more often, and the all-or-nothing contract was shipping cairo boards with no walls on 4 of 12 draws); trimming does change 4.8.8/honeycomb boards, since a chain that used to be dropped whole can now survive shortened. **Follow-up owed: the endless pool needs re-hardening.** Fewer links means the certifier works harder, and two entries re-measure over their generation cap (rhombille 8996ms against 3500, deltoidal 2564 against 2000). Removing them by hand is the wrong fix, since the rhombille one is the pool entire rhombille representation; run `scripts/harden-endless-pool.mjs`. The authored ladder wants the same re-validation for its 33 walled-Laves levels.
- **Exact integer vertex keys, because the rounding bet gets worse with patch size.** The 4.8.8 and hex builders key their vertex dedupe on `Math.round(x * 1e6)`, which bets no coordinate lands near a half-step. Losing that bet does not throw: it splits one corner into two vertices, DROPPING the adjacency the cells had through it, so the board certifies against a neighborhood the player never sees, the one failure the no-guess contract cannot absorb. The bet is not lost today, but the margin narrows exactly where it matters: measured on these four with float coordinates, the closest any vertex comes to a 1e-6 boundary is 5.8e-8 at M=N=6 and 2.1e-8 at M=N=12, while the spread between independent computations of one shared corner grows from 8.9e-16 to 3.6e-15 over the same range, and nothing bounds the gap. So each builder picks INTEGER coordinates for its own lattice (`latticeVertices`) and derives the float exactly once per vertex, cairo's are `(a + b√3)/2`, floret's a triangular basis on which the pinwheel's 60° rotation maps integers to integers, rhombille's and deltoidal's the shared `(B√3/4, C/4)` addressing of the hexagon substrate they both subdivide. Then there is no rounding decision to get right and no size at which it starts being wrong. `assembleTiling` also owns the other three shared decisions: READING ORDER (ascending centroid y, ties by centroid x, taken in the builder's own units BEFORE normalization so it cannot move if a scale is retuned, a frozen fixture's mine list is a list of INDICES and means nothing except against it), the OPENER (the cell nearest the patch's center of mass, with ties broken to the later cell in reading order because exact lattice integers make a mirror-symmetric tie bitwise rather than float noise, deltoidal at M=3,N=4 ties cells 31 and 39), and the NORMALIZATION.
- **The compass needed per-lattice direction sets AND, on two of them, a separate ray ANCHOR.** `COMPASS_DIRS_BY_TILING` in gimmicks.js replaces the old two-way ternary: `COMPASS_DIRS_8` for 4.8.8 and cairo, `COMPASS_DIRS_60` (0/60/120 and opposites) for hex and rhombille, `COMPASS_DIRS_30` (30/90/150 and opposites, so it has a true due-north and no due-east) for floret and deltoidal. **Cairo and deltoidal compute the ray from `cellPos.ax/ay`, a point that is NOT where the number is drawn.** On their incircle centers every direction scores worse than the hex verticals that were rejected, cairo 53.9% on the diagonals and 64.1% on the axes, deltoidal 67.2% at its best, because the incircle centers of a pentagon or a kite do not lie on the lattice's straight lines. Cairo's pentagon spans one edge of the underlying √3 square lattice, so the midpoint of its two lattice-site vertices falls on a 45°-rotated square lattice of its own: 100.0% on the diagonals, 87.9% on the axes, against the shipped 4.8.8 axes' 90.4%. Deltoidal's is the midpoint of the kite's long diagonal, at radius exactly **1/2** of the hexagon circumradius, and that number is a lattice coincidence rather than a tunable, sweeping 0.30 to 0.866 puts every other value below the bar, including the vertex centroid (0.625) and the incircle center (0.634), while 1/2 reaches 89.8-91.3%. Splitting the anchor from the drawn center costs nothing, measured with the ray taken from the anchor and the LINE traced between drawn centers. **Every center must be CLOSED FORM, never a numerical search:** a pattern-search incircle carries ~1.5e-9 of error, larger than `computeCompassRay`'s 1e-9 EPS, and measuring deltoidal that way silently destroyed 4 of its 6 direction families (27.1% of all rays changed), the rays came back short and PLAUSIBLE rather than empty, which is the failure a review does not catch. The other silent failure is ROTATIONAL PHASE: re-derive a builder 30° around and the clean set swaps with the rejected one, which still returns rays of mean length 1.3-2.8. `test/tilingCompass.test.mjs` is the guard for both, it re-measures every shipped set and its rotated alternative against the builders' actual output (accept bar 88%, reject bar 75%, mean-ray bar 2.2), and injects 1.5e-9 of anchor noise to assert the ray collapses, which doubles as proof the bar is not vacuous.
- **The renderer derives a PER-CELL clip-path and box, because these lattices put one shape in several orientations.** The old layout picked one constant clip-path per `pos.shape`, which holds only while every cell of a shape is identical up to TRANSLATION, true of the octagon, the interstitial diamond and the hexagon, false of all four Laves tilings (cairo has 4 distinct clip-paths, floret 6, rhombille 3, deltoidal 6, against 4.8.8's 2 and hex's 1). Box size does not identify the rotation either: rhombille's 0° and 60° rhombi share a 1 × 1.732 box and need different clip-paths, so anything keyed on box dimensions mis-shapes half the board without erroring. `cellOutline` in tilingGeometry.js derives both from the cell's own polygon, which is the rule the three hand-inlined branches were cases of, `SQ_BOX_FRAC` IS the diamond's bbox width and `HEX_BOX_H` IS the hexagon's bbox height. **Verified byte-equivalent on 4.8.8 and the honeycomb:** worst clip-path error **0 percentage points** over 5400+ cells (including 1×1 through 30×30 degenerate containers, and re-derived across `OCT_CUT` 0.15 to 0.49, so the equivalence is structural rather than tuned-in), boxes agreeing to within 1e-13 px, and **0 differing pixels out of 711,000** in headless Chromium. The octagon's string differs, `octagonClipPath()` mixes `toFixed(3)` with bare `0%`/`100%` literals, but Chromium normalizes `42.000%` to `42%`, so nothing that can read a clip-path can tell.

- **`OCT_CUT` was raised 0.37 → 0.42 on 2026-07-28** (Christopher: "make the squares and octagons more even"). It is the single knob balancing the 4.8.8's two cell sizes, and it is tuned BY EYE, so what is pinned in `test/tilingGenerator.test.mjs` is not the value but the two properties it trades off, with a floor on each: the diamond's number circle rose from **59% to 72%** of the octagon's (and its number from 74% to 84% of the octagon's font, for free, since the font is half the cell's own box), while the octagon's flat sides fell to **0.27 of its diagonals**. Both directions of drift are real, cut smaller and the diamond shrinks back toward the 41% it has at a regular octagon; cut larger and the flats vanish, at 0.44 reaching a fifth of the diagonals, where the board reads as a lattice of rotated squares rather than a 4.8.8. Nothing downstream hardcodes it: adjacency is cut-INDEPENDENT (the valence histogram and the zero vertex-only-pair count hold across 0.05 to 0.499), so no certificate, fixture or par value moved, and `SQ_BOX_FRAC`, the clip-paths and both font sizes all derive. The polygons do NOT ride the board: the canonical payload carries `cellPos` and the `{type, M, N}` descriptor, so the renderer rebuilds them through `buildTiling` exactly as `applyWallsTiling` rebuilds the wall wireframe, memoized on one slot since a single board is on screen at a time.
- **A font-size correction: "P is the inscribed diameter" was true for the hexagon and FALSE for the shipped octagon.** A REGULAR octagon has `OCT_CUT = 0.292893`, and there the inscribed diameter is exactly one pitch, but `OCT_CUT` is tuned well up from that for legibility, past the crossover where the 45° faces start binding instead of the axis flats, so the shipped octagon's inscribed diameter is **0.820 P** (0.891 P before the cut was raised to 0.42). The 4.8.8's two shapes and the hexagon therefore sit at three different font-to-inscribed-diameter ratios; "P is the flat-to-flat width" is the statement that is true of both the octagon and the hexagon. **Shipped font sizing is UNCHANGED** and deliberately stays off the rule, retrofitting would shrink the octagon's number 18% and the interstitial diamond's 29% on boards that read correctly today. The four new tilings follow the hexagon's rule: `assembleTiling` scales each so the cell's INSCRIBED DIAMETER is one pitch unit, `FONT_UNITS = 0.5` is then exactly half the largest circle the cell can hold, and their cell areas land within 25% of the hexagon's, so `_fitTilingPitch` and the `--cell-min-size` / `--cell-max-size` clamps still mean the same thing.
- **The number is drawn at the cell's own visual center, which on an asymmetric cell is not the box center.** Every shape shipped before this was centrally symmetric (as is the rhombille rhombus), so box center, centroid and incircle center coincided and the question never arose. A floret pentagon's incircle center sits 0.25 of a pitch off its box center and a deltoidal kite's 0.21, against an inscribed radius of half a pitch, a number flex-centered on the box reads as shoved toward the point. `_anchorPadding` corrects it with one-sided padding: `.cell` flex-centers its content on the CONTENT box, so a one-sided pad moves the glyph by half the pad, and `box-sizing: border-box` means the border box, and with it the clip-path, does not move at all. The octagon, the interstitial diamond and the hexagon emit no padding and are byte-identical. The same padding is why the sonar watermark dropped its `left/top: 50%` + `translate(-50%, -50%)`: an absolutely positioned child with every offset AUTO falls at its STATIC position, which the flex box centers in the same content box the number lands in, whereas 50% of the PADDING box would have put the symbol 12px from its own number on a floret at a 48px pitch and spilled it out of the clip.
- **Two rectangular assumptions in the overlays, both properties of the two earlier tilings rather than of a tiling.** `_renderTilingWalls` took DOM cell 0's rect WIDTH as the pitch and its rect CENTER as unit `cellPos[0]`. The first is true only of 4.8.8 and the honeycomb: measured on the builders as they ship, cell 0's box is exactly one pitch wide on 4.8.8 and hex but **1.155 on floret, 1.366 on cairo and deltoidal, and 2.000 on rhombille** (stable across every patch size, since which orientation lands first is a property of the lattice and the reading order), so every wall on a Laves board would have been scaled by up to 2× and landed nowhere near its edge. The second is true only while the cell is centrally symmetric, which the kite and the two pentagons are not. Both are gone rather than patched: unit coords now map straight from `#board`'s own content-box origin at the live `--cell-size`, which is where `layoutTilingCells` places every box, and which is algebraically identical to the old output on 4.8.8 and the honeycomb. Separately, `#board.tiling-board .cell` now zeroes BOTH `border-radius` and the `--cell-shape-radius` token, because a box radius can only eat into a clip-path: it bites wherever a polygon vertex reaches its own box corner, dropping the tip and leaving a background speck with a hit-test dead zone at the same spot. That is every high-valence vertex of three of the four (the six kite tips at a deltoidal hexagon center, the six pentagon tips at a floret rosette center, the rhombille cube corners), measured up to 12.9px² on 48 of 72 deltoidal cells, 9.7px² on 60 of 90 rhombille, 4.9px² on 48 of 72 floret, and nothing afterward. It costs the other three nothing (4.8.8 and cairo untouched at every pitch; the hexagon recovers 0.09px² a cell at the 18px minimum). Zeroing the TOKEN as well as the property is what reaches the effect-theme gap seal, whose `::after` body layer reads the radius off its originating cell and would nick the same tips on any theme with an ambient effect.
- **The floret's rosette lattice is inherently ROTATED, and its board box is the one documented residual.** Its two lattice vectors sit at 60°, so laying rosettes at plain `m·L1 + n·L2` gives a sheared PARALLELOGRAM, which leaves two opposite triangular wedges of the board box empty, something no other tiling here produces, and which reads as a broken board rather than a lattice. The shear COMPOUNDS with N, so it gets worse on bigger patches, not better. `L2` drifts x by exactly `L1/3` per row, so rows are re-seated by whole-`L1` translations, which bounds the remaining stagger at ±L1/3; whole-`L1` steps are lattice symmetries, so the cells stay congruent, the adjacency rule is untouched, and the compass phase is unaffected. Re-seating the rows bounded the shear but did not remove it: no choice of basis squares up a lattice whose own `L1` sits at **10.89°** off the horizontal, and the board still filled only **67.4%** of its box against 80-94% for the other five.
- **The floret is CROPPED TO A RECTANGLE at CELL granularity (2026-07-28), which is what finally squared it up.** The two ways to fix the shear were to rotate the whole tiling, which would have invalidated the measured compass direction set, since every one of those is fixed by the lattice's rotational phase, or to change WHICH lattice cells the board uses. The second is strictly safer and is what ships. `buildFloretTiling` now enumerates a padded patch, then keeps the `6MN` cells nearest the center under a rectangular metric. The boundary then steps by ONE PENTAGON instead of by a six-cell rosette, so it can follow a rectangle closely; a rosette straddling the edge just contributes the petals that fall inside. Occupancy **67.4% → 82.2%** on the 3×4 practice patch, which puts floret above deltoidal rather than last, and 77-85% across every `(M, N)` from 2×3 to 5×5. Nothing else moves: the lattice, its orientation, the compass set, cell congruence and the corner-inclusive adjacency rule are all untouched, and `TILING_TYPES`-wide tests plus the compass phase guard confirm it. Two consequences worth knowing. The crop picks its aspect by SWEEPING candidate ratios and keeping the one whose polygons land in the smallest bounding box, every cell has equal area, so minimum box area IS maximum fill, and that adapts to any `(M, N)` instead of baking in a ratio tuned for one board (the patch's own aspect gives 76.4%, a square crop 73.5%, the tightest 82.6%). And because edge rosettes are now partial, a 3×4 patch has **6** complete hubs rather than 12, which the gate asserts directly. The cell SET changed, so the frozen fixture and the gate's topology pins were re-derived; `total` is still exactly `6MN`, so the container and its storability are unchanged.
- **Rhombille has no Pass B, and it is the generation-cost outlier.** Measured with an instrumented certifier: **0 canonical and 0 generic subset moves across 103 certified boards**, and only 3 progress rounds in 4500, it finds subset pairs, but `diffMines` almost never lands at 0 or at `|diff|`, so no deduction follows. Its ladder runs Pass A straight to Pass C. The structural correlate is that it pairs the highest mean valence with the FEWEST full-containment pairs of any lattice measured (23/366, 6.3%, against ~33% on floret and deltoidal). So its gate asserts `canonicalSubsetMoves === 0` and `genericSubsetMoves === 0` EXPLICITLY rather than omitting the hex gate's `genericSubsetMoves >= 1` line, a missing assertion reads as an oversight, an asserted absence reads as the finding it is. Leaning on Pass C for every board is also what makes it dear: worst single board over 1800 generated (30 seeds × 10 modifier configurations per lattice, 0 failures) is 4.8.8 21 ms · hex 21 ms · cairo 178 ms · floret 982 ms · deltoidal 2094 ms · **rhombille 2371 ms**, roughly two orders of magnitude above the 4.8.8. It is superlinear in cells, too, which is why its practice board is 72 cells rather than the 90 its frozen gate fixture uses: the same sweep at M=5,N=6 measured 13.7 s worst case, six times the cost for 25% more cells. The cost is paid behind the boot overlay, once per load, on a test-gated surface.

**Sonar transfers to a tiling; it reads "within two steps" as graph distance** (a depth-2 breadth-first walk) when an explicit topology is present. That is the honest generalization rather than a convenience: on an UNWALLED rectangle the depth-2 closure of the 8-neighborhood is EXACTLY the 5×5 block, so the graph reading and the geometric one already agree wherever both are defined (pinned as its own test, if it ever fails, the generalization is the wrong one). Rectangular boards keep the literal 5×5 scan verbatim, walls severing only the inner ring. That inner-ring-only rule is NOT the same as graph distance once walls exist (the outer ring reaches through a wall the inner ring is blocked by) and looks more like an accident than a principle, but it is the rule players have been solving against and the help text says "a 5×5 area", so changing it is a design call rather than a refactor's side effect. **No board has ever combined sonar with walls** (measured across all 144 canonicals, 2026-07-19), so the quirk has never actually manifested in production. **Pressure plates follow the topology (2026-07-19), and the plate's demand region is single-sourced.** `plateDisarmCells` in `adjacency.js` answers "which cells must be revealed before this plate disarms", and is read by BOTH the live `checkPlateDisarmed` (gameActions.js) and the target set of `estimatePlateMovesToDisarm` (boardSolver.js). That is coherent rather than a bug, the plate states what must end up revealed, walls constrain the reasoning and the flood that get you there, and a severed cell is still reachable from its own side, but it is exactly the kind of thing a well-meaning refactor "fixes", which is why a test asserts the walled neighbor is still demanded. Plates are NOT in `DAILY_SAFE_GIMMICKS` (challenge/chaos only), so no canonical board includes one and there is no stored-board blast radius.
