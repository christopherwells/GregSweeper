## Molt Day (daily-streak insurance)
Every 5 consecutive daily completions banks one **molt day** (player-facing name; glyph 🦀), capped at 2. A banked molt day is spent automatically and lazily at the next completion to cover a missed ET day, so the streak survives a day off. When the gap exceeds the bank the streak resets to 1 and the bank is RETAINED (all-or-nothing: a molt day is spent only when it actually saves the streak). Covered days add nothing to the count and never help earn. Weekly never touches streak; archive plays (`state.isArchivePlay`) and practice dailies (`?seed=`, `state.isDailyPractice`, the `isPractice` guard in `saveGameResult`) never earn, spend, or touch it. Archive `dailyHistory` rows carry `archive: true` and are filtered out of the streak derivation by `streakBearingDates` (archiveEligibility.js) before `reconcileStreakFromHistory` runs, so a replayed gap day can't retroactively splice the streak. The metaphor is Greg the crab sheltering while it molts.
- **One pure module** `src/logic/moltDay.js` is the single source of truth (no imports): `applyStreakContinuation` (the commit math), `projectContinuation` (read-only "what would completing today do"), `isStreakAlive` (read-side lapse check, a covered gap is still alive), `coversTonight` (the push gate). Constants `MOLT_EARN_EVERY = 5`, `MOLT_CAP = 2`. Consumed by THREE surfaces so they can never disagree: the completion path (`statsStorage.saveGameResult`), the provisional notice on the title card (`getMoltProvisionalNotice` → `main.js`), and the push script (`send-push.mjs` imports `coversTonight`).
- **Storage** (`statsStorage.js`): `modeStats.daily.moltBanked` + `moltLastUse = { date, covered, streakKept }` (defaults 0/null, backfilled like other added fields). `getDailyStreak()` now returns `{ streak, best, banked }` and is bank-aware (a covered gap reports the running streak, not 0). `saveGameResult` records a transient `_lastMoltEvent` drained once by `consumeMoltEvent()` (NOT persisted, so a stale "earned" can't resurface). `applyCloudProgress` rides the molt fields in the SAME date-anchored snapshot as `(dailyStreak, lastDailyDate)` so the bank never pairs with the other side's streak (pinned by `test/moltDayCloudMerge.test.mjs`). **Legacy-preserve rule (fixed 2026-06-16):** a missing cloud `moltDay` node, OR the bare default `{banked:0, no lastUse}`, is the pre-molt shape every existing account carries, absence of information, NOT an authoritative 0. `adoptMolt` only overwrites the local bank when the cloud carries REAL molt state (`banked > 0` or a recorded `lastUse`); otherwise it preserves local. Without this, the overwrite listener (`applyCloudProgress(cloud, {overwrite:true})` on every snapshot) zeroed the freshly-granted backfill on every boot, so an existing-streak player never kept their molt days (Christopher, 92-day streak, saw 0 crabs). A genuine cross-device spend (`{banked:0}` WITH a `lastUse`) is still adopted, so a spend can't resurrect.
- **Cloud**: `saveProgress` writes `users/{uid}/moltDay = { banked, lastUse }`. The rule block IS whitelisted in `firebase-rules.json`, the `users/{uid}` node ends with `$other: false`, so an un-whitelisted child would make the WHOLE progress `update()` fail validation and drop silently (the 866683d class of bug); pinned by `test/moltDayRules.test.mjs`.
- **One-time launch backfill** (`backfillMoltDays` in statsStorage, `backfillGrant` pure in moltDay.js): an existing streak earns the molt days it would have banked (>4 → 1, >9 → 2). Self-guarding (skips once any bank or `moltLastUse` exists), so it runs safely every boot, never re-grants, and never undoes a spend cross-device; local-only (the next completion syncs it, and a 2nd device converges from the shared streak). Called at boot after `_reconcileDailyStreak`.
- **Daily-card indicators** (`updateTitleProgress`): the card frames Greg's note with its corners, 🦀 tokens AND the streak ("N days") together at bottom-left in one `.daily-corner-group`, par ("Par Ns") bottom-right, the Past chip riding the hero's grid at top-right. The molt tokens sat in their own top-left corner until the card became a full-width hero, whose left column is the mode icon; they ship as ONE positioned group with the streak so neither has to know the other's width, and they may NOT nest (a streak reads 0 while a bank survives, since a lapse past the bank keeps the crabs). The streak + par are PLAIN corner text in the note's muted color (NOT pills, NOT italic), so the Past chip stays the one pill that pops; they hug the corners absolutely like Past (a reserved `padding-bottom` on the daily card keeps them clear of the note across breakpoints). Greg's note keeps the THEME-matched Greg sprite (`themeSpriteImgHTML` resolves the active world's Greg via `getThemeEmoji('smiley')`, not the forced-canonical `spriteImgHTML`). A provisional "Molt day holds your N day streak" replaces the note before play when a cover is holding the streak; completed shows "Played today" + the dimmed `.daily-completed` card. No in-game LCD change.
- **Earned celebration**: earning a molt day flags `flagMoltCelebrate` (statsStorage); `showTitleScreen` drains it once (`consumeMoltCelebrate`) to show the `#molt-earned-modal` popup, and on dismiss the crab drops into the card's top-left corner (`moltPlace` keyframe, `_animateMoltPlacement`). The covered/used event still shows its quiet inline `.molt-note` in the win modal.
- **Tests**: `test/moltDay.test.mjs` (bank-math table + `backfillGrant`), `test/moltDayCloudMerge.test.mjs` (snapshot atomicity + the legacy-preserve rule + an end-to-end legacy-streak backfill-then-listener boot), `test/moltDayRules.test.mjs` (rule block), `test/sendPushMolt.test.mjs` (the three push branches).


## Push Notifications
PWA web push via FCM, opt-in via Settings (`Notifications` block alongside the modifier-popup toggle). The `notify-daily-ready.yml` workflow runs an hourly cron at `0 * * * *` UTC; `send-push.mjs` reads each enabled subscriber's `notificationPrefs.hourLocal` from Firebase and only sends to those whose chosen ET hour matches the current ET hour. So each subscriber gets at most one push per day at the time they picked in Settings.

Message text rotates day-to-day from a small per-category pool (`DAILY_BODIES`, `WEEKLY_BODIES`, `STREAK_BODIES`, `STREAK_COVERED_BODIES` in `send-push.mjs`). Pick is deterministic by date so all subscribers on the same day see the same line, but the wording varies day-to-day instead of repeating "Today's daily is waiting" forever. Categories: `weekly` (Monday, overrides daily), `daily` (default), `streak` (8pm ET evening rescue when `dailyStreak ≥ 3 && lastDailyDate < today`).

The script runs two passes per hour, both routed through the pure decision helpers `reminderDecision` / `streakDecision` (exported from `send-push.mjs`, imported by `test/sendPushMolt.test.mjs`): (1) reminder, sends daily/weekly to users whose `hourLocal` matches the current hour and `dailyReminder !== false`; if a molt day covered yesterday (`moltDay.lastUse.date` === yesterday) the daily body is swapped for an acknowledgment ("Your molt day covered Tuesday. Streak intact at N."). (2) streak-warning, fires only at hour 20 (8pm ET); sends to users whose `streakWarning !== false`, `dailyStreak ≥ 3`, and `lastDailyDate < today`. **Molt-day aware**: if `coversTonight(...)` (the bank covers them skipping tonight) the at-risk warning would be a lie, so a soft `STREAK_COVERED_BODIES` nudge goes out instead. The streak push uses a separate FCM tag so it stacks with the morning reminder instead of replacing it. Debugging: `node scripts/send-push.mjs --dry-run --fixture <users.json> [--date YYYY-MM-DD] [--hour N]` prints each pass's decisions with no credentials or network (example fixture at `test/fixtures/push-users.example.json`); the main IIFE is guarded so the module imports cleanly for tests.

- `src/firebase/firebasePush.js`: `enableNotifications({hourLocal})`, `disableNotifications()`, `loadNotificationPrefs()`, `updateNotificationHour()`. Hardcoded `VAPID_PUBLIC_KEY` constant, set this from the Firebase Console value (Project Settings → Cloud Messaging → Web Push certificates) before push will work. Empty string = `'no-key'` toast.
- Subscription stored at `users/{uid}/pushSubscription = { token, subscribedAt }` with auth.uid match. Token is the FCM-managed string from `messaging.getToken({vapidKey})`, server-side script POSTs against `fcm.googleapis.com/v1/projects/{id}/messages:send` using this token.
- Prefs stored at `users/{uid}/notificationPrefs = { enabled, hourLocal, dailyReminder, streakWarning }`.
- SW handlers in `sw.js`: `push` event renders the notification with icon + tag + deepLink in `data`; `notificationclick` focuses an existing tab matching the deepLink or opens `?mode=daily` / `?mode=weekly`.
- **Manual prereqs (one-time setup before push works)**: (a) Generate VAPID key pair in Firebase Console → Cloud Messaging → store the **public** key as the `VAPID_PUBLIC_KEY` constant in `src/firebase/firebasePush.js` (safe to ship publicly), (b) Generate a service-account JSON in Firebase Console → Project Settings → Service Accounts → store the entire JSON (one line) as the `FIREBASE_SERVICE_ACCOUNT` repo secret. Without (a) the toggle shows "Push not configured yet"; without (b) the workflow fails on access-token mint.
- iOS: requires add-to-home-screen on iOS 16.4+. `firebasePush.js` detects iOS-non-standalone and surfaces "Install GregSweeper to your home screen first" instead of silently failing. Android/desktop work without that hoop.
- Categories: `weekly` (Mon morning), `daily` (default), `streak` (8pm ET rescue). The cron picks based on the calendar; per-category opt-out via `notificationPrefs.dailyReminder` (default true) and `notificationPrefs.streakWarning` (default false, explicit opt-in via Settings).


## Daily Archive (replay past dailies, feed the model)
Past dailies are replayable. A "Past dailies" link on the Daily card opens a month calendar (`#archive-modal`, outside `#app`); tapping a date plays that date's canonical board. Archive plays are a day-of daily in every visible way (same board, par, features, Certified chip) but are walled off from anything that would corrupt the day-of ritual or the par fit.

- **A finished board is NOT replayable** (Christopher, 2026-07-18: "I don't want them able to play archive boards they've already played"). A daily is a one-off: once a board is cleared there is nothing left to find on it, and a replay recorded nothing anyway (`archiveSubmitPlan` is first-completion-only), so it was playable but pointless. `archiveDayState(date, today, completed)` returns `'playable' | 'done' | 'today' | 'unavailable'` and is the single source for the decision; the calendar paints `'done'` as a NON-INTERACTIVE span carrying the ✓ and an "already played" label, so a completed month still reads as a completion map (his call) without inviting a tap. The click handler RE-DERIVES the state rather than trusting the rendered class, because the grid is painted once per month view while the completed-set refreshes on open. **`completed == null` means UNKNOWN, not empty, and fails OPEN**: a signed-out player or a failed `loadDailyHistory` read cannot be told what they have finished, and blocking the whole calendar on a flaky read is worse than letting a replay through, the data are protected regardless, since `archiveSubmitPlan` fails CLOSED on unknown history and records nothing. The calendar's completed-set and the Board Heatmap's spoiler gate both derive from the same `users/{uid}/dailyHistory` node (via `loadDailyHistory` and `fetchUserDailyHistory` respectively), so the two surfaces cannot disagree about what you have played.
- **Two pure gates** (`src/logic/archiveEligibility.js`, node-tested in `test/archiveEligibility.test.mjs`): `isArchivableDate(date, today)` offers `FIRST_ARCHIVE_DATE` (2026-03-06, the app launch) through yesterday (today is the live Daily's job; canonical storage only began 2026-04-27, so launch..04-26 were regenerated from each date's seed with the current pipeline and backfilled by `scripts/backfill-old-dailies.mjs`, fresh boards stamped with old dates, NOT the unrecoverable per-device originals, and all below `ARCHIVE_FIT_EPOCH` so they never feed the fit); `archiveSubmitPlan(date, hasHistory)` returns `{submitFit, writeHistory}` enforcing first-completion-only (a `dailyHistory` row present → record nothing) and the `ARCHIVE_FIT_EPOCH` (2026-05-07, the dailyHistory ship) below which a date stays playable but never submits a fit row (it could double-count a pre-history live play). `CRUX_VIEWED_KEY_PREFIX` is the shared localStorage key PR 4's `?crux=` route writes and the archive submit reads.
- **Launch** (`launchDailyArchive(date, raw)` in modeManager): the calendar PROBES the canonical first (`loadDailyBoard`; archive has NO local-gen fallback, a missing board isn't offered), then this bypasses `switchMode`'s resume-the-real-daily path and forces a fresh `newGame` with `state.isArchivePlay = true`, the caller-set past `dailySeed`, and the fetched board in `state._archiveRaw`. `newGame` keeps the past seed for archive, reads `_archiveRaw` verbatim, never re-stamps `canonicalDailyBoard` (today's stash), and ABORTS rather than local-gen if the board is somehow missing. `switchMode` clears `isArchivePlay` on every normal mode switch so a resumed real daily can't inherit it.
- **Never persists, and never CLEARS either** (`ownsSaveSlot` in gameState.js, read by both ends): archive shares the daily save slot, so persisting would clobber an in-progress real daily, and a past-date save would fail resume anyway. The outgoing real game is persisted before archive starts, so returning to today's daily resumes intact. Archive is always re-launched from the calendar. The CLEAR end had no such guard until issue #247: `handleWin` ended with a bare `clearGameState(state.gameMode)`, so winning a past daily DELETED the real daily in progress, the player's reveals gone and the board back with a zeroed clock, in the one mode where a manual restart is deliberately impossible (`blocksManualRestart`), which also made it a way to re-clock a board already scouted. The same line hit the weekly slot from a past-weekly replay. `ownsSaveSlot` is the one question both ends ask, false for `isArchivePlay`, `isWeeklyArchive` and `isLevelPractice` (the ?level= / coastline / Par Lab lane, which borrows the challenge slot), and winLossHandler's three end-of-game paths clear through `_clearOwnSave`. Those lanes never persist, so skipping the clear leaves nothing behind. Pinned in `test/saveSlotOwnership.test.mjs`, which guards both ends by source scan because the rule was already right and the defect was a caller that never asked it.
- **Win path** (`winLossHandler`): `isArchivePlay` is excluded from `isRealDaily`, so streak, `saveProgress`, `markDailyCompleted`, the residual cache (`appendDailyResidual`), and the "day streak" suffix are all skipped. Submission routes through `submitArchiveCompletion`: read `dailyHistory[date]`; on a fresh date submit `submitArchiveScore` to `dailyArchive/` (only when `date >= ARCHIVE_FIT_EPOCH`) and write `dailyHistory` (the dedup key + the chart feed); a replay records nothing. Archive uses ONLY the auto-submit path (the manual name form stays hidden, with a defensive guard in main.js so a stale form can't post archive into `daily/`).
- **R refit** (`scripts/refit-par-model.R`): archive rows fetch from `dailyArchive.json`, parse through the shared `parse_score_rows`, bind with an `archive` marker, drop `cruxViewed` rows, and are held OUT of the fit until `ARCHIVE_FIT_THRESHOLD` (20) rows exist (instrument-first, like timed mode and new features). Once pooled, an `archivePlay` offset term (positive-only lognormal prior, since `build_priors` bounds every fixed effect at `lb=0`; a non-negative replay-pace offset is the documented assumption) absorbs the cohort shift and is netted out of the intercept bias-correction. `archivePlay` is FIT-ONLY, never written into `PAR_MODEL` (predictPar stays day-of par), exactly like `legacy_bombs`. Archive rows that collide with a same-`(uid,date)` day-of row are dropped (defends the falls-open dedup).


## Crux Teaser (`?crux=` share route)
A standalone share page showing a PAST daily's crux, the first step plain counting could not reach, as a "find the safe square" mini-puzzle, then a CTA to today's board. The teaser itself writes nothing, but the route is NOT fully write-free: `initAnonymousAuth` and the module-level lastSeen-beacon wiring in main.js run before the `?crux=` early-return, so a prod crux visitor still gets an anonymous session and (after auth settles) a `users/{uid}/lastSeen` stamp, deliberate, since a share-page visitor is a prospective player. Built for public growth (the par model needs sample size). Never spoils the live board: the route refuses today and later, and the default (`?crux=` / `?crux=1`) is yesterday ET.

- **One source of truth** (`src/logic/cruxExtract.js`, node-tested in `test/cruxExtract.test.mjs`): `extractCrux(board, rows, cols, fr, fc)` finds the crux = the first `isBoardSolvable(..., {trace:true})` entry with `tier >= 1` (the SAME definition the win-receipt confession uses, `winLossHandler._renderWinReceipt` now calls `extractCrux`, so receipt and teaser can never disagree about the square). Default first click is board center, matching the receipt and the feature/par solve. All trace entries are SAFE reveals (mines are flagged, never traced), so the crux is always a safe deduction; the sentences come from `explainDeduction`.
- **Pre-crux snapshot** (`boardSolver.js`, opt-in `{captureCruxState:true}`): captures `sim.slice()` (0 hidden / 1 revealed / 2 flagged) the instant before the first `tier>=1` reveal, the exact state a player faces at the crux. Additive and off in generation hot loops (like `trace`); lets `materializeCrux` skip re-implementing flood/unlock.
- **Materialization** (`materializeCrux`): crops the snapshot to the sources + answer + a widening ring (1→3, capped at 9×9 so the teaser stays phone-sized), rebuilds a plain mini (other gimmicks stripped) with every revealed number RECOMPUTED to count the mines shown so the real layout satisfies it (`findDeducibleFrontier` on a satisfiable system can never prove a false square), then re-verifies the answer is provably safe at `tier >= 1` from the shown numbers alone, widening until it is. **Walls are carried, not stripped**: in-crop wall edges (both endpoints inside the crop) are remapped into the mini so the recompute + re-verify are wall-aware, and they ship in the payload so the teaser DRAWS them, numbers, adjacency, and what the player sees all agree; out-of-crop walls can't affect an in-crop count, so they're dropped. Returns the `cruxes/{date}` payload `{rows, cols, cells:[{r,c,n}], answer:{r,c}, sources:[{r,c}], walls?:[edgeKey], tier, sentence, sentenceSocratic}` (~600 B, max ~1.4 KB) or null. **Coverage ≈ 77% of past canonicals** (measured 37/48); the rest are genuine breather boards (no tier>=1 step) or cruxes whose proving region is too wide to crop. `scripts/measure-crux-yield.mjs` reports yield/tiers/sizes.
- **Teaser page** (`src/ui/cruxTeaser.js` + `#crux-teaser` sibling of `#app`): `main.js` init branches on `?crux=` BEFORE the startup gate (resolve date, refuse `>= today` and `< FIRST_ARCHIVE_DATE` → fall back to yesterday, then render and return, no game init, no canonical prefetch). `loadCrux(date)` (dailyBoardSync) fetches the world-readable node (works logged-out). The mini renders revealed clues + fog, plus wall lines via `_renderMiniWalls` (a bar in each walled edge's gap, positioned from the laid-out cells' offsets, `pointer-events:none`). **The frame is "look how much Greg can prove", not "find THE safe square"** (a real position has many provably-safe cells, not one, a single-answer model wrongly bounced the others). The teaser recomputes the FULL deducible frontier ON THE PAGE (`findDeducibleFrontier` over the payload's numbers + walls via `_boardFromPayload`) and leads with the counts ("Greg can prove N squares safe and M mines"); left-tap / Enter OPENS a provably-safe cell (✓, advances a counter), right-click / long-press FLAGS a proven mine (the drawn flag sprite via `spriteImgHTML`, not an emoji), and any gated wrong gesture bounces with a teaching nudge, open only safe, flag only mines, the same control scheme and gating as the Gym. Greg and the flag render as the canonical drawn sprites (`spriteImgHTML('smiley'|'flag')`), so the share page matches the real game's look. A "Show me all" button (or finding every safe) lights up the whole frontier + the crux sentence + the play CTA. Because the frontier is recomputed client-side, this needed NO re-backfill; the payload's `answer`/`sources` fields are now vestigial (the `sentence` is still the featured crux explanation). Viewing sets `localStorage[CRUX_VIEWED_KEY_PREFIX + date] = '1'` (the flag the Daily Archive submit reads to drop a previewed date from the par fit). When there's no crux node, the route solves the canonical client-side (`loadDailyBoard` + `extractCrux`) to distinguish a genuine BREATHER (no tier>=1 step, shows "{date} was a breather…") from a crux that just couldn't be cropped (the rare liar case, keeps the plain "no teaser" line); no Firebase marker needed, and a liar board is never mislabeled a breather. Fog cells use class `crux-fog`, NOT `hidden` (the global `.hidden` is display:none).
- **Writes**: the nightly `precompute-daily-board.mjs` and the admin `regenerate-daily-board.mjs` write `cruxes/{date}` alongside the board + meta (regenerate refreshes/clears it so a stale layout is never described). `scripts/backfill-cruxes.mjs [--dry-run] [date]` populates past canonicals (strictly-past only), now via the `backfill-cruxes.yml` dispatch workflow. **Rules: `cruxes/{date}` is world-readable and `".write": false`, writable by NOBODY (issue #206, closed 2026-08-10).** It was cloned from `dailyMeta` and inherited that node's `auth != null && !data.exists()`, but the family rule is that the anonymous write-once form is granted ONLY where a real first-client fallback writer exists, and this node has none, the same reasoning that put `".write": false` on `boardHeatmap`. Measured live before the fix: **56 past dates carried a canonical board and no crux**, each permanently claimable by anyone who minted an anonymous session (the app does this on boot), on a public path the share route renders verbatim under the GregSweeper masthead; because both legitimate writers ALSO authenticated anonymously, neither could ever replace a node someone else had taken. Coverage is ~77% by design (breather boards, uncroppable cruxes), so that gap is structural and permanent rather than a backfill to run. **The service-account migration is deliberately NARROW**: `scripts/crux-write.mjs` is the one path to the node and mints its own token, while the precompute's `dailyBoard` and `dailyMeta` writes keep their anonymous auth, those have fallback writers and must keep working, so a missing or broken service account costs a teaser and can never cost a daily board. The nightly therefore fails SOFT (`mintCruxToken({ required: false })`, logs and skips) and the backfill fails HARD (`required: true`, cruxes are its only job, so writing zero silently would look like success). A service-account token BYPASSES the rules, so write-once is re-established by hand with an explicit `cruxExists` check; only `regenerate-daily-board.mjs` overwrites, which it does by deleting first, and it already used `access_token` so it is unaffected. Pinned by `test/cruxRules.test.mjs`, which also asserts the three nodes that DO keep an anonymous grant each have a named client writer, the question that should have been asked when this block was cloned.
- **Share card upgrade** (`generateShareCard` daily branch, HARD CEILING 5 lines + URL): title+date · `⏱ {t}s · beat Greg by {Δ}s 🦀` (Greg = par; over-par → "Greg won by") · pace bar · modifier icons + the board's hardest step in plain words (from the certified `state.boardCertificate.tier`, never more than proved) · strikes. The win modal's `#gameover-crux-challenge` ("🦀 Challenge a friend", daily/weekly wins only) copies `?crux=<yesterday>` (hardcoded prod base, like the card; cruxes read from prod even on the test build).


## Board Heatmap ("where the mines went off", Journal PR E)

The Journal's one POPULATION exhibit, and the only Firebase phase of the Journal arc: a past daily board drawn as a grid, each square shaded by how many players detonated a mine on it. `bombHitEvents[].{row,col}` on the score rows is the ONLY per-cell signal a client ever submits (`clickTimeline` never leaves the device; `hintEvents` carry no coordinates), so it is the one thing this can be built from.

- **Pure layer** `src/logic/boardHeatmap.js` (node-tested in `test/heatmapAggregate.test.mjs`) owns every decision that could fabricate a claim: `aggregateBombHits(scoreRows, board)` (the rollup's whole decision layer), `selectHeatmapDate(entries, completedDates)` (the gate), `heatmapCopy(plan, dateLabel)`, `heatLevel`/`maxCellCount`/`cellKey`/`parseCellKey`. The script and the client both consume it, so the map and the map's caption can never disagree.
- **Aggregation rules.** ONE ROW PER PLAYER per date (day-of wins over an archive replay, then earliest timestamp) so one person's two sittings can't read as two people struggling. `n_players` counts SOLVERS, not hitters, so it is the honest denominator for the rate scale. Brute-force probe rows (`isBombHitCheat`, most of the board's mines found by detonation) are dropped ENTIRELY, from both the cell counts and the denominator, that player is messing around, not playing (his ruling, 2026-07-18). Coordinates are bound-checked against the canonical board's `rows`/`cols`.
- **Shading is a RATE, not a rank (Christopher's ruling, 2026-07-18).** A square's level comes from the SHARE of that board's solvers who detonated it, on the fixed `HEAT_BANDS` scale (≤5% / ≤10% / ≤20% / above), so the same shade means the same thing on every board and the legend can state real percentages. The first implementation scaled against the board's own busiest square, which ranks rather than measures: a board where three people had a bad moment and nobody else did lit up as though it were brutal, because those three WERE the maximum. On a rate scale one hit among thirty reads as the 3% it is, which is why a single hit is safe to draw and why there is no per-square minimum. A square's count IS a distinct-player count (one row per player, and a struck mine stays revealed, so a player can hit a given square at most once), so the share is a genuine proportion of people.
- **The THREE gates (this is the feature's ethic, do not relax).** (1) AUDIENCE: nothing renders until `MIN_PLAYERS_FOR_HEATMAP` (30) distinct players have SOLVED a board. Below that the exhibit does not exist, no map, no waiting copy, no card (his ruling: keep it hidden until we regularly have 10+ players and probably closer to 30). (2) SPOILER: a board is only drawn for a player who has already completed it, the map lights only cells that held mines, and past dailies are replayable through the Daily Archive, so an unplayed board would ship as a partial mine map. Unknown history (signed out / failed fetch) resolves to 'none', never to a guess. (3) ALIGNMENT: the canonical board is REQUIRED, not preferred, if it cannot be fetched, or its shape disagrees with the rolled-up grid, the caption renders and the grid does not. In gates 1 and 2 the pure layer WITHHOLDS the payload rather than merely masking it, so a rendering bug cannot leak a map.
- **Rollup** `scripts/rollup-board-heatmap.mjs` + `.github/workflows/rollup-board-heatmap.yml` (15:30 UTC daily, after the 14:00 refit window, plus `workflow_dispatch` with `dryRun`/`refresh`/`date` inputs, all passed as ENV VARS rather than interpolated into the shell). Only dates strictly before today in ET are rolled up, so a map is built on settled scores. **`boardHeatmap/{date}` is writable by NOBODY at the rules layer** (`".write": false`), the sibling `cruxes`/`dailyBoard` blocks grant `auth != null && !data.exists()` because they have a legitimate first-client fallback writer, but this node has none, and copying that grant would let any anonymous visitor pre-claim a date and permanently publish a fabricated per-cell mine map with a forged `n_players` that sails past the honesty gate (the #114 poisoned-canonical class, with no signature layer and no coverage in the nightly sweep). The service-account script bypasses rules and is the only writer. **Every run RECOMPUTES the trailing `REFRESH_WINDOW_DAYS` (45, matching the client's fetch window)**: a date becomes eligible the moment it is past in ET and the cron runs at 11:30 ET, so a freeze-on-first-write would pin `n_players` at its day-after value and gate 1 could never open on its own. Dates older than the window are skipped unless `--refresh`. A date with no canonical `dailyBoard` is skipped rather than published unanchored.
