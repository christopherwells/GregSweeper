## Refit Workflow (.github/workflows/refit-par-model.yml)
- **The push RETRIES on a rebase.** A plain `git push` loses the whole night's fit when a human pushes to main while Stan is sampling, and that is not hypothetical: the 2026-08-03 run fit cleanly (4 files, 315 insertions) and died on `! [rejected] main -> main (fetch first)` because a PR merged mid-run, so the model just did not update that day and the failure read as a modeling problem. The four files the refit commits are refit-OWNED, so rebasing onto whatever landed is always the correct merge.
- **The refit's anchor is the PRECOMPUTE, not a wall-clock hour (moved 2026-08-07, again 2026-08-09).** The cron is `'17 23 * * *'`, 23:17 UTC, 3h43m ahead of `precompute-daily-board`'s 03:00 UTC run. **It moved an hour earlier because the margin had gone to the queue**: measured over the two nights the 00:17 cron ran, it STARTED at 02:28 and 02:24 UTC, a consistent ~2h10m late, finishing ~25 minutes before the precompute rather than the 2h43m intended, and another half hour of delay would have put it AFTER the board it informs, silently. At 23:17 the same delay lands it ~01:30, about 90 minutes clear. `test/poolReprice.test.mjs` pins that the two crons stay 3-12 hours apart so this cannot silently invert again. The original reasoning holds: so a night's board is generated under the model and experiment target fit that same night. The old 13:13 UTC slot put the refit AFTER the precompute it feeds, leaving every board written against a model 13.8h old. **This is NOT a fix for experiment-target drift** and must not be described as one: a board written on day D is still played on D+7 under a target rewritten seven times since, which is inherent to the seven-day horizon (the drift fix is that clients no longer re-derive the board, daily and weekly, same arc). What the move buys is coherent ordering plus his original complaint, that the refit reliably had not run by the time he checked at 10am. Still 17 minutes past and never on the hour, because GitHub queues top-of-hour crons behind everyone else's and the old 14:00 slot fired 60-120 minutes LATE all week (measured 2026-07-30..08-01); 00:17 UTC also sits clear of the Pages congestion window (~15:00-16:30 UTC). **Two consequences to know.** ET days roll at 04:00 UTC, so the fit now runs ~3h43m before the ET day in progress ends and plays from roughly 8pm ET onward land in the NEXT night's fit, a one-cycle delay on the tail of each day, falling uniformly on late-evening play, never a hole. And the `tilingBandConfigs` in-band CI alarm (the designed refit-drift alarm) now reddens ~2.7h before the precompute instead of ~14h, so a bad night has a much shorter window to be caught before boards are written on it. Cron ignores DST, so the anchor is ~7:17pm EDT / ~6:17pm EST the PREVIOUS evening, plus drift; the one-cycle lag therefore starts around 7pm ET rather than 8pm.
- **The refit RE-PRICES THE CHALLENGE POOL (2026-08-09).** Every pool entry's `ppc` is measured at the model of the day, and the ladder's band, the endless admission floor and the validator's acceptance band all match against it, so a refit left the whole pool mislabeled with nothing saying so. `scripts/reprice-challenge-pool.mjs` re-answers each price from `scripts/data/pool-features.json`, which stores the feature vector of the draw that set each entry's median par. **Measuring a spec is expensive and MODEL-INDEPENDENT, generation, certification, strict load-bearing, timing, and only the price is not**, so this costs seconds rather than the ~20 minutes a re-measurement would, and it relabels IN PLACE and never re-selects, so level assignments move only as far as prices genuinely moved. Exact rather than approximate: par is exp() of the linear predictor and so monotone in it, which makes the median-par draw the median-linear-predictor draw. The step is `continue-on-error` and checked afterward, a boundary violation means a re-SEARCH, which is a human's call, and the model fit (which also drives par, the handicaps, the experiment target and the next precompute) must not be lost to it. `src/logic/parModelFingerprint.js` records WHICH equations a capture was taken under, because a PR's checks run against the branch merged into main and the refit lands nightly, so "stale" and "broken" are different states wanting different remedies. **The SEARCH CACHE stores features and a fingerprint too** (`--reprice-cache` re-answers every cached price instantly, seeding itself from the pool store); entries measured before that keep their old price and the emit warns how many it is choosing from. **ADMISSION NEEDS HEADROOM, NEVER A PASSING MEASUREMENT**, the same lesson landed three times, on the generation cap (`ENDLESS_GEN_HEADROOM` 0.35, tightened from 0.75 after entries admitted at ~1000-1500ms measured 2207ms and 2327ms on other seeds; it costs 1.5% of the material), the endless floor (`PPC_FLOOR_MARGIN` 1.03) and the par ceiling (`PAR_CEILING_MARGIN` 0.95).
- Pulls `daily/*` and `dailyMeta/*` from Firebase (both world-readable, no secrets required), fits the Bayesian mixed-effects model via `brms` + Stan, patches `src/logic/difficulty.js` between `PAR_MODEL:START` / `PAR_MODEL:END` markers, and rewrites `src/logic/handicaps.json`. Commits both files under "Christopher Wells" identity and pushes to main, then explicitly dispatches the Pages deploy, GITHUB_TOKEN pushes never fire push-triggered workflows (GitHub's recursion guard), so without the dispatch each refit sat on main undeployed until the next human push (found and fixed 2026-06-10). Also pulls `dailyBoard/*` (world-readable) for the clue-digit derivation below. If that dispatched deploy fails in the Pages congestion window, the retry watchdog (`retry-pages-deploy.yml`, see Deploy under Development) re-dispatches it unattended.
- Guards: `MIN_SCORES_TO_FIT = 30` (total scores required, priors do the regularization so the old `MAX_COEF_DRIFT` clamp was retired), `MIN_PLAYS_FOR_FIT_INCLUSION = 5` (per-user TOTAL-play threshold, only users at/above this contribute to the global PAR_MODEL and receive a handicap entry in handicaps.json; below-threshold users get a provisional handicap computed client-side via `estimateHandicapFromHistory`. Set low because partial pooling shrinks a small-N user's random intercept toward zero and the heavy players anchor the fixed effects, so a light player can't drag the coefficients, the threshold only excludes true one-offs. Bomb-hit plays count toward the threshold now that they're included in the fit via the `bombHits` regressor), `ADAPT_DELTA = 0.99` with `MAX_DIVERGENT_FRAC = 0.25%`, a fit that comes back with Rhat > 1.05, ESS < 400, or more than 0.25% divergent transitions is rejected and the previous `PAR_MODEL` stays.
- Priors: the coefficients are now LOG-multipliers, so the prior CENTERS are OLS-seeded per refit from `lm(log(pure_time) ~ features)` (`compute_log_ols_seeds`), each a `lognormal(log(seed), sigma)` with the wide `PRIOR_SIGMAS` (sigma = 1.0). Variance priors are on the LOG scale (`normal(0,1)` residual, `student_t(3,0,1)` between-user), NOT the old seconds-scale values (which would be absurd on a log response). The seconds-scale `PRIOR_MEANS` at the top of the script are retained as documentation only. (OLS-seeding is dynamic per run; freeze a hardcoded log-scale `PRIOR_MEANS` if a stable non-ratcheting anchor is wanted.)
- After the fit: random intercepts are play-weighted-recentered in LOG space (geometric-mean centering, brms can park the baseline in either the global intercept or the random intercepts; without recentering the handicaps come out shifted by a common constant), then `k = exp(recentered ranef)`, clamped to `[0.1, 10]`. Each player's mean per-play bomb cost rides SEPARATELY as `bombSeconds` (never folded into `k`). The log-intercept is MEDIAN bias-corrected over day-of rows so `mean(log pure-play time) = mean(predicted log-par)`, par = `exp(Xβ)` is the time Greg beats half his runs (bombs live in the handicap, never in par).
- First CI run after a `brms` package cache miss takes ~5 min (Stan + dependencies compile). Subsequent runs hit the cache and finish in ~2-3 min including Stan model compilation.
- **Bomb-hit plays are kept in the fit; ALL bomb cost is subtracted out of `pure_time` BEFORE logging** (new-mechanic base surcharge `bombBaseSum` + legacy at a fixed `LEGACY_BOMB_RATE`/hit ≈ 15s, shipped as `secPerBombHit`), so there is NO bomb regressor under the log model. Each player's per-play bomb cost then rides as the separate additive `bombSeconds` in their handicap. The per-player bomb cost that par excludes is then folded back into THAT player's handicap (see Handicaps), so bombs are a personal handicap component, never board difficulty. Kept-not-filtered replaced an earlier filter-out that dropped ~60% of plays with asymmetric bias (Chris's bomb-hit rate is higher than Kate's). Clients submit per-hit `bombHitEvents: [{ t, row, col, penalty, infoValue }, ...]`. **Brute-force exception:** a run that found most of the board's mines by stepping on them IS dropped from the fit (the `df` filter mirrors the client `isBombHitCheat` gate, see the two-arm rule under Weekly), a probe's time (tiny wall-clock + every mine's info-value) is a garbage data point no matter how it's priced. The historical probes (e.g. the 100%-mine brute-force on 2026-06-15) are excluded the same way without being deleted from the leaderboard. **The bomb accounting needs only the strike COUNT, not the event log**, which is worth knowing before any backfill: `bombBaseSum = Σ(penalty − infoValue)` and `penalty = infoValue + BASE × (1 + RAMP × (i−1))`, so the difference is the ramped base alone and `bombBaseSum(n) = 3n + 0.75n(n−1)` exactly (13.5s at 3 strikes, 21s at 4). R reads it from `bombHitEvents` purely so the pre-2026-06-15 flat-base cohort needs no date split. The consequence is a trap: a row carrying `bombHits > 0` and NO events routes to the legacy path and is charged `LEGACY_BOMB_RATE` (15s/hit), while a row carrying `totalBombPenalty > 0` and no events computes `bombBaseSum = 0` and is charged NOTHING, so **there is no field combination that prices an event-less new-mechanic row correctly**, and one must either carry its events or accept the legacy rate.
- New features added to the fit follow a threshold guard: until ≥20 plays have nonzero values for a given new feature, its coefficient is pinned to 0 in the SHIPPED `PAR_MODEL` even if brms has fit a posterior. This avoids the lognormal-prior median (~prior_mean × 1.65) being shipped as a real coefficient, which would inflate `predictPar` with no data justification. The fit still treats it as a regressor so other coefficients aren't polluted by missing-data variance.
- **Clue-digit studies (2026-07-17, PR D, absorbed from Christopher's `cwells/par-digit-feature` experiment, commit 51d451f).** The arithmetic-load question: beyond board size and the reasoning tiers, does clue MAGNITUDE (more 2s vs 3s) cost time? `clue_digit_counts`/`digit_shares_from_boards` derive the per-board TRUE-adjacency digit counts FROM THE CANONICAL BOARDS at fit time (full historical coverage from day one, every `dailyBoard` back to `DIGIT_ERA_START = 2026-04-27` carries the data, no client instrument needed; before that date the stored board was regenerated by the backfill and does NOT match its `dailyMeta`/played time, so it is the provenance floor). Parameterization per his qmd: NONZERO-DIGIT SHARES with 5+ lumped and 1s the omitted reference (raw counts are density in disguise, mean clue ≈ 8×density, r = 0.94, reproduced locally 0.944, so only the SHAPE at fixed density can carry signal), scaled ×10 so one unit is "one extra clue-in-ten of that digit". The four features are `clueShare2/3/4/5plus`. **They are measured in a SEPARATE canonical-era SECONDARY brms fit** (`digit_df`, reusing the same lognormal + lb=0 + OLS-seed `build_priors`/`compute_log_ols_seeds` machinery, so a digit study reads on the same positive log-multiplier scale as every other study), whose posteriors merge into `target_candidates`, so a digit share can become the experiment target (a journal study) and appear in the parameter table, WITHOUT ever entering `PAR_MODEL`. This is the STRONGEST form of the new-feature ship-guard: the shipped `predictPar` is byte-identical with or without the digit block (verified: `grep clueShare src/logic/difficulty.js` = 0), so a digit coefficient still confounded with density can never move real par. The secondary fit is fully failure-tolerant (any error / bad diagnostics drops the digit candidates for the night and leaves the primary pipeline untouched) and gated on ≥`MIN_SCORES_TO_FIT` canonical-era rows with variance. **Note (flagged for review): on the current log-scale data (211 canonical-era rows) the digit effect is NOT the null Christopher's June seconds-scale read found (LRT p = 0.52, 155 rows), clueShare3 lands ~+30% per unit, tight (CV 0.18); digit VIFs 1.5-3.9.** Promote to a shipped par term only once the density confound is resolved on more players (the same instrument-first discipline as the per-technique predictors above).
- **Gimmick-contribution study (2026-07-30, instrument-first, secondary fit only).** Christopher's hypothesis: an INTEGRAL gimmick and an incidental one price differently, and raw cell counts cannot see it. The instrument is the strip-solve counterfactual the load-bearing filter always computed and discarded, per testable type, `<g>Required` + `<g>ClicksSaved` (no technique-delta, his ruling), plus the locked split `lockedMineCount`/`lockedNumberCount` (what is UNDER a lock is different work: a mine to prove vs a number delayed; `applyLocked` places both). **Plumbing:** emitted by `computeDailyFeatures` ONLY when the caller passes `opts.contributionOpener` (the certified opener), the final daily/weekly boards, both precompute meta writers, and the verify sweep pass it; the candidate-scoring hot loops (selectDailyRngSeed, the pipeline's per-candidate pass) never do, so a candidate vector just lacks the keys and no selection cost is paid. ## Adaptive Experimental Design
- EVERY daily generates 10 candidate seeds (`${dateString}:trial0`..`trial9`), solves each, scores each by its assigned mission, and picks the highest-scoring candidate. ~500-800 ms of CPU on first daily load.
- **Multi-objective per-slot missions.** Slot 0 = the PRIMARY mission, force-injecting the high-CV target's gimmick (chosen by the R refit) and allowed to roll a second gimmick at the natural ~10% rate. Slots 1-9 = COVERAGE missions, each force-injecting a different undersampled gimmick from the ranked `coverage_targets` list (also produced by the refit) and constrained to single-gimmick only via `getDailyGimmick(seed, rng, forcedGimmick, singleOnly=true)`. Slots map ONE-TO-ONE onto the coverage list and do NOT cycle: slot N takes `coverage[N-1]`, and a slot past the end of the list has no mission and is SKIPPED, so the effective candidate count is `1 + coverage.length` (with today's 8-entry list, 9 of the 10 slots are evaluated) unless a decorrelation mission claims the tail (next bullet). Wrapping would hand the top-deficit features double slots and silently halve the sampling rate of everything below them. **Four things are single-sourced in `experimentDesign.js` and must never be re-implemented anywhere**: the slot arithmetic (`resolveMissionForSlot`), the score formula and its cap (`missionCandidateScore` / `COUNT_CAP`), the candidate count (`resolveCandidateCount`), and the payload mission stamp (`missionStamp`). Both the client (`getMissionForSlot` → `selectDailyRngSeed`/`parResolve`) and the Node precompute (`daily-board-pipeline.missionForSlot` / `candidateCountFor`) call them. The slot mapping used to exist as two copies and DRIFTED (the pipeline wrapped, the client did not), so precompute could pick a `:trial8/9` seed the client would never choose and `parResolve` could quote a par for a different board than the date's canonical (fixed 2026-07-18; pinned by `test/missionSlots.test.mjs`); the other three followed it into one place before they could do the same. `TARGET_TO_GIMMICK` likewise now exists once, the pipeline's inline duplicate is gone.
- **Decorrelation missions (PR F1, 2026-07-18).** A third mission type, occupying the slots PAST the coverage list on nights the refit emits one. Primary missions chase a coefficient's uncertainty and coverage missions chase a gimmick's sample gap; neither breaks COLLINEARITY, which is what actually blocks a confounded coefficient, more boards of the same correlated shape cannot separate a feature from its confounder. A decorrelation mission aims at the RESIDUAL instead. The refit emits an optional `decorrelation_mission: { feature, confounder, slope, intercept, residualSd, weight }` (the fitted line between the worst-confounded PAIR it can act on), and the client scores a candidate by the MAGNITUDE of its residual, `|features[feature] − slope × features[confounder] − intercept| / residualSd`, capped at `COUNT_CAP` like every other mission. **Both tails count** (Christopher's ruling, 2026-07-18: "both tails should be sampled"): what reduces the correlation is residual VARIANCE, so a board two SDs BELOW the line is worth exactly as much as one two SDs above. An earlier cut scored a signed residual toward whichever tail the fit judged thinner; that discarded half the reachable boards for no gain in precision, and a one-sided design is also what would bury the inverted-U the clue-ambiguity hypothesis predicts. A board sitting ON the line scores 0 and loses the day to coverage, which is correct. All the statistics stay R-side; the client does one subtraction and one divide, so every player resolves the same board. Deliberately PAIRWISE rather than a multi-term VIF, because the client's scorer takes exactly two features and a mission it cannot act on is worse than none. `getTargetGimmickName` returns null for the target (there is no gimmick to force), so a decorrelation board rolls the NATURAL lottery and SELECTS rather than constructs, which makes candidate count its only reach knob: `resolveCandidateCount` adds `DECORRELATION_SLOTS` (10) past the coverage list on those nights, linear cost, paid only then. **With no mission emitted, selection is byte-identical to the pre-F1 behavior** (`resolveMissionForSlot` with a null/malformed mission returns exactly what it returned before), and `normalizeDecorrelationMission` rejects anything malformed so a corrupt file degrades to an ordinary day rather than a NaN score. **Frequency is a CADENCE, not a weight** (`DECORRELATION_INTERVAL` = 7 days, anchored to `lastDecorrelationDate` like the revalidation clock, advancing only on a night that shipped a mission). A confound bad enough to deserve a mission is bad every night, so a weight tuned to actually win takes the whole calendar: measured at 11 of 12 days, which starves the coverage slate. The weight itself is DERIVED R-side, solving for the residual depth at which a decorrelation board ties the strongest coverage mission, so it recalibrates when the deficits move; a flat guessed weight made the mission lose 12 of 12 days and ship as dead code. Measured reach (`scripts/measure-decorrelation-reach.mjs`, 400 generated boards, seeded and reproducible): the generator's natural confound is r = 0.76 / R² = 0.58 between `clueShare3` and `density`, and its residuals are symmetric (15.3% beyond 1 SD on each side); best-of-19 (a live decorrelation day with an 8-entry coverage list) reaches ≥1 residual SD 100% of the time and ≥2 SD 63%, landing above the line 59% of the time (so both corners really are sampled), and adds spread around the line without dragging either marginal far (3-share +0.46 SD, density +0.17 SD). The high-clue tail is NOT reachable by selection at all (60% of boards have no 5+ clue, median 0), which is the surviving case for F2's constructive placer. Pinned in `test/decorrelationMission.test.mjs`.
- **The clue-digit shares are MEASURED but never MAXIMIZED.** `clueShare2/3/4/5plus` are computed client-side by `clueShares` in `dailyFeatures.js` (a straight port of `clue_digit_counts` / `digit_shares_from_boards` in the R refit, same exclusions: mines carry no clue, mystery hides its number, a plate shows a timer; and since 2026-07-27 the same uncapped digit range on both sides, see Board Topology) so the digit axis is scorable at SELECTION time. The R refit keeps deriving them from the canonical boards for the fit, which is authoritative and covers every date back to `DIGIT_ERA_START`. They are listed in `OBSERVATIONAL_TARGETS` and the COUNT scorer returns 0 for them: every board feeds every digit study, so a "threes study" needs no threes-heavy board, and chasing a high 3-share would actively deepen the confound (3-share runs r ≈ 0.80 with density, so the boards that maximize it are the dense ones we already have too many of). Before the port this held by accident, because `features.clueShare3` was undefined; it is now explicit and regression-tested. The refit's `digit_df` join drops any meta-carried copies of the shares BEFORE joining the board-derived ones (`select(-any_of(DIGIT_FEATURES))`), without that, dplyr suffixes both sides to `.x`/`.y`, `digit_df$clueShare2` becomes NULL, `sd(NULL)` is NA, and the eligibility `if` (which sits OUTSIDE its tryCatch) kills the WHOLE nightly refit, not just the digit block.
- **Scoring, and the winner is a LOTTERY, not an argmax (2026-07-30).** Each candidate's score is `target_count_in_features × deficit_weight`, computed by the shared `missionCandidateScore` in `experimentDesign.js` (which both selection paths call, see the mirror-pair note below), where the target and weight come from `getMissionForSlot(i)`. Slot 0's weight is fixed low (`PRIMARY_WEIGHT = 0.1`). The day's winner is then drawn by `selectMissionWinner`, a weighted lottery over the scored slots (P ∝ score), seeded from the date alone (`${date}:missionDraw`, disjoint from the `:trialN` namespace), so every client and the precompute resolve the same winner. The argmax it replaced was a monoculture machine: deficit weights move slowly (`1/(n_boards+1)`, n growing ~1/day), so the top-deficit mission won EVERY day until saturation, worm took 10 of 12 shipped dates and the whole precomputed horizon (Christopher's report, 2026-07-30), because `min(wormLoad, COUNT_CAP) × 0.143 ≈ 0.71` against every other slot's ~0.36 ceiling. Same lesson as PR F1's weight tuning from the other side: a weight sets who wins a contest, never how often a mission runs, sampling ∝ score IS the frequency mechanism, and it self-corrects nightly as the refit moves the weights. Probed with the live 2026-07-29 spec over 30 days: worm 33%, mystery 20%, locked 13%, the rest 3-10%, primary ~7%, the ~1-in-10 primary intent lands on its own. Two deliberate edges: DECORRELATION slots keep argmax supremacy (top score outright → wins outright; below it → out of the draw entirely, their weight is R-derived to "tie the strongest coverage at depth" under exactly that contest, and their frequency is already owned by the 7-day cadence), and an all-zero pool draws uniformly rather than freezing on slot 0 (∝ band weight since the par bands landed, see Par Bands). Since 2026-08-02 the lottery is additionally PAR-BANDED: each candidate's score is multiplied by its closeness to the day's target par (`parBand.js`), which shifts mission-win shares ≤ ~4 points while ending out-of-band boards. Pinned in `test/missionWinner.test.mjs`, including a grep guard that neither path regrows a private argmax.
- **Force-injection rationale.** Without forcing, the natural per-seed gimmick-inclusion rate of ~6.6% means ~50% of seeds have zero of the targeted feature, making maximization meaningless. Force-injection drops miss rate to 0% so the 10-way contest competes on cell COUNT and DEFICIT WEIGHT instead of mere presence. All four call sites of `getDailyGimmick` (`selectDailyRngSeed`, `gameActions.js`'s play path, the on-demand par calc in `main.js`, and the precompute script) pass the same `(forcedGimmick, singleOnly)` resolved from `getMissionForSeed(seed)` so the chosen seed and the regenerated board match.
- **Primary-target selection.** After each fit, the coefficient with the highest posterior coefficient of variation (SD / |mean|) from a whitelist of push-able features wins, EXCLUDING any feature targeted in the last 3 days (`recentTargets` in `experimentTarget.json`). Stops three liar-heavy dailies in a row while still pushing data toward the most uncertain coefficient. Client fetches via `loadExperimentTarget()` in `src/logic/experimentDesign.js`. **Two additions ride this candidate pool (PR D, 2026-07-17):** (1) the four `clueShare*` digit shares (from the secondary fit, see Refit Workflow) are merged into `target_candidates`, so a digit share can WIN the primary slot and become a journal study; a digit target is OBSERVATIONAL (not a gimmick, so no force-injection, `getTargetGimmickName` returns null and it falls through to the natural lottery; `selectDailyRngSeed` scores it 0 via `OBSERVATIONAL_TARGETS` and a coverage slot wins the actual board, which is correct: every board feeds every digit study, so a "threes study day" needs no threes-maximized board. **That zero used to be accidental**, the shares were just not computed client-side. PR F1 ported the histogram so the decorrelation residual is scorable, so the refusal is now an explicit list; see the Adaptive Experimental Design section). (2) Every `REVALIDATION_INTERVAL = 14` days the primary target is instead the STALEST SETTLED feature (see Refit Workflow's revalidation bullet), stamped `reason: "revalidation"`.
- **Coverage-target selection.** The R refit counts unique-date occurrences of each gimmick feature, drops any gimmick at >= 20 boards (COVERAGE_SATURATION_BOARDS coverage throttle - saturated features still appear via the primary target or the natural lottery) in `df_fit`, computes `deficit_weight = 1 / (count + 1)` per gimmick, excludes the chosen primary target, and emits the result sorted descending by deficit. So `liarCellCount` with 1 board (deficit 0.5) ranks above `compassCellCount` with 5 boards (deficit 0.17). Lives in `experimentTarget.json` as `coverage_targets: [{feature, n_boards, deficit_weight}, ...]`.
- **Double-gimmick rate.** Default `DOUBLE_GIMMICK_PROB = 0.10` (was 0.20). The coverage missions absorb most of the "make boards more varied" goal so we don't need the natural double rate doing as much work, and lower noise = cleaner per-feature deltas. Coverage slots additionally suppress the roll entirely via `singleOnly`.
- **State plumbing.** `state.dailyRngSeed` holds the effective RNG seed (the trial variant on improvement days, plain dateString otherwise). All daily-mode RNG creation in `gameActions.js` routes through this field; `state.dailySeed` remains the plain date for Firebase keys / leaderboard joins / local-storage lookups. The play path uses `getMissionForSeed(state.dailyRngSeed)` to recover which mission won, then force-injects the matching gimmick, without this, a coverage-slot winner would get the primary gimmick force-injected on the play board and we'd ship the wrong layout.
- **Determinism.** Same date + same loaded primary + same coverage_targets list → same per-slot missions → same candidates → same winner across all clients. Cache-version drift on `experimentTarget.json` between clients can desync the chosen seed; Check-for-Updates handles most cases, and the diagnostics modal surfaces the loaded primary target + coverage list so mismatches are inspectable.
